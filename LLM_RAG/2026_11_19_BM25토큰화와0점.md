# 2026-11-19 · RAG 평가: 검색 누락과 답변 오류 구분하기

## 1. 오늘 배운 내용과 목표

- 오늘 배운 주제: RAG 6장 1~2강 평가셋과 지표, 7장 1~7강 평가셋 구축부터 실패 분석·개선 후 회귀 검증까지.
- 오늘의 목표: 답변이 틀렸을 때 근거를 못 찾은 건지, 근거는 찾았는데 답변이 틀린 건지 나눠서 확인하기.
- 이전 내용과 연결: BM25 검색에서 상위에 나왔다고 그 문서가 답을 담고 있는 것은 아니다. 평가할 때도 검색 순위와 근거의 충분함을 따로 본다. 오전에는 트랜스포머의 위치 정보, 어텐션, FFN이 한 블록 안에서 어떻게 이어지는지도 복습했다.

## 2. 개념과 용어 정리

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/명령어 | 뜻 | 기억할 점 / 주의점 |
| --- | --- | --- |
| 평가셋 | 질문, 기준 답변, 근거를 연결해 같은 조건으로 평가할 수 있게 만든 자료 | 한 문서로 답하는 질문, 여러 조건을 합쳐야 하는 질문, 문서만으로 답할 수 없는 질문을 섞는다. |
| `user_input` / `reference` | 사용자 질문 / 평가에 사용하는 기준 답변 | 기준 답변도 문서로 확인돼야 한다. LLM으로 초안을 만들어도 사람 검수가 필요하다. |
| `retrieved_contexts` / `response` | 시스템이 실제로 찾은 문맥 / 모델이 실제로 만든 답변 | 기준 근거를 검색 결과 자리에 넣으면 검색기 성능을 시험한 것이 아니다. |
| Context Precision | 질문에 유용한 근거가 검색 결과의 앞쪽에 있는지를 보는 지표 | 단순히 ‘관련 문서 수 / 가져온 문서 수’를 세는 방식으로 해석하지 않는다. |
| 문서 단위 F1 | 일반 정밀도와 재현율의 조화평균 `2PR/(P+R)` | 직접 세어 구하는 문서 단위 F1은 근거의 순서·답변의 주장까지 보는 RAGAS 지표와 구분한다. |
| Context Recall | 기준 답변을 만드는 데 필요한 내용이 검색 결과에 포함됐는지를 보는 지표 | 관련 문서가 첫 번째여도 핵심 조건이 빠졌다면 재현율은 낮을 수 있다. |
| Faithfulness | 모델이 답변에서 한 주장들이 검색 문맥의 뒷받침을 받는지를 보는 지표 | 질문과 관련 있는 말이라도 문맥에 없는 조건을 덧붙이면 충실도는 내려갈 수 있다. |
| Answer Relevancy | 답변이 질문에 직접 대응하는지를 보는 지표 | 관련성은 근거 검증이나 정오 판단을 대신하지 않는다. |
| 회귀 검증 | 변경 전후에 같은 평가셋을 돌려, 좋아진 사례와 나빠진 사례를 함께 확인 | 실패 사례만 고치고 정상 사례가 퇴보하지 않았는지도 본다. |

### 💡 참고 (검색용) - 이해만 하고 넘어가기

| 패턴/문법 | 뜻 | 필요할 때 찾는 팁 |
| --- | --- | --- |
| `EvaluationDataset.from_pandas(...)` | 표 형태로 준비한 평가 데이터를 RAGAS 평가 객체로 바꾸는 과정 | 지표에 필요한 필드가 무엇인지 먼저 확인한다. 검색과 생성 평가에 필요한 입력이 같지는 않다. |
| `evaluate(...)` → `to_pandas()` | 평가를 돌리고 질문별 결과를 표로 확인하는 흐름 | 평균만 보지 말고 질문, 근거, 답변, 점수를 같은 행에서 비교한다. |
| 임계값 | 기준보다 낮은 행을 검토 대상으로 뽑는 값 | 실패를 확정하는 규칙이 아니다. 경계값과 평가 모델이 바뀌면 선별 결과도 바뀔 수 있다. |

## 3. 예제 및 실습

### 실습 내용

#### 1) 6장 1~2강 / 7장 1~2강: 질문 유형을 나누고 평가셋을 만든다

- 단순 사실형: 규정의 시간이나 금액처럼 근거 한 곳에서 답을 찾을 수 있는 질문.
- 복합형: 재택근무를 허용하는 일반 규정과 수습 기간의 예외처럼, 두 근거를 함께 봐야 하는 질문.
- 답변 불가형: 지원금의 금액과 지급일은 있지만 첫 달 일할 계산이 문서에 없다면, 해당 질문의 기준 답변은 ‘문서로는 확인할 수 없다’가 된다.

평가용 질문과 기준 답변을 만들고, 어떤 근거로 검증할지 연결한다. 이후 검색기를 비교할 때는 같은 질문을 주고 **각 검색기가 실제로 찾은 문맥**을 따로 기록한다. 생성기를 비교할 때는 무엇을 바꾸는지에 따라 문맥을 고정하고 프롬프트만 바꿀 수도 있다.

#### 2) 7장 3~5강: 검색과 생성 점수가 서로 다른 이유

| 구분 | 예제 출력 | 무엇을 확인할까 |
| --- | --- | --- |
| 검색 지표 측정 | 도서관 질문 두 건, Context Precision 약 1.0 / Recall 1.0 | 관련 근거가 앞에 있어도 뒤에 무관한 문서가 들어 있을 수 있다. |
| 검색 누락 | 도서관 운영시간은 찾았지만 대출 한도는 빠짐, Precision 약 1 / Recall 0 | 관련 문서를 가져온 것과 답에 필요한 내용을 모두 찾은 것은 다르다. |
| 조건 불일치 | 2024년 1학기 질문에 2023년 2학기 장학금 문서, Precision 0 / Recall 0 | 질문에서 연도·학기를 놓쳤는지, 정답 문서가 애초에 색인됐는지부터 확인한다. |
| 생성 지표 측정 | 올바른 운영 안내의 Faithfulness 1.0 / Answer Relevancy 약 0.593 | 질문 관련성만 낮게 나왔다고 곧바로 오류로 확정하지 않는다. |
| 근거 없는 추가 주장 | 22시는 맞지만 ‘주말 24시간’을 덧붙인 답변, Faithfulness 0.5 / Relevancy 약 0.653 | 관련성 수치는 오히려 높았지만, 주말 24시간이라는 주장은 문맥에 없다. |

검색 실패 예제에는 정상 사례도 있다. 정상 조식 시간 답변의 근거는 충분히 찾았고 검색 지표가 약 1/1이었다. 나중에 파이프라인을 바꿀 때 이런 정상 사례도 같은 표에 남긴다.

#### 3) 7장 6~7강: 실패 행을 읽고 같은 질문으로 다시 검증하기

1. 점수가 낮은 행을 뽑고 질문에서 빠지면 안 되는 조건을 적는다.
2. 검색 문맥에 그 조건이 없으면 원문 색인, 메타데이터 필터, 청킹 순서로 의심할 지점을 좁힌다.
3. 근거가 있는데 답변에 새 주장이 붙었으면, 답변을 주장 단위로 쪼개 문맥과 연결한다.
4. 검색 설정이나 프롬프트를 한 번에 하나만 바꾼다. 정상 질문과 실패 질문을 그대로 다시 평가한다.
5. 충실도가 올라도 관련성은 내려갈 수 있으니 두 지표의 변화와 답변 본문을 함께 본다. ‘모두 답변 불가’로 바꿔 환각만 줄이면 정상 질문의 답도 없어질 수 있다. 예를 들어 같은 질문을 다시 비교한 한 행에서 관련성이 약 0.243에서 0.203으로 낮아졌다. 평균만 보면 이런 개별 회귀를 놓치기 쉽다.

#### 5) 복습 예제: 어디부터 고칠지 분류하기

다음 코드는 실제 모델이나 RAGAS를 실행하지 않는다. 가상의 필수 근거와 생성된 주장만으로, 문제를 검색과 생성 중 어디서 먼저 좁힐지 연습한다.

```python
def diagnose(required, retrieved, response_claims):
    missing = required - retrieved
    unsupported = response_claims - retrieved
    if missing:
        return "검색 근거 누락", sorted(missing)
    if unsupported:
        return "생성에서 추가한 주장", sorted(unsupported)
    return "이 예제에서는 이상 없음", []

required = {"운영시간", "대출한도"}
print(diagnose(required, {"운영시간"}, {"운영시간"}))
print(diagnose(required, required, required | {"주말24시간"}))
print(diagnose(required, required, required))
```

### 실행 결과

- 예제 출력: 생성 점수 평균은 Faithfulness 0.75, Answer Relevancy 0.6228이지만, 행별로 보면 어떤 주장이 문제였는지가 다르다.
- 위 독립 예제 예상 출력: 먼저 대출 한도의 ‘검색 근거 누락’, 다음은 주말 24시간의 ‘생성에서 추가한 주장’, 마지막은 ‘이 예제에서는 이상 없음’이다.
- 실제 RAG에서는 표현이 다를 수 있으니 단순 집합 비교 대신 근거와 답변의 의미가 맞는지 확인해야 한다.

## 4. 실수 및 트러블슈팅

- **관련 문서가 하나 있으니 검색 성공이라고 판단:** 도서관 운영시간은 찾았지만 대출 한도를 답할 수 없으면, 복합 질문 전체로는 부족하다. 질문을 조건별로 쪼개 문맥에서 하나씩 찾는다.
- **임계값 미달을 환각으로 단정:** 0.6 미만으로 두 답변이 모두 검토 대상으로 뽑혔어도, 실제 답변을 읽으면 한 건만 문맥에 없는 내용을 덧붙였다. 임계값은 검토 대상을 줄이는 데만 쓴다.
- **프롬프트만 바꿔 검색 누락까지 해결하려고 함:** 검색 문맥에 정답이 없으면 프롬프트가 근거를 만들어낼 수 없다. 반대로 근거가 충분한데 답이 틀리면 무조건 `k`를 올리기보다 답변이 근거를 어떻게 사용했는지 먼저 본다.
- **BM25 0점을 문서 자체 평가로 읽음:** 공백 토큰화에서 `VPN`과 `VPN을`은 다르다. `사내`는 토큰이 같아도 이 예제에서는 네 문서 중 두 문서에 있어 IDF가 0이다. 높은 키워드 점수와 답이 될 근거는 다르다.

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 검색 문맥과 생성 답변을 따로 남겨야 어디를 수정할지 알 수 있다.
- 💡 참고로 알아둘 내용: 평가셋에는 맞혀야 하는 질문뿐 아니라 근거가 없어서 답하면 안 되는 질문도 필요하다.
- ⚠️ 헷갈리기 쉬운 주의점: Precision이나 Relevancy 하나만으로 전체 RAG가 잘 작동한다고 판단하지 않는다.
- 한 문장 요약: 같은 질문을 기준으로 근거가 있나, 답변이 근거를 사용했나, 수정 뒤 다른 질문이 나빠지지 않았나를 차례로 본다.
