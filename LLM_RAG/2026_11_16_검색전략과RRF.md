## 2. 개념과 용어 정리

### 1) 키워드 검색과 벡터 검색

키워드 검색은 입력한 단어나 표현과 문서의 표현이 맞는지를 바탕으로 자료를 찾는다. 벡터 검색은 질문과 문서를 숫자 배열로 표현하고 의미적으로 가까운 자료를 찾는다.

| 필요한 검색 | 검토할 방식 | 이유 |
| --- | --- | --- |
| 모델명·오류 코드처럼 정확한 표현 찾기 | 키워드 검색 | 특정 식별자를 정확히 구별해야 함 |
| 표현이 달라도 비슷한 뜻 찾기 | 벡터 검색 | 같은 의미를 다른 말로 질문할 수 있음 |
| 정확한 표현과 비슷한 의미를 함께 활용 | Hybrid Search | 두 검색 방식의 장점을 함께 사용 |

복합기 앱에 적용한다는 가정으로 생각해봤다. 정확한 오류 코드로 매뉴얼을 찾는 경우와 ‘인쇄하면 검은 줄이 생긴다’는 증상으로 찾는 경우는 검색 요구가 다르다. 이 사례는 개념 이해를 위한 대화 예시이며 실제로 구현한 기능은 아니다.

### 2) TF와 IDF

- TF(Term Frequency): 한 문서 안에서 특정 단어가 얼마나 자주 등장하는지와 관련된 값.
- IDF(Inverse Document Frequency): 여러 문서에 흔하게 등장하는 단어의 구별력을 낮추고, 상대적으로 드문 단어의 구별력을 반영하는 값.

한 문서에서 자주 나오는 단어는 그 문서의 주제를 나타낼 수 있다. 하지만 모든 문서에서 흔하게 나오는 단어라면 특정 문서를 구별하는 힘은 약하다. 두 관점을 함께 사용해 단어의 중요도를 계산한다.

### 3) BM25와 단어 빈도 포화

판서에서는 단어 빈도 증가에 따라 점수가 계속 커지는 직선과, 처음에는 올라가다가 증가 폭이 줄어드는 BM25 곡선을 비교했다.

같은 검색어가 문서에서 반복되면 관련성 점수에 기여하지만, 반복 횟수가 늘어날수록 추가 반복의 효과는 줄어든다. 단어를 많이 반복한 문서가 점수를 과하게 받는 것을 줄이는 원리다.

BM25와 TF-IDF를 같은 알고리즘으로 보지는 않는다. 또 TF를 변환하는 방법에 따라 점수 계산이 달라지므로 모든 TF-IDF 구현이 항상 직선으로 증가한다고 일반화하지 않는다.

### 4) Hybrid Search와 가중치

키워드 검색과 벡터 검색을 함께 사용하고 결과를 결합하는 방식이다. 어떤 질문에는 정확한 용어가 중요하고, 어떤 질문에는 의미적 유사성이 중요할 수 있다.

필요에 따라 두 검색의 비중을 조절할 수 있지만, BM25 점수와 벡터 검색 점수는 범위와 의미가 다르므로 원점수를 단순히 더하는 방식은 주의해야 한다.

판서의 점수 범위 비교는 서로 다른 점수 체계를 설명하는 예시로 이해한다. 일반적인 코사인 유사도의 수학적 범위는 -1~1이며, 검색 서비스가 변환해 반환하는 점수와 구분한다.

### 5) RRF는 검색 순위를 합치는 방식

RRF(Reciprocal Rank Fusion)는 여러 검색 결과에서 문서가 몇 등으로 나왔는지를 바탕으로 순위를 결합한다. BM25와 RRF는 대체 관계가 아니라 역할이 다르다.

```text
BM25: 키워드 검색에서 문서별 점수와 순위를 계산
벡터 검색: 의미적 유사성을 바탕으로 순위를 계산
RRF: 각 검색의 순위를 이용해 결과를 결합
```

문서 하나에 대한 기본 RRF 점수는 각 검색에서 다음 값을 계산해 더하는 형태다.

```text
각 검색의 기여 점수 = 1 / (k + 순위)
최종 점수 = 해당 문서가 등장한 각 검색의 기여 점수 합계
```

여기서 k는 순위 차이가 점수에 미치는 영향을 조절하는 상수다. 이전 실습의 `retriever`에 사용한 `k=2`, 즉 가져올 문서 개수와는 다른 설정이다.

### 6) Query 변환

사용자 질문을 검색에 유리한 형태로 바꾸는 과정이다. 판서에서는 다음 흐름을 확인했다.

```text
사용자 질문 → LLM → 검색에 유리한 질문으로 변환
```

원래 의도를 유지하면서 검색에 필요한 대상이나 핵심 표현을 명확하게 하는 것이 중요하다. 질문을 바꾼 결과가 실제 검색 품질을 개선하는지는 확인해야 한다.

### 7) HyDE는 가상 문서를 검색 단서로 사용

HyDE(Hypothetical Document Embeddings)는 질문에 대해 가상의 답변 문서를 생성하고, 그 문서를 임베딩해 관련된 실제 문서를 검색하는 방식이다.

```text
질문 → LLM이 가상 문서 생성 → 가상 문서 임베딩
     → 실제 문서 집합에서 검색 → 실제 검색 자료를 답변 근거로 활용
```

가상 문서에는 틀린 세부 내용이 포함될 수 있다. 가상 문서 자체를 사실의 근거로 믿는 것이 아니라 실제 자료를 찾기 위한 단서로 사용한다.

### 8) 이후 목차에서 짚은 내용

판서에서는 Re-ranking, 맥락 압축·검색 최적화, 평가셋 구성과 검색·생성 지표, 실패 원인 분석으로 이어지는 목차도 확인했다.

맥락 압축은 검색된 자료에서 질문에 필요한 정보를 추려 전달하는 것과 연결된다. 필요한 근거를 잃지 않도록 해야 한다. 평가셋과 결과 비교는 검색 방식을 바꿨을 때 실제로 개선됐는지 판단하는 데 중요하다.

이 항목들은 목차를 짚은 범위이며, 각 기능을 상세 실습까지 완료했다는 뜻은 아니다.

## 3. 예제 및 실습

### 판서에서 확인한 RRF 계산

판서에서는 k=60을 사용했다.

```text
1등의 기여 점수 = 1 / (1 + 60) = 1/61
2등의 기여 점수 = 1 / (2 + 60) = 1/62
```

보충 예시로, 어떤 문서가 키워드 검색 1등이고 벡터 검색 2등이라면 두 기여 점수를 더해 최종 순위 계산에 사용한다. 검색 엔진마다 서로 다른 원점수를 직접 비교할 필요를 줄일 수 있다.

이번 화면 확인 구간은 판서 중심이었다. 검색 기능 구현, 코드 실행 시간 측정, 검색 품질 비교를 완료한 결과는 아직 이 기록에 포함하지 않는다.

### 문서가 없는 상태에서 기본 세팅을 맡긴다는 가정

대화에서 다음 상황을 질문했다.

> 수업 내용을 모르는 상태에서 ‘키워드 검색 기능을 만들고 싶다. 문서는 나중에 줄 테니 기본 세팅만 해봐’라고 하면 어떤 방식을 고를까?

논의한 기본 접근은 다음과 같다.

1. 문서를 넣을 자리와 검색어 입력·결과 표시 흐름을 준비한다.
2. 처음에는 단어가 포함된 부분을 찾는 단순 검색으로 연결한다.
3. 문서가 없을 때는 결과를 비워두고 검색이 완료된 것처럼 꾸미지 않는다.
4. 실제 문서를 받으면 형식·분량과 검색 예시를 확인한다.
5. 결과가 너무 많으면 관련도 순위, 표현이 달라도 찾아야 하면 의미 검색을 검토한다.

이것은 앞으로 구현을 요청할 때의 접근 방법이며, 이번에 실제 프로젝트를 새로 구성한 작업은 아니다.

## 4. 실수 및 트러블슈팅

### 1) 컴퓨터 유즈 연결 오류와 수업 확인 범위

처음에는 창 목록을 읽기 전 단계에서 ‘지정된 경로를 찾을 수 없습니다’ 오류가 발생했다. 연결 초기화 후에도 같았지만 Codex 앱을 재시작한 뒤 미트 창과 공유 판서를 확인할 수 있었다.

파일 정리가 원인이었는지는 확인되지 않았다. 재시작 후 연결이 복구됐다는 사실과 원인에 대한 추측을 구분한다.

화면을 볼 수 있게 된 뒤에도 수업 음성을 계속 듣거나 전체 강의를 자동 녹화한 것은 아니다. 판서에서 확인한 내용과 대화에서 보충한 설명을 중심으로 기록한다.

### 2) BM25와 RRF를 같은 종류의 선택지로 생각하기 쉬움

BM25는 키워드 검색의 점수 계산 방식이고, RRF는 여러 검색의 순위 결합 방식이다. ‘BM25 또는 RRF 중 하나’로만 생각하지 않는다. 필요하면 BM25로 얻은 순위를 RRF의 입력으로 사용할 수 있다.

### 3) 모든 검색 기능에 모든 고급 기법이 필요한 것은 아님

기본적인 키워드 검색 기능을 만든다고 해서 유료 임베딩 API, 벡터 DB, Hybrid Search, RRF, 재정렬을 처음부터 전부 넣을 필요는 없다. 기존 프로젝트 구조와 실제 자료를 보고 필요한 수준을 선택한다.

요구사항에 맞는 최소 구현을 만든 뒤 실제 질문에서 부족한 부분을 확인하고 개선하는 순서로 접근한다.
