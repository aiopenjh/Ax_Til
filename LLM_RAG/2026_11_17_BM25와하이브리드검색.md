- 오늘의 주제: RAG 5장 1강 BM25, 2강 하이브리드 검색.
- 목표: 같은 질문에서 키워드 순위와 벡터 순위가 어떻게 달라지고, 둘을 합치면 어떤 문서가 앞으로 오는지 판단하기.
- 기록 범위: 당일 갱신된 공개 튜터 코드와 노트북의 저장 출력을 바탕으로 만든 복습 기록이다. 당일 판서와 실제 수강 진도, 개인 노트북 실행은 확인하지 못했다. 3장 노트북의 검색 결과 포맷은 별도 점검으로만 덧붙였다.

## 2. 개념과 용어 정리

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어 | 뜻 | 기억할 점 / 주의점 |
| --- | --- | --- |
| BM25 | 질문에 나온 단어를 바탕으로 문서 관련도를 매기는 키워드 검색 방식 | 같은 단어를 많이 반복한다고 점수가 비례해 계속 오르지는 않는다. |
| 벡터 검색 | 질문과 문서를 임베딩으로 표현해 의미가 가까운 후보를 찾는 방식 | 가까운 문서가 항상 질문의 정답이나 출처는 아니다. |
| Hybrid Search | 두 검색기에서 얻은 후보를 결합하는 방식 | 이 예제는 키워드와 벡터 검색에 각각 0.5를 준다. 같은 비중은 품질 보장을 뜻하지 않는다. |
| 순위 결합 | 각 검색 결과 안에서의 순위로 기여도를 계산 | 단위가 다른 두 검색기의 원점수를 그대로 더하는 것과 다르다. |

### 💡 참고 (검색용) - 이해만 하고 넘어가기

| 패턴 | 뜻 | 필요할 때 찾는 팁 |
| --- | --- | --- |
| 가중 RRF | 문서가 각 목록에서 받은 `가중치 / (c + 순위)`를 합산하는 방식 | `c`는 순위 차이를 완만하게 하는 값이고, 검색기에서 몇 개를 가져오는지는 별개다. |
| PGVector | PostgreSQL에서 벡터 저장과 거리 기반 검색에 쓰는 확장 | 개념 비교는 DB 없이도 가능하고, 벡터 검색 자체를 검증할 때 DB가 필요하다. |

두 노트북은 **질문 자체가 다르다.** 표는 검색 결과이며 답변 생성의 정확도를 검증한 결과가 아니다. 2강 노트북에서는 검색기별 후보 수가 2여도 합쳐진 문서는 3개였다. 검색기별 후보 수와 결합 후 결과 수를 구분한다.

### 5분 연습 · 같은 질문의 후보 목록 두 개 합치기

아래 목록은 하나의 가상 질문에 대한 고정 후보 순위다. 라이브 검색이 아니라 순위 결합만 실행한다. `hybrid_rank.py`에 붙여 넣고 `python hybrid_rank.py`로 실행한다. 외부 라이브러리, API 키, DB는 필요 없다.

```python
def fuse(rankings, c=60):
    scores = {}
    for docs, weight in rankings:
        if weight == 0:
            continue
        for rank, doc in enumerate(docs, 1):
            scores[doc] = scores.get(doc, 0) + weight / (c + rank)
    return sorted(scores, key=lambda doc: (-scores[doc], doc))

keyword = ["A", "B"]
vector = ["B", "C"]
print(fuse([(keyword, 1), (vector, 0)]))
print(fuse([(keyword, 0.5), (vector, 0.5)]))
```

예상 출력:

```text
['A', 'B']
['B', 'A', 'C']
```

두 검색기에서 모두 나온 B는 각각의 순위에서 점수를 받는다. 이 작은 예제에서는 비중이 0인 검색기를 아예 제외하고, 동점이면 문서 ID로 정렬한다. 튜터 노트북 또는 라이브러리의 내부 동작을 그대로 복제한 코드는 아니다.

## 4. 실수 및 트러블슈팅

- **검색 설정과 질문을 동시에 바꾸면 원인을 분리할 수 없다.** 위 두 결과만으로 하이브리드가 더 좋다고 결론 내릴 수 없다. 같은 질문, 같은 문서, 같은 후보 개수를 유지한 뒤 검색 방식만 한 번에 하나씩 바꾼다.
- **검색한 문서와 답변에 넣은 문서가 다르면 결과를 믿기 어렵다.** 공개 [3장 노트북 코드](https://github.com/yonggyo1125/ax_study/blob/48627947fb30720a30653a924faf7e50b2d666dc/12_rag/chapter03/03_01.ipynb)에서 `format_docs(docs)`가 전달받은 `docs` 대신 바깥의 `searched_docs`를 읽는 부분을 확인했다. 새 검색 결과가 있어도 이전 문서가 들어갈 수 있는 코드다. 고칠 때는 함수 인자를 순회하고, 다른 문서 목록을 두 번 연속 넣어 출력이 각각 바뀌는지 확인한다. 개인 실습에서 발생한 장애를 뜻하지 않는다.

## 5. 오늘의 핵심

- BM25와 벡터 검색은 **각각 후보를 찾고**, RRF는 **그 후보의 순위를 합친다**.
- 0.5 대 0.5는 검색기 기여 비중이지 정확도나 정답 확률이 아니다.
- 검색을 비교할 때는 같은 질문·문서에서 기대 근거가 상위에 있는지 먼저 본다.
