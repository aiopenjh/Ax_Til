## 2. 개념과 용어 정리

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/명령어 | 뜻 | 기억할 점 / 주의점 |
| --- | --- | --- |
| BM25 | 질문에 나온 단어를 바탕으로 문서 관련도를 매기는 키워드 검색 방식 | 문서 안에서 해당 단어가 자주 나오면 유리하지만, 반복할수록 추가 점수는 작아진다. 문서 집합 전체에서 흔한 단어는 덜 중요하게 본다. |
| 벡터 검색 | 자연어 질문을 먼저 임베딩하고, 같은 모델로 미리 만든 문서 벡터와 비교하는 방식 | 가까운 문서가 항상 질문의 정답이나 출처는 아니다. |
| Hybrid Search | 두 검색기에서 얻은 후보를 결합하는 방식 | 이 예제는 키워드와 벡터 검색에 각각 0.5를 준다. 같은 비중은 품질 보장을 뜻하지 않는다. |
| 순위 결합 | 각 검색 결과 안에서의 순위로 기여도를 계산 | 단위가 다른 두 검색기의 원점수를 그대로 더하는 것과 다르다. |

### 💡 참고 (검색용) - 이해만 하고 넘어가기

| 패턴/문법 | 뜻 | 필요할 때 찾는 팁 |
| --- | --- | --- |
| 가중 RRF | 문서가 각 목록에서 받은 `가중치 / (c + 순위)`를 합산하는 방식 | `c`는 순위 차이를 완만하게 하는 값이고, 검색기에서 몇 개를 가져오는지는 별개다. |
| `PGVector` | PostgreSQL의 `pgvector` 확장을 사용하는 LangChain 벡터 저장소 클래스 | 벡터 검색을 실행하려면 PostgreSQL이 필요하다. 아래 RRF 순위 계산은 DB 없이 할 수 있다. |

## 3. 예제 및 실습

### 실습 내용

#### 1) 5장 1·2강: BM25와 하이브리드 검색 설정

- 1강 `05_01.ipynb`: 문장을 공백으로 나눠 BM25에 넣고, `k=2`로 사내 규정의 상위 후보 두 건을 찾는다.
- 2강 `05_02.ipynb`: BM25와 PGVector에서 각각 최대 두 건을 뽑고, `EnsembleRetriever`에서 두 검색기의 가중치를 `[0.5, 0.5]`로 둔다.

#### 2) 검색 점수 읽기와 순위 합치기

- 거리와 관련도: PGVector에서 코사인 거리로 설정한 `similarity_search_with_score`는 값이 작을수록 가깝다. `similarity_search_with_relevance_scores`로 반환한 관련도는 반대로 높을수록 가깝다. 그래서 0.2와 0.8을 비교하면 거리에서는 0.2, 관련도에서는 0.8이 더 유리하다. 3장 실습 코드가 관련도 임계치로 넘기는 값은 `1 - 0.7 = 0.3`이다. 옆 주석의 `0.7 이상`과 실제 값은 다르다. 다른 저장소에서도 같은 환산식을 쓴다고 가정하지 않는다.
- TF·IDF와 BM25: TF는 한 문서 안에서 단어가 나온 빈도, IDF는 그 단어가 전체 문서에서 얼마나 드문지에 따른 가중치다. BM25에서는 같은 단어가 처음 몇 번 나올 때보다 이미 많이 나온 뒤 한 번 더 나올 때 점수가 덜 오른다.
- RRF: BM25 원점수와 0~1로 표현한 벡터 관련도는 척도가 다르다. 원점수에 가중치만 곱해 더하면 척도가 큰 쪽에 끌릴 수 있다. RRF는 원점수 대신 각 목록의 순위를 사용한다.

BM25 비중 0.2, 벡터 비중 0.8, 순위 상수 `c=60`으로 계산해 봤을 때의 예시다. 순위 상수 `c`는 검색 후보 개수 `k`와 다르다.

| 문서 | BM25 순위 | 벡터 순위 | RRF 계산 | 결합 점수 |
| --- | ---: | ---: | --- | ---: |
| A | 1 | 3 | `0.2 / (60 + 1) + 0.8 / (60 + 3)` | 0.01598 |
| B | 2 | 1 | `0.2 / (60 + 2) + 0.8 / (60 + 1)` | 0.01634 |

이 조건에선 B가 앞선다. 위의 0.5:0.5 설정과는 가중치가 다르다.

#### 3) 5장 3강: 질문 유형별 RRF 가중치

- 여기서 가중치 순서는 `[BM25, 벡터]`다. 정확한 규정명·오류 코드를 찾을 때는 `[0.8, 0.2]`, 표현이 달라도 뜻이 비슷한 문서를 찾을 때는 `[0.2, 0.8]`부터 비교한다. 이 값들은 실험 출발점이지 정답은 아니다.
- 가중치 효과만 보려면 질문과 후보 순위를 고정한다. 위 문서 순위를 그대로 두고 `[0.8, 0.2]`를 적용하면 A 약 `0.01629`, B 약 `0.01618`로 A가 앞선다. `[0.2, 0.8]`에서 B가 앞선 결과와 비교할 수 있다.
- 이렇게 추린 문서는 LLM이 답변을 만들 때 참고할 근거로 넘길 수 있다.

참고: 메타데이터 필터는 연도나 분류로 후보 범위를 좁힌다. Top-k는 후보 수 상한이다. 컷오프를 둘 때 관련도 점수라면 최소값, 코사인 거리라면 최대값으로 읽는다. 실습 코드의 숫자와 주석이 다르면 실제 함수에 전달되는 값을 먼저 확인한다.

#### 4) 복습 예제: 후보 목록 두 개 합치기

아래 목록은 하나의 가상 질문에 대한 고정 후보 순위다. 라이브 검색이 아니라 순위 결합만 실행한다. `hybrid_rank.py`에 붙여 넣고 `python hybrid_rank.py`로 실행한다. 외부 라이브러리, API 키, DB는 필요 없다.

```python
def fuse(rankings, c=60):
    scores = {}
    for docs, weight in rankings:
        if weight == 0:
            continue
        for rank, doc in enumerate(docs, 1):
            scores[doc] = scores.get(doc, 0) + weight / (c + rank)
    return sorted(scores, key=lambda doc: (-scores[doc], doc))

keyword = ["A", "B"]
vector = ["B", "C"]
print(fuse([(keyword, 1), (vector, 0)]))
print(fuse([(keyword, 0.5), (vector, 0.5)]))
```

예상 출력:

```text
['A', 'B']
['B', 'A', 'C']
```

두 검색기에서 모두 나온 B는 각각의 순위에서 점수를 받는다. 이 작은 예제에서는 비중이 0인 검색기를 아예 제외하고, 동점이면 문서 ID로 정렬한다.

### 실행 결과

- 예제 출력: 1강 BM25는 원격 근무 → 계정 관리, 2강 하이브리드 검색은 보안 → 원격 근무 → 계정 관리 순서다.
- 새롭게 확인한 부분: 2강은 검색기별 후보가 최대 2건인데 결합한 결과는 3건이었다. 두 노트북은 질문이 다르므로 이 결과만으로 검색 품질을 비교하기 어렵다.

## 4. 실수 및 트러블슈팅

### 발생한 문제 요약

#### 1) 두 검색 결과를 바로 비교하기 어려움

- 상황: BM25와 하이브리드 검색의 저장 출력에서 문서 순서가 달랐다.
- 원인: 검색 방식과 함께 질문도 달라져 순위가 바뀐 이유를 한 가지로 좁힐 수 없었다.
- 해결: 질문, 문서, 후보 수를 고정하고 검색 방식만 바꿔 비교한다.
- 해결 결과: 저장 출력에서 순서 차이만 확인했다. 같은 조건의 비교는 다음 실습에 남겼다.

#### 2) 문맥 포맷 함수가 이전 검색 결과를 참조할 수 있음

- 상황: 3장 예제 `03_01.ipynb`에서 답변에 넣는 문서 목록을 확인했다.
- 원인: `format_docs(docs)`가 전달받은 `docs` 대신 함수 밖의 `searched_docs`를 읽는다.
- 해결: 함수에서 전달받은 `docs`를 순회하고, 서로 다른 문서 목록 두 개로 출력이 바뀌는지 비교한다.
- 해결 결과: `docs`만 순회하면 호출할 때 넘긴 문서 목록이 문맥에 들어간다.
