## 2. 개념과 용어 정리

### 1) LLM의 한계와 RAG가 필요한 이유

지식 컷오프는 모델이 학습한 지식의 기준 시점이다. 웹 검색이나 외부 문서를 참고하면 그 이후 정보도 답변에 사용할 수 있지만, 모델의 학습 지식 자체가 매번 자동으로 갱신되는 것은 아니다.

환각은 근거가 없거나 틀린 내용을 그럴듯하게 생성하는 현상이다. 최근 모델은 검색과 도구 사용, 모르는 내용에 대한 대응이 개선됐지만 오류가 사라진 것은 아니다. 검색한 문서를 잘못 읽거나 일부 근거만 보고 잘못 결론을 낼 수도 있다.

코드를 새로 만드는 것 자체는 환각이 아니다. 실제로 없는 라이브러리 함수를 있다고 설명하거나, 실행하지 않은 코드를 검증됐다고 말하는 것이 문제다. 실행에 성공해도 요구한 결과가 맞는지는 별도로 확인해야 한다.

```text
코드 작성 → 실행 → 오류 확인 → 수정 → 다시 테스트
                         ↓
             결과가 요구사항과 맞는지도 확인
```

같은 테스트를 반복하는 것만으로 모든 상황을 검증할 수는 없다. 빈 값, 잘못된 입력, 경계값 등 다른 조건도 확인해야 한다.

RAG는 질문과 관련된 자료를 먼저 검색하고, 그 자료를 LLM에 제공해 답변을 생성하는 방식이다. 최신 정보나 내부 문서를 참고할 수 있지만, 검색된 자료가 잘못됐거나 모델이 잘못 해석하면 답도 틀릴 수 있다.

### 2) RAG의 전체 흐름

```text
[미리 준비]
문서 수집 → 텍스트 정리 → 청킹 → 임베딩 → 벡터 저장소에 저장

[질문이 들어왔을 때]
질문 → 질문 임베딩 → 관련 청크 검색
     → 검색 결과와 질문을 프롬프트에 조립 → LLM 답변 생성
```

검색과 생성은 서로 다른 단계다. 검색은 참고할 자료를 고르고, 생성은 그 자료와 질문을 바탕으로 답을 작성한다. LLM이 모든 답변을 벡터 DB에서 그대로 꺼내 오는 것은 아니다.

같은 질문에 같은 임베딩 모델을 사용하면 일반적으로 같은 벡터가 나온다. 그래도 저장 자료의 변화, 검색 설정, 생성 과정 등의 차이 때문에 최종 답변이 항상 같다고 보장되지는 않는다.

### 3) ETL과 청킹

| 단계 | 뜻 | RAG에서 하는 일 |
| --- | --- | --- |
| Extract | 추출 | 문서에서 필요한 텍스트 가져오기 |
| Transform | 변환 | 정리, 청킹, 메타데이터 구성, 임베딩 등 검색용 가공 |
| Load | 적재 | 가공한 데이터와 벡터를 저장소에 넣기 |

Transform은 단순히 컴퓨터 언어로 번역하는 것보다 넓은 개념이다. 필요 없는 문자를 제거하고 문서를 검색하기 좋은 단위로 나누는 작업도 포함한다. 실제 시스템에서는 임베딩 생성 등 일부 단계가 별도 작업으로 나뉠 수 있다.

청킹은 긴 문서를 검색에 사용할 작은 조각으로 나누는 것이다. overlap은 조각의 경계에서 문맥이 끊기지 않도록 일부 내용을 겹치는 설정이다.

- 너무 작은 청크: 필요한 설명이 여러 조각으로 흩어질 수 있다.
- 너무 큰 청크: 질문과 관계없는 내용까지 많이 포함될 수 있다.
- overlap 증가: 문맥 보존에 도움이 되지만 중복과 저장량이 늘어난다.

복합기 매뉴얼처럼 오류 코드별로 나눌 수도 있다. 다만 `E6XX`, `E4XX` 같은 범주의 실제 의미는 제조사와 모델의 매뉴얼을 확인해야 한다. 코드만 보고 모든 기종에서 동일한 부품 고장이라고 단정하지 않는다. 제조사, 모델명, 오류 코드, 문서 위치를 메타데이터로 함께 관리하면 검색 범위를 좁히기 좋다.

### 4) 임베딩, 벡터 차원, 메모리

임베딩은 문장이나 이미지의 특징을 숫자 목록인 벡터로 표현하는 것이다. 검색에서는 질문과 문서의 벡터를 비교해 관련성이 높은 자료를 찾는다. 같은 검색 공간에서 비교하려면 호환되는 임베딩 모델과 설정을 사용해야 한다.

```text
질문 문장 → 임베딩 모델 → [0.1, 0.2, ..., 0.02]
```

벡터의 크기를 말할 때 차원 수와 저장 용량을 구분한다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 차원 | 벡터에 들어 있는 숫자 개수 | 1,536차원 |
| 자료형 | 숫자 하나를 저장하는 방식 | float32는 4바이트 |
| 원시 벡터 용량 | 차원 수 × 숫자당 크기 | 1,536 × 4 = 6,144바이트, 약 6KiB |

위 계산은 벡터 숫자 자체만의 용량이다. 실제 저장소는 원문, 메타데이터, 검색 인덱스 등의 공간도 사용한다. 모든 저장 데이터를 항상 RAM에 올려두는지 여부도 구현 방식에 따라 다르다.

이미지도 임베딩할 수 있지만, 검색용 임베딩만으로 원본 이미지를 그대로 복원할 수 있다고 생각하면 안 된다. 이미지 생성·복원 모델이 사용하는 잠재 표현과 일반 검색용 임베딩은 목적과 구조가 다르다.

### 5) 벡터 유사도 계산

| 방법 | 비교하는 것 | 해석할 때 주의할 점 |
| --- | --- | --- |
| 코사인 유사도 | 두 벡터의 방향 | 일반적으로 클수록 방향이 비슷함 |
| 유클리디안 거리 | 두 점 사이의 거리 | 일반적으로 작을수록 가까움 |
| 내적 | 대응 좌표를 곱해 더한 값 | 방향뿐 아니라 벡터 크기도 영향을 줌 |

벡터를 정규화했는지에 따라 결과의 의미가 달라진다. 숫자가 비슷하다는 이유만으로 실제 의미가 항상 정확히 일치하는 것은 아니다. 검색된 원문이 질문에 답할 수 있는 내용인지 확인해야 한다.

BM25는 단어 기반 검색, Query Rewrite는 검색에 적합하게 질문을 다듬는 과정, Reranking은 검색된 후보의 순위를 다시 평가하는 과정으로 개념을 확인했다. 오늘 이 기능을 모두 직접 구현한 것은 아니다.

### 6) 프롬프트 템플릿

`ChatPromptTemplate`은 역할과 질문이 들어갈 자리를 미리 정해 메시지를 조립하는 도구다.

- system: 답변 역할이나 방식에 대한 지시
- user: 실제 사용자 질문
- `{question}`: 나중에 질문을 넣을 자리

템플릿에 값을 채워 메시지를 출력하는 것과 LLM을 호출해 답변을 받는 것은 다르다. 템플릿 조립만 확인하는 단계에는 모델 API 호출이나 임베딩이 필요하지 않다.

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/명령어 | 뜻 | 기억할 점 / 주의점 |
| --- | --- | --- |
| RAG | 검색한 자료를 참고해 답변 생성 | 검색 품질과 생성 품질을 나눠 확인 |
| Chunk | 문서를 나눈 검색 단위 | 크기와 경계가 검색 결과에 영향 |
| Overlap | 청크 사이에 겹치는 내용 | 문맥 보존과 중복 비용의 균형 |
| Embedding | 특징을 벡터로 표현 | 질문과 문서에 호환되는 모델 사용 |
| Vector Store | 벡터와 관련 자료를 저장·검색 | 원문과 메타데이터도 함께 필요 |
| Retriever | 질문에 관련된 자료를 찾는 구성 요소 | 검색 결과가 정답이라는 보장은 없음 |
| ChatPromptTemplate | 역할과 입력을 조립하는 틀 | 조립과 모델 호출을 구분 |

### 💡 참고 (검색용) - 이해만 하고 넘어가기

| 패턴/문법 | 뜻 | 필요할 때 찾는 팁 |
| --- | --- | --- |
| ANN | 가까운 벡터를 빠르게 찾는 근사 검색 | 데이터가 많을 때 속도와 정확도 검토 |
| BM25 | 단어 기반 검색 점수 | 정확한 코드·고유명사 검색과 함께 검토 |
| Query Rewrite | 검색어·질문 재작성 | 질문이 모호할 때 |
| Reranking | 검색 후보 순위 재평가 | 첫 검색 결과의 순서를 개선할 때 |
| 파인튜닝·LoRA·PEFT | 모델을 조정하는 학습 방법과 관련 기술 | 외부 문서 검색인 RAG와 목적 구분 |

## 3. 예제 및 실습

### 수업 예제: 학교 규정 검색

튜터의 `12_rag/chapter01/src/02.ipynb`에서 다음 흐름을 확인했다.

```text
학교 규정 문서
  → 청크 크기 90, overlap 20으로 분리
  → 4개 청크
  → 임베딩과 InMemoryVectorStore
  → retriever로 관련 규정 검색
  → 질문과 검색 결과를 프롬프트에 넣기
  → 답변 생성
```

튜터 노트북에는 최대 신청 학점 질문에 대해 다음 학기에 최대 21학점까지 신청할 수 있다는 출력이 저장돼 있다. 이 결과는 예제 학교 규정에 대한 것이며 모든 학교의 실제 규정으로 일반화하지 않는다.

`similiarity.ipynb`는 puppy, dog, Apple을 1,536차원으로 임베딩하고 코사인 유사도와 유클리디안 거리를 비교하는 예제다.

### 실행 결과와 남은 확인

- 청킹 예제의 4개 청크 생성은 앞선 실습에서 확인했다.
- 튜터 코드에는 검색·답변 생성과 유사도 계산 결과가 저장돼 있다.
- 최신 튜터 자료를 받은 이후 내 컴퓨터에서 전체 노트북을 다시 실행해 최종 답변까지 확인한 결과는 아직 기록하지 않는다.
- 영어 회화 도우미 문제 1-1은 직접 풀기 시작한 단계다. `ChatPromptTemplate`으로 메시지를 조립하고 소스코드와 출력 캡처를 준비하는 과제이며, 완료·제출 결과는 아직 확인되지 않았다.

## 4. 실수 및 트러블슈팅

### 1) Codex 로그인과 임베딩 API를 같은 기능으로 생각함

- 상황: 별도 API 대신 Codex 연결만으로 수업 예제를 진행하고 싶었다.
- 확인한 내용: Codex의 대화용 로그인과 코드에서 사용하는 임베딩 API는 같은 인터페이스가 아니다. 대화가 가능하다고 임베딩 엔드포인트도 바로 사용할 수 있는 것은 아니다.
- 진행: 수업에서는 튜터가 안내한 API 방식으로 환경을 설정했다. 키 값은 TIL이나 저장소에 남기지 않는다.
- 남은 확인: 실제 임베딩·최종 답변 생성 실행은 별도로 확인한다. 인증 성공만으로 전체 RAG 동작 성공을 단정하지 않는다.

### 2) 임베딩·검색·생성을 하나로 생각함

- 상황: 답변이 모두 미리 저장된 벡터에서 그대로 복원되는 것처럼 이해했다.
- 정리: 임베딩은 비교 가능한 표현을 만들고, 검색은 관련 자료를 고르며, LLM은 입력된 맥락을 바탕으로 답변을 생성한다.
- 주의: 검색용 벡터가 원본 내용을 완전하게 보관하는 압축 파일은 아니다.

### 3) 코드가 실행되면 답도 맞다고 생각함

- 정리: 문법 오류 없이 실행되는 것과 요구한 결과가 나오는 것은 별개다.
- 확인 방법: 기대한 값과 실제 값을 비교하고, 정상 입력 외의 조건도 테스트한다.

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: RAG는 외부 자료를 검색해 LLM의 답변에 근거로 넣는 구조다.
- 💡 참고로 알아둘 내용: 검색은 벡터 유사도뿐 아니라 단어 검색, 검색어 재작성, 재정렬로 보완할 수 있다.
- ⚠️ 헷갈리기 쉬운 주의점: 벡터 차원과 바이트 수, 템플릿 조립과 모델 호출, 튜터 실행 결과와 내 실행 결과를 구분한다.
- 한 문장 요약: 문서를 잘 나누고 질문과 관련된 근거를 찾아 전달한 뒤, 검색 결과와 최종 답변을 각각 검증한다.
