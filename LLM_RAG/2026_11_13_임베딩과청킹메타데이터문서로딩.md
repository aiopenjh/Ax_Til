## 2. 개념과 용어 정리

### 1) 인덱싱 안에 청킹과 임베딩이 들어간다

RAG의 큰 흐름은 인덱싱과 질의 처리로 나눌 수 있다. 인덱싱을 청킹과 같은 뜻으로 생각했는데, 청킹은 인덱싱에 포함되는 한 과정이었다.

```text
[인덱싱: 질문을 받기 전에 준비]
문서 수집 → 문서 분할 → 임베딩·저장

[질의 처리: 질문이 들어오면 실행]
질문 임베딩 → 관련 청크 검색 → 질문과 근거를 LLM에 전달 → 답변 생성
```

수업의 5단계는 수집 → 분할 → 임베딩·저장 → 검색 → 생성이다. 앞의 세 단계는 검색할 자료를 준비하고, 뒤의 두 단계는 질문에 맞는 자료를 찾아 답변을 만든다.

문서가 그대로라면 질문할 때마다 모든 문서를 다시 임베딩할 필요는 없다. 추가되거나 바뀐 부분을 반영하면 된다. 다만 임베딩 모델이나 청킹 기준을 바꾸면 기존 인덱스와의 호환성을 확인하고 다시 구축할 범위를 정해야 한다.

### 2) 임베딩은 의미를 비교할 수 있는 숫자 배열을 만드는 것

임베딩은 단어나 문장의 의미적 특징을 숫자 목록인 벡터로 표현하는 과정이다. 질문과 문서를 호환되는 임베딩 모델로 변환한 뒤 벡터의 방향이나 거리를 비교한다. 숫자로 바꾸는 단계와 관련 문서를 찾아오는 단계는 구분한다.

판서에서는 다음과 같은 원핫 표현과 실수 벡터를 비교했다.

```text
[원핫 표현 예시]
나는   → [1, 0, 0]
너를   → [0, 1, 0]
사랑해 → [0, 0, 1]

[학습된 임베딩 표현 예시]
문장 → [0.1, 0.02, ...]
```

원핫 표현은 각 항목을 구별하지만 그 자체로 의미가 얼마나 가까운지 표현하지는 않는다. 학습된 임베딩은 여러 좌표에 특징을 나누어 담아 의미의 유사성을 비교하도록 만든다. 실제 좌표 하나하나가 사람이 정해 둔 ‘과일’, ‘감정’ 같은 항목과 일대일로 대응하는 것은 아니다.

#### 내가 궁금했던 벡터의 숫자와 차원

- 1,536차원은 벡터 안에 숫자가 1,536개 있다는 뜻이다. 숫자의 최댓값이 1,536이라는 뜻이 아니다.
- `text-embedding-3-small`은 기본 설정에서 텍스트 하나를 1,536개의 숫자로 표현한다. 모든 임베딩 모델의 차원이 같은 것은 아니다.
- `...`는 나머지 좌표를 생략한 표시다. 무한히 이어진다는 뜻이 아니다.
- 좌표는 `-0.01`부터 `1.00`까지 0.01 간격으로만 정해지는 것이 아니다. 더 작은 소수 값도 들어갈 수 있다.
- 실제 컴퓨터는 유한한 정밀도로 숫자를 저장한다. 가능한 조합이 매우 많지만 무한대인 것은 아니다.
- 벡터를 길이 1로 정규화한 경우 각 좌표는 -1과 1 사이에 있지만, 모든 종류의 임베딩에 동일한 값 범위를 가정하면 안 된다.

1,536차원을 그대로 눈으로 그릴 수는 없다. 교안의 사과·바나나와 컴퓨터·모니터 그림은 의미가 가까운 항목을 공간에 배치한다는 개념도다. 실제 1,536차원 벡터를 계산해서 축소한 결과인지는 그림만 보고 단정할 수 없다. 실제 벡터를 시각화할 때는 차원 축소를 사용할 수 있고, 이때 원래 관계의 일부가 손실될 수 있다.

### 3) 코사인 유사도와 유클리디안 거리는 읽는 방향이 다르다

| 비교 방법 | 무엇을 비교하나 | 결과를 읽는 방법 |
| --- | --- | --- |
| 코사인 유사도 | 두 벡터의 방향 | -1부터 1까지이며 1에 가까울수록 같은 방향 |
| 유클리디안 거리 | 두 점 사이의 직선거리 | 0 이상이며 작을수록 가까움 |
| 내적 | 대응 좌표의 곱을 더한 값 | 방향과 벡터 크기가 함께 영향을 줌 |

판서의 피타고라스 정리 `√(a² + b²)`를 고차원으로 확장하면 유클리디안 거리의 계산을 이해할 수 있다. 좌표별 차이를 제곱해 모두 더하고 제곱근을 구한다.

코사인 유사도 0은 방향이 직각이라는 뜻이고, -1은 반대 방향이라는 뜻이다. 음수라고 문장의 뜻이 반드시 반의어 관계라는 뜻은 아니다. 유사도 점수는 정답일 확률도 아니다.

ANN은 가까운 벡터를 빠르게 찾는 근사 검색 방법이다. 코사인·유클리디안·내적과 함께 네 번째 거리 공식으로 묶으면 안 된다. 무엇으로 가까움을 측정할지와 어떻게 빠르게 찾을지는 서로 다른 선택이다.

### 4) 청킹은 덩어리 나누기이고 recursive는 재귀적이라는 뜻

`CharacterTextSplitter`는 지정한 구분자를 기준으로 텍스트를 나누고 크기에 맞춰 묶는다. 구분자 사이의 덩어리가 너무 크면 설정한 크기를 넘는 청크가 생길 수 있다. `separator=""`로 설정하면 문자 단위로 나눌 수 있지만 문장 중간이 잘릴 수 있다.

`RecursiveCharacterTextSplitter`는 큰 단위로 나누어 보고, 아직 너무 큰 부분에는 더 작은 구분 기준을 적용한다. 기본 구분자 순서는 다음과 같다.

```python
["\n\n", "\n", " ", ""]
# 문단 → 줄바꿈 → 공백 → 문자 단위
```

마지막 기본값은 마침표가 아니라 빈 문자열이다. 별도 목록을 지정할 때 인자 이름은 `separators`다.

| 설정 | 의미 | 주의할 점 |
| --- | --- | --- |
| `chunk_size` | 청크를 만들 때 목표로 하는 최대 길이 | 기본 길이 계산은 문자 수이며 토큰 수와 다름 |
| `chunk_overlap` | 인접 청크가 일부 내용을 공유하도록 하는 설정 | 경계에서 문맥이 끊기는 것을 줄이지만 모든 청크가 정확히 같은 길이만큼 겹치는 것은 아님 |

overlap을 ‘까먹는 것을 줄이는 장치’라고 이해했는데, 정확하게는 모델의 기억을 늘리는 기능이 아니라 잘린 문서 경계의 문맥을 보완하는 설정이다. 겹침이 많아지면 중복 저장과 임베딩 비용도 늘어난다.

### 5) 메타데이터는 본문에 붙이는 관리 정보

LangChain의 `Document`는 본문인 `page_content`와 부가 정보인 `metadata`를 함께 담는다.

```python
file_info = {
    "source": "cs_lab_policy.pdf",
    "department": "컴퓨터공학과",
    "version": "v1.2",
}
doc = Document(page_content=raw_text, metadata=file_info)
```

`split_documents([doc])`로 나누면 각 청크에 원본 메타데이터가 전달된다. 파일명, 학과, 버전, 페이지 등의 정보는 검색 조건을 좁히고 원문을 찾아갈 때 사용할 수 있다.

처음에는 ‘결국 답변 맨 뒤에 file_info를 붙이는 것 아닌가?’라고 생각했다. 하지만 정보 보관과 화면의 출처 표시는 별개다. 출처를 답변에 표시할지는 서비스의 요구사항으로 정할 수 있고, 내부 메타데이터는 검색·필터링·문서 갱신에도 활용한다. 출처가 붙어 있다는 사실만으로 답변의 정확성이 보장되는 것도 아니다.

### 6) 문서 로더는 파일을 공통 구조로 읽어오는 도구

PDF와 웹페이지는 저장 구조가 다르다. 문서 로더는 각 형식에서 본문과 속성을 추출해 LangChain에서 처리할 `Document` 목록으로 변환한다.

| 도구 | 역할 |
| --- | --- |
| `PyMuPDFLoader` | PDF를 읽고 본문·페이지 등 메타데이터를 추출 |
| `WebBaseLoader` | 웹페이지 HTML을 읽고 텍스트·출처 등을 추출 |
| `.load()` | 로더를 실행해 문서 목록을 가져오는 기본 사용 방식 |

‘요즘 AI는 PDF나 이미지도 읽는데, 문서 로딩을 왜 따로 배우나?’라는 의문이 들었다. 교안의 ‘모델이 파일을 직접 읽을 수 없다’는 설명은 모든 최신 AI 서비스에 그대로 적용할 수 있는 표현은 아니다. 파일 입력 기능을 제공하는 서비스도 있고, 내부에서 전처리와 도구를 사용하기도 한다.

직접 파이프라인을 만들 때 로더를 배우는 이유는 어떤 텍스트가 추출됐는지, 페이지와 표가 어떻게 처리됐는지, 검색용 데이터로 무엇을 넘길지 확인하기 위해서다. `WebBaseLoader`는 그 일을 하는 도구 중 하나이며, 모든 AI의 인터넷 읽기가 이 클래스로 구현된다는 뜻은 아니다. 스캔 PDF·복잡한 표·동적 웹페이지는 단순 텍스트 추출만으로 충분하지 않을 수 있다.

### 7) 앞선 대화에서 이어진 LLM과 체인 복습

파인튜닝은 추가 학습으로 모델의 가중치를 조정하는 과정이다. 대화 중 내 말투와 앞선 내용을 참고해 답하는 것은 현재 제공된 문맥을 활용하는 것이며, 대화할 때마다 즉석에서 파인튜닝하는 것과는 다르다. 별도 메모리를 저장해 다음 대화에 제공하는 기능도 모델 가중치 학습과 구분한다.

RAG 역시 지식을 모델 가중치에 주입하는 학습이 아니다. 질문할 때 필요한 외부 자료를 검색해서 입력 문맥으로 제공한다. 긴 대화가 압축되면 이전 세부 내용이 빠질 수 있으므로, AI가 모든 과거 대화를 항상 전부 보고 있다고 생각하면 안 된다.

```text
prompt | model | parser
   ↓       ↓       ↓
메시지 조립 → 모델 호출 → 응답에서 문자열 추출
```

- `|`는 이 체인에서 ‘또는’이 아니라 앞 단계의 출력을 다음 단계로 전달하는 연결이다.
- `StrOutputParser()`는 응답에서 문자열을 추출하는 도구다. 정답 여부를 검사하거나 문체를 보장하는 도구는 아니다.
- `{question}`은 값을 넣을 자리이고, `invoke({"question": question_text})`의 키와 일치해야 한다. `sentence` 같은 다른 이름을 써도 양쪽을 맞추면 된다.
- `invoke`는 호출한다는 뜻이다. LangChain에서는 해당 구성 요소나 체인에 입력을 전달해 실행하는 메서드다.
- system 지시가 모호하면 원하는 형식에서 벗어날 수 있다. 역할뿐 아니라 포함할 내용과 제외할 내용을 구체적으로 정하는 것이 도움이 된다.

`temperature`와 `reasoning_effort`도 다른 설정이다. 전자는 토큰 선택의 무작위성과 관련되고, 후자는 모델이 추론에 쓰는 노력 수준을 조절한다. 낮은 temperature가 사실 정확성을 보장하지 않으며, 높은 추론 강도도 항상 더 좋은 답을 보장하지는 않는다. 모델에 따라 지원하는 값과 두 설정의 조합이 다르므로 수업 코드의 옵션을 다른 모델에 그대로 복사하면 오류가 날 수 있다.

모델 이름과 추론 강도를 같은 성능 순서로 생각하지 않는다. 모델 비교에서는 같은 문제·입력·도구 조건으로 답의 정확성, 시간, 사용량을 따로 확인해야 한다. 입력에는 질문 외의 지침과 문맥도 포함될 수 있고, 눈에 보이는 답변 길이와 보고되는 출력 사용량이 항상 같은 것은 아니다. 토큰 수와 실제 비용도 구분해서 비교한다.

## 4. 실수 및 트러블슈팅

### 1) 키를 바꿨는데 Missing credentials가 계속 발생

- 상황: 내 API 키를 등록했지만 모델·임베딩 생성에서 인증 정보가 없다는 오류가 났다.
- 원인: 코드가 기대하는 환경 변수 이름과 설정을 맞춰야 했고, 실행 중인 노트북 환경에도 새 설정을 다시 로드해야 했다.
- 해결: `OPENAI_API_KEY`로 이름을 맞추고, 현재 작업 위치에서 `.env`를 찾아 다시 읽도록 정리했다.

```python
from dotenv import find_dotenv, load_dotenv

load_dotenv(find_dotenv(usecwd=True), override=True)
```

실행 중인 환경 변수나 이미 생성한 모델 객체에 이전 값이 남을 수 있으므로 로딩 셀과 객체 생성 셀부터 다시 실행한다. `override=True`는 기존 환경 값을 덮어쓰므로 어떤 `.env`를 찾았는지도 중요하다. 키 값은 TIL에 기록하지 않는다.

뒤이어 나온 `vector_store is not defined`는 앞선 인증 오류 때문에 저장소 생성이 끝나지 않아 생긴 후속 오류였다. 마지막 셀의 오류만 따로 보기보다 처음 실패한 셀부터 확인해야 했다.

### 4) 실행됐는데 주말 이용 여부에 모르겠다고 답함

실습실 규정 전체에는 ‘주말은 미개방’이라고 적혀 있었지만, 체인에 넘긴 값은 `r_doc = docs[1]`이었다. Python 인덱스는 0부터 시작하므로 두 번째 청크이며, 이 청크에는 평일 개방 시간만 있었다. 주말 규정은 `docs[2]`에 있었다.

```text
질문: 실습실은 주말에 이용할 수 있나요?
전달한 근거: 평일 오전 9시부터 오후 10시까지 개방
실제 출력: 잘 모르겠습니다. [출처: 컴퓨터공학과(cs_lab_policy.pdf)]
```

이 경우 모델이 근거에 없는 내용을 추측하지 않은 것은 지시와 맞는다. 다만 질문에 답할 근거를 전달하는 과정은 개선해야 한다. 현재 예제는 청크를 직접 골랐으므로, 이후에는 질문과 관련된 청크를 검색해서 넘기는 흐름으로 연결할 필요가 있다.

코드가 실행됐다는 것, 출처가 출력됐다는 것, 질문에 맞는 근거를 전달했다는 것은 각각 따로 확인해야 한다.

### 5) 긴 문서 청킹 예제에 남아 있는 변수 이름 불일치

긴 원문을 분할하는 추가 셀에는 결과를 `chunk`에 저장하고 반복문에서는 `chunks`를 사용하는 부분이 남아 있었다. 해당 셀에는 저장된 실행 결과가 없으므로 완료한 실습으로 보지 않는다. 다음에 이어 할 때 결과 목록의 이름을 일치시키고 출력할 청크 변수와도 구분해야 한다.

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 인덱싱 안에 수집·청킹·임베딩·저장이 들어간다. 검색은 관련 근거를 고르고 생성은 그 근거로 답을 만든다.
- ⭐️ 반드시 기억할 내용: 1,536은 좌표 개수다. 숫자 범위나 벡터 개수와 혼동하지 않는다.
- 💡 참고로 알아둘 내용: 메타데이터는 출처 표시 외에 필터링과 문서 관리에도 쓰이며, 로더는 여러 파일 형식을 공통 처리 구조로 연결한다.
- ⚠️ 헷갈리기 쉬운 주의점: 코사인은 클수록, 거리는 작을수록 가깝다. ANN은 별도 거리 공식이 아니다.
- ⚠️ 헷갈리기 쉬운 주의점: 모델 성능이 좋아도 전달한 청크에 정답이 없으면 제대로 답하기 어렵다.
- 한 문장 요약: RAG는 좋은 모델을 고르는 것만으로 끝나지 않고, 문서를 읽고 나누고 필요한 근거를 골라 전달하는 과정까지 설계하는 작업이다.

## 6. 느낀 점과 다음 학습
