## 2. 개념과 용어 정리

### 1) 팀 전체 테스트 통과와 내 기능 검증은 다르다

운영자 API와 예약 상세 코드는 다른 담당의 인증·예약·슬롯·식당 객체를 함께 사용한다. 팀의 기존 테스트가 통과하더라도 내 서비스의 권한 분기를 실제로 호출하지 않으면, 남의 식당이나 예약을 잘 막는지는 알 수 없다.

이번에는 담당 기능을 검사하는 테스트 10개를 추가했다. 운영자 서비스 4개, 예약 상세 서비스 4개, 운영자 라우터 2개로 나눴다.

| 확인 단계 | 확인하는 것 | 아직 확인하지 않는 것 |
| --- | --- | --- |
| 서비스 + 가짜 저장소 | 식당 소유 여부, 예약 조회 허용 여부, 예외 종류 | 실제 JOIN·SQL·DB 데이터 |
| 라우터 + 가짜 로그인·서비스 | 역할 의존성, HTTP 상태, 응답 헤더·본문 | 실제 JWT 발급·검증·회원 조회 |
| 실제 앱 + DB | 인증·SQL·응답이 이어지는 전체 흐름 | 이번 테스트만으로는 증명하지 못함 |

테스트 범위를 좁히는 이유는 기능을 가짜로 완성하려는 것이 아니라, 먼저 확인할 책임을 분리하기 위해서다.

### 2) 가짜 저장소 — 데이터를 꺼내는 부분만 바꾸기

서비스가 DB에서 읽는 결과를 정해진 객체로 돌려주게 만들면 DB 없이도 권한 조건을 검사할 수 있다.

```python
class FakeOwnerQueryRepository:
    async def get_restaurant(self, restaurant_id):
        if restaurant_id == RESTAURANT.id:
            return RESTAURANT  # 주인이 정해진 식당
        return None            # 나머지는 없는 식당

    async def list_reservations(self, restaurant_id, day, offset, limit):
        return [], 0           # 빈 목록과 전체 개수
```

```python
service = OwnerService(db=None)
service.query = FakeOwnerQueryRepository()  # 판단 로직은 실제 서비스 그대로
```

`db=None`만 넣으면 모든 서비스가 자동으로 DB 없이 동작하는 것은 아니다. 이 테스트는 DB를 직접 쓰는 `query`를 가짜로 바꾸고, 해당 서비스 경로가 그 저장소를 통해서만 조회하는 구조를 이용한다.

### 3) 운영자 식당과 예약 상세의 403·404 구분

| 기능 | 요청자·대상 | 기대하는 판단 |
| --- | --- | --- |
| 운영자 식당 예약 목록 | 자기 식당 | 조회 허용 |
| 운영자 식당 예약 목록 | 다른 운영자의 식당 | `ForbiddenError`, 403 |
| 운영자 식당 예약 목록 | 없는 식당 | `NotFoundError`, 404 |
| 운영자 CSV | 다른 운영자의 식당 | `ForbiddenError`, 403 |
| 예약 상세 | 예약한 본인 또는 해당 식당 운영자 | 조회 허용 |
| 예약 상세 | 관계없는 사람 | `NotFoundError`, 404 |
| 예약 상세 | 없는 예약 | `NotFoundError`, 404 |

예약 상세에서는 관계없는 사람에게 존재 여부까지 숨기기 위해 없는 예약과 같은 404를 사용한다. 반면 운영자 식당 API는 존재하는 남의 식당과 없는 식당을 구분한다. 어떤 기능을 검사하느냐에 따라 기대할 예외도 달라진다.

```python
with pytest.raises(ForbiddenError):  # 이 경우는 반드시 권한 오류
    await service.list_restaurant_reservations(
        OWNER_B, RESTAURANT.id, None, PageParams(page=1, page_size=40)
    )
```

예외 하나만 기대하는 테스트로 나누면 잘못된 403·404 교체를 놓치지 않기 쉽다. 성공 테스트도 함께 있어야 모두 거절하는 잘못된 구현을 걸러낼 수 있다.

### 4) 번호와 사용자 객체를 구분하기

예약 데이터의 `user_id`에는 사용자 번호를 넣지만, 서비스가 요청자를 판단하는 인자에는 `AuthenticatedUser` 객체를 넘긴다.

| 위치 | 넘기는 값 | 이유 |
| --- | --- | --- |
| `Reservation.user_id` | `ME.user_id` | 누가 예약했는지 식별 |
| 식당의 `owner_id` | 운영자 UUID | 어느 사용자가 주인인지 식별 |
| `service.get_reservation(me, id)` | `ME` 객체 | 요청자의 식별자와 역할을 서비스가 사용 |
| 가짜 조회 반환값 | `(reservation, slot, owner_id)` | 실제 저장소의 반환 모양과 일치시킴 |

`return None,`처럼 끝에 쉼표가 붙으면 None 자체가 아니라 원소 하나인 튜플이 된다. 서비스의 `is None` 검사가 기대대로 동작하려면 가짜 저장소도 실제 계약을 지켜야 한다.

### 5) 라우터 테스트 — 로그인만 바꾸고 역할 검사는 남기기

```python
app = FastAPI()
register_error_handlers(app)
app.include_router(router, prefix="/api/v1")
app.dependency_overrides[get_authenticated_user] = fake_login_customer
app.dependency_overrides[create_owner_service] = FakeOwnerService
```

가짜 로그인은 손님 또는 운영자 객체를 반환한다. 그 뒤의 `require_owner`는 실제 코드를 사용한다. 그래서 손님을 반환한 경우 운영자 API가 403으로 거절하는지 확인할 수 있다.

```python
async with httpx.AsyncClient(
    transport=httpx.ASGITransport(app=app), base_url="http://test"
) as client:
    response = await client.get("/api/v1/owner/restaurants")
assert response.status_code == 403
assert response.json()["success"] is False
```

`ASGITransport`는 네트워크 서버를 별도로 띄우지 않고 앱을 호출한다. HTTP 응답 형식은 확인하지만 실제 배포·브라우저·DB 환경을 그대로 검증하는 것은 아니다.

### 6) CSV는 상태 코드와 파일 규격을 함께 확인하기

| 확인 항목 | 기대값 | 의미 |
| --- | --- | --- |
| 상태 코드 | 200 | 파일 응답 성공 |
| `Content-Type` | `text/csv`로 시작 | CSV 형식 |
| `Content-Disposition` | `reservations_1.csv` 포함 | 내려받을 파일명 |
| 본문 | `예약번호` 머리 줄 포함 | 생성한 CSV 내용 확인 |

CSV 코드는 `StringIO`와 `csv.writer`로 한 줄씩 만들고 `StreamingResponse`로 보낸다. 맨 앞에는 엑셀의 한글 인식을 위한 BOM을 한 번 넣고, 예약 시각은 서울 시각으로 바꿔 출력한다.

```python
yield "\ufeff"  # BOM은 파일 맨 앞에 한 번
writer.writerow(["예약번호", "시작", "끝", "인원", "상태", "연락처"])
yield buffer.getvalue()
buffer.seek(0)
buffer.truncate(0)  # 다음 줄을 만들기 전에 비움
```

파일 문자열을 한 번에 만들지 않는 것과 DB 조회까지 스트리밍하는 것은 다르다. 이 구현의 서비스는 예약 목록을 먼저 가져오므로 DB에서 모든 결과를 메모리로 읽는 비용까지 없어진 것은 아니다.

## 4. 실수 및 트러블슈팅

### 발생한 문제 요약

- 상황: 로그인과 DB가 연결되기 전이라 담당 API를 실제 계정으로 확인하기 어려웠음
- 원인: 기존 팀 테스트가 내 서비스의 403·404 분기를 직접 검사하지 않았음
- 해결: 조회 저장소와 로그인 의존성만 가짜로 교체하고, 서비스·권한 문지기의 실제 판단을 검사하는 테스트 추가
- 해결 결과: 당시 전체 81개 통과 기록 확인. SQL·시간대·실제 인증은 별도 통합 확인이 필요함

### 테스트 작성 시 주의할 부분

| 문제 | 원인 | 확인할 것 |
| --- | --- | --- |
| 본인인데도 거절됨 | ID 자리와 사용자 객체 자리를 혼동 | 테스트 데이터의 ID와 서비스 인자 비교 |
| 없는 예약 분기가 실행 안 됨 | `None` 대신 `(None,)` 반환 | 가짜 저장소의 반환값 확인 |
| CSV 테스트가 권한을 검증한 것처럼 보임 | 서비스까지 가짜로 교체됨 | CSV 형식 검사와 실제 소유 검사 테스트를 구분 |
| 테스트 통과를 실제 DB 성공으로 해석 | 가짜 저장소가 SQL을 실행하지 않음 | 다음 단계에서 실제 JOIN·인증·시간대 확인 |
