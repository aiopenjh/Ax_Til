## 2. 반드시 이해할 핵심

### 요청에서 응답까지

**요청 → 라우팅 → 입력 검증 → 업무 처리·저장 → 응답** 순서로 본다.
FastAPI는 API를 만드는 프레임워크이고, Uvicorn은 요청을 받아 앱을 실행하는 서버다.
라우팅은 메서드와 경로에 맞는 함수를 찾는 것이다. 예: `@app.get("/books/{book_id}")`.

AI에게는 **메서드·경로·입력 위치와 형식·성공 및 실패 응답**을 함께 요구한다.
예: “POST /books로 제목과 가격을 JSON으로 받아 저장하고, 성공하면 201과 생성된 ID를 반환해 줘.”

### 주소와 HTTP 메서드

`localhost`는 자기 PC를 가리키는 이름이고, `127.0.0.1`은 IPv4에서 자기 PC를 가리키는 주소다.
`http://127.0.0.1:8000/books/1`에서 `8000`은 포트, `/books/1`은 리소스 경로다.
URI는 리소스의 식별자, URL은 위치와 접근 방법을 나타내는 URI다.
REST는 리소스와 일관된 인터페이스 등을 중심으로 설계하는 방식이다. 우선 “도서라는 대상 + 메서드”로 이해한다.

| 메서드 | 도서 API 예시 | 하는 일 |
| --- | --- | --- |
| GET | `/books/1` | 조회 |
| POST | `/books` | 생성 |
| PUT | `/books/1` | 전체 교체 |
| PATCH | `/books/1` | 일부 변경 |
| DELETE | `/books/1` | 삭제 |

조회 요청으로 데이터를 바꾸지 않는다. GET의 검색 조건은 보통 쿼리로 보낸다.
같은 요청을 반복해도 의도한 효과가 같으면 **멱등**이다. 응답까지 같아야 한다는 뜻은 아니며, PATCH는 설계에 따라 달라진다.

### Path·Query·Body와 Content-Type

도서 수정 예시: `PATCH /books/1?notify=true`, JSON 본문 `{"price":12000}`.

- **Path:** `1`처럼 “어떤 도서인지” 지정한다.
- **Query:** `notify=true`처럼 조건이나 옵션을 전달한다.
- **Body:** `{"price":12000}`처럼 생성·변경할 데이터를 전달한다.
- **Content-Type:** 본문 형식을 알리는 헤더다. JSON은 `application/json`, 일반 폼은 `application/x-www-form-urlencoded`다.

`Form`도 본문을 보내는 방식이다. AI 코드의 `Path/Query/Body/Form`·모델 선언과 실제 요청 위치·형식이 맞는지 본다.

### 응답은 상태 코드까지 확인

- `200`: 성공 / `201`: 생성 성공 / `204`: 성공, 응답 본문 없음
- `404`: 대상 없음 / `422`: FastAPI 기본 입력 검증 실패 / `500`: 처리하지 못한 서버 오류

실패했는데 `200`과 오류 문장만 주면 성공으로 오해할 수 있다. 상태 코드와 응답 본문을 함께 확인한다.

### 비동기는 기다리는 시간을 활용하는 것

**I/O-bound**는 입출력 대기 시간이 큰 작업, **CPU-bound**는 계산 시간이 큰 작업이다. DB·외부 API 호출은 전자, 이미지 변환 같은 큰 계산은 후자의 예다.
비동기 I/O를 `await`하며 대기할 때 다른 요청을 처리할 수 있다. `async`를 붙여도 CPU 계산이 자동으로 빨라지지는 않는다.
`async def` 안의 동기 I/O·`time.sleep()`·긴 계산은 이벤트 루프를 막을 수 있으므로, 사용 라이브러리와 호출 방식을 확인한다.
FastAPI의 일반 `def` 엔드포인트는 별도 스레드풀에서 처리한다. 직접 호출한 보조 함수까지 자동으로 옮겨 주지는 않는다.

### 도메인·검증·저장은 역할이 다르다

- **도메인:** 도서·대출 같은 업무 대상과 “대출 중이면 다시 빌릴 수 없다” 같은 규칙. 이를 코드로 표현한 것이 도메인 모델이다.
- **입력 검증:** Pydantic 모델 등으로 필수값·타입·범위를 확인하는 것. `price: int`만으로 음수까지 막지는 않는다.
- **저장:** 데이터를 보관하는 것. `in_memory_db` 같은 메모리 딕셔너리는 재시작하면 초기화되고 여러 프로세스에 자동 공유되지 않는다.

“저장 완료”라는 설명만 믿지 않고 **저장 위치와 재시작 후 유지 여부**를 확인한다. 영구 저장이 필요하면 DB 등 저장소를 요구한다.
`None` 허용과 필드 생략 가능 여부는 다르다. 기본값·검증 조건·예외 처리의 세부 구현은 후속 학습으로 둔다.

### 로그로 실패한 지점 찾기

로그는 어떤 요청이 어디서 실패했는지 찾는 기록이다.
`DEBUG` 상세 진단 / `INFO` 정상 흐름 / `WARNING` 주의 징후 / `ERROR` 작업 실패 / `CRITICAL` 심각한 장애.
포맷·출력 위치·레벨 설정은 한곳에서 관리하고, 각 모듈은 `logging.getLogger(__name__)`로 기록할 수 있다.
오류가 나면 요청·상태 코드·관련 로그를 같이 본다. 비밀번호·토큰·민감한 본문은 무작정 로그에 남기지 않는다.
