## 2. 개념과 용어 정리

### 1) FastAPI와 요청 처리 흐름

- FastAPI: 파이썬으로 API를 만드는 웹 프레임워크. 요청을 어떤 함수에 연결할지 정하고, 입력값을 검사하고, 처리 결과를 응답으로 돌려주는 틀이다.
- Uvicorn: 네트워크로 들어온 요청을 받아 FastAPI 앱을 실행하는 ASGI 서버. FastAPI가 요청 처리 규칙을 가진 주방이라면, Uvicorn은 외부 주문을 주방으로 전달하는 역할로 생각하면 된다.
- 라우팅(Routing): 요청의 HTTP 메서드 + 경로에 맞는 처리 함수를 찾는 것. `GET /books/1`과 `DELETE /books/1`은 주소가 같아도 하는 일이 다르다.

요청 흐름: 클라이언트 요청 → 라우팅 → 입력 검증 → 업무 처리·저장소 접근 → 응답

예를 들어 “1번 책을 보여 줘”라는 요청이 오면, 경로의 `1`이 올바른 번호인지 확인하고 해당 책을 찾아 응답한다. 번호가 잘못됐는지, 책이 없는지, 서버가 고장 났는지는 서로 다른 실패이므로 구분해야 한다.

### 2) 비동기 서버의 작동 원리 — 기다리는 시간을 활용하기

동기 처리에서는 작업이 끝나야 다음 단계로 넘어간다. 이때 DB 응답이나 외부 API를 기다리며 실행 흐름이 멈추면, 기다리는 동안 해당 일꾼도 다른 일을 하기 어렵다.
비동기 처리는 기다릴 수 있는 지점에서 다른 작업으로 실행 기회를 넘겨 대기 시간을 활용한다. 여러 작업을 번갈아 진행하는 동시성과, 여러 계산을 실제로 동시에 실행하는 병렬성은 구분해야 한다.

| 구분      | 뜻                                                    | 기억할 점 / 예시                                                                                           |
| --------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| WSGI      | 웹 서버와 파이썬 앱을 연결하는 동기식 인터페이스 규약 | 규약 자체가 ‘요청 1개 = 스레드 1개’를 강제하지는 않음. 프로세스·스레드 운용은 서버 구현과 설정에 따라 다름 |
| ASGI      | 비동기 처리를 지원하는 서버·앱 연결 규약              | FastAPI와 Uvicorn이 사용하는 규약. ASGI를 쓴다고 모든 코드가 자동으로 비동기 처리되는 것은 아님            |
| I/O-bound | 계산보다 입출력을 기다리는 시간이 큰 작업             | DB 조회, 외부 API 응답 대기. 비동기 I/O로 대기 시간을 활용할 수 있음                                       |
| CPU-bound | CPU가 실제로 계산하는 시간이 큰 작업                  | 큰 이미지 변환, 복잡한 수치 계산. `async`만 붙여도 계산이 빨라지는 것은 아님                               |

주방 비유로 이해하기

- 스레드: 레시피를 따라 실제로 일하는 요리사.
- 함수: 해야 할 순서를 적은 레시피. 호출 스택은 함수 호출과 중간 작업 정보를 쌓아 두는 작업대에 비유할 수 있다.
- 이벤트 루프: 진행 가능한 작업을 번갈아 실행하도록 조율하는 담당자.
- `await`: 비동기 I/O를 기다려야 할 때 “응답이 오면 이어서 하겠다”며 다른 작업에 실행 기회를 넘길 수 있는 지점.

요리사가 배달 재료를 기다리는 동안 다른 주문의 채소를 다듬는 것과 비슷하다. 다만 칼질 자체가 오래 걸리는 상황(CPU 계산)에서는 기다릴 틈이 없으므로, `async`라는 이름표만 붙여 해결할 수 없다.

`async def`와 `def`를 구분할 때

- `async def` 안에서는 비동기를 지원하는 라이브러리와 `await`를 함께 사용해야 대기를 활용할 수 있다. `time.sleep()`이나 동기 HTTP 호출을 그대로 넣으면 이벤트 루프를 막을 수 있다.
- FastAPI가 호출하는 일반 `def` 엔드포인트는 별도 스레드풀에서 실행된다. 동기 I/O를 처리할 때 활용할 수 있지만 스레드 자원도 무한하지는 않다.
- `async def` 안에서 내가 직접 호출한 일반 보조 함수까지 자동으로 스레드풀로 옮겨 주지는 않는다. 함수 선언뿐 아니라 그 안에서 무엇을 호출하는지 확인할 것.

### 3) HTTP 메서드와 주소 — 어떤 대상에 무엇을 할 것인가?

`http://127.0.0.1:8000/books/1?include_author=false`를 나누어 보면 다음과 같다.

| 주소 구성               | 뜻                                     | 기억할 점                                                                              |
| ----------------------- | -------------------------------------- | -------------------------------------------------------------------------------------- |
| `http://`               | 통신에 사용할 방식                     | 실제 서비스에서는 보통 HTTPS로 통신을 암호화함                                         |
| `127.0.0.1`             | IPv4에서 자기 컴퓨터를 가리키는 주소   | `localhost`도 자기 컴퓨터를 가리키는 이름. 다른 사람 PC에서 접속하면 그 사람 PC를 뜻함 |
| `8000`                  | 서버 프로그램이 요청을 받는 포트       | 같은 컴퓨터에서도 포트가 다르면 다른 프로그램에 연결될 수 있음                         |
| `/books/1`              | 도서 중 1번이라는 대상을 지정하는 경로 | `1`은 경로 매개변수(Path Parameter)                                                    |
| `?include_author=false` | 응답에 저자를 포함할지 지정하는 조건   | 쿼리 문자열(Query String). 여러 조건은 `&`로 연결                                      |

URI는 리소스를 식별하는 이름이고, URL은 위치와 접근 방법까지 나타내는 URI다. REST는 리소스와 일관된 인터페이스 등을 중심으로 설계하는 방식이다. 우선 주소로 ‘도서’라는 대상을 나타내고, 메서드로 ‘조회·생성·변경·삭제’를 표현하는 원리부터 익힌다.

| HTTP 메서드 | 도서 API 예시 | CRUD에서 하는 일  | 반복 요청 시 기억할 점                                                          |
| ----------- | ------------- | ----------------- | ------------------------------------------------------------------------------- |
| GET         | `/books/1`    | 조회(Read)        | 조회가 목적인 안전한 메서드. 요청 때문에 도서가 변경되거나 삭제되면 안 됨       |
| POST        | `/books`      | 생성(Create)      | 생성 요청을 반복하면 책이 여러 개 생길 수 있음. 기본적으로 멱등을 보장하지 않음 |
| PUT         | `/books/1`    | 전체 교체(Update) | 대상의 전체 표현을 새 값으로 교체. 같은 내용을 반복해도 의도한 효과가 같아야 함 |
| PATCH       | `/books/1`    | 일부 변경(Update) | ‘가격을 12000원으로 설정’과 ‘가격에 1000원 더하기’는 반복했을 때 효과가 다름    |
| DELETE      | `/books/1`    | 삭제(Delete)      | 반복해도 해당 책이 없는 상태라는 의도한 효과는 같음                             |

멱등성(Idempotency): 같은 요청을 한 번 보내든 여러 번 보내든 서버에 의도한 효과가 같은 성질. 엘리베이터 호출 버튼을 여러 번 눌러도 같은 층을 호출하는 것에 비유할 수 있다.

예를 들어 첫 `DELETE /books/1`은 `204`, 다시 삭제하면 `404`를 돌려줄 수 있다. 응답은 달라도 책이 없는 상태는 같으므로 멱등성에 어긋나지 않는다. GET도 다른 사람이 데이터를 수정하면 조회 결과가 바뀔 수 있다. 멱등은 응답 내용이 영원히 같다는 뜻이 아니다. PATCH도 값을 특정 상태로 설정하는 방식이면 멱등하게 설계할 수 있다.

### 4) Path·Query·Body·Form과 Content-Type

요청은 ‘해야 할 일’, ‘대상’, ‘전달할 데이터’를 구분해서 읽는다. 예를 들어 `PATCH /books/1?notify=true`에 `{"price":12000}`을 보내면, 1번 책의 가격을 바꾸면서 알림 옵션도 전달하는 것이다.

| 구분         | 전달하는 내용                    | 예시 / 주의점                                                                            |
| ------------ | -------------------------------- | ---------------------------------------------------------------------------------------- |
| 메서드       | 어떤 일을 할 것인지              | `PATCH`는 메서드이며 헤더가 아님                                                         |
| Path         | 어떤 대상인지                    | `/books/1`의 `1`                                                                         |
| Query        | 검색·정렬·옵션 같은 조건         | `?q=python&sort=desc`. GET 전용이 아니며 POST·PATCH에도 붙일 수 있음                     |
| Body         | 요청 본문에 담는 데이터          | `{"price":12000}`. POST 전용이 아니며 PUT·PATCH에도 사용                                 |
| Form         | 폼 형식으로 인코딩한 본문 데이터 | 일반 폼은 `application/x-www-form-urlencoded`, 파일 첨부 폼은 `multipart/form-data` 사용 |
| Content-Type | 보내는 본문의 형식을 알리는 헤더 | JSON이면 `application/json`. 실제 내용도 선언한 형식과 맞아야 함                         |

JSON 본문을 요구하는 API에 폼 데이터를 보내거나, Query로 받는 값을 Body에 넣으면 의도대로 전달되지 않을 수 있다. FastAPI 코드의 `Query`, `Body`, `Form`, 모델 선언과 실제 요청 위치·형식을 함께 확인한다. GET 검색 조건은 보통 Query로 보내며, GET 본문은 도구·서버 간 호환 문제가 있어 피한다.

`Optional`과 기본값의 차이: `Optional[str]` 또는 `str | None`은 문자열 외에 `None`도 허용한다는 타입 표현이다. 생략 가능 여부는 기본값과 별개로 확인해야 한다. 예를 들어 `q: str | None = None`은 타입에서 `None`을 허용하고, 기본값도 `None`으로 주어 쿼리 생략 시 사용할 값을 정한 것이다. Pydantic 모델에서도 `str | None`만 적고 기본값을 주지 않으면 필수 필드일 수 있다.

### 5) 도메인·입력 검증·저장소 구분하기

- 도메인(Domain): 서비스가 해결하려는 업무 영역. 도서 대여 서비스라면 도서·회원·대출과 “대출 중인 책은 다시 빌릴 수 없다” 같은 규칙이 해당한다. 인터넷 주소의 도메인 이름과는 다른 뜻이다.
- 도메인 모델: 업무 데이터와 규칙을 코드로 표현한 것. `Book` 객체가 제목·대여 상태를 갖고, 허용되지 않은 상태 변경을 막는 방식으로 구성할 수 있다.
- 입력 검증: 요청의 필수값·타입·범위를 먼저 확인하는 것. `price: int`는 정수 타입 조건이지 양수 조건까지 뜻하지는 않는다. 가격이 양수여야 한다면 별도 범위 조건도 필요하다.
- 저장소: 데이터를 실제로 보관하는 곳. `in_memory_db` 같은 딕셔너리는 실행 중인 프로세스 메모리에 있을 뿐이다. 서버를 재시작하면 초기화되고, 여러 프로세스가 자동으로 같은 내용을 공유하지도 않는다.

Pydantic으로 요청 모양을 검사했다고 대출 규칙이나 영구 저장까지 해결된 것은 아니다. AI가 “저장 완료”라고 설명해도 저장 위치와 재시작 후 유지 여부를 확인해야 한다. 영구 저장이 필요하면 DB 등 지속되는 저장소를 요구한다.

### 6) 로깅 — 실패한 지점을 찾는 블랙박스

로그는 프로그램이 어떤 순서로 움직였고 어디에서 실패했는지 남기는 기록이다. 단순 `print()`와 달리 시간·레벨·모듈 이름을 붙이고, 필요한 중요도만 골라 출력할 수 있다.

설정을 한곳에 모으는 이유: 파일마다 출력 형식과 저장 위치를 따로 정하면 나중에 한 흐름으로 추적하기 어렵다. 포맷·출력 대상·레벨은 중앙에서 관리하고, 각 모듈은 `logging.getLogger(__name__)`로 자기 이름의 로거를 가져와 기록한다. 중앙 설정과 모듈별 로거는 함께 쓰는 방식이다.

| 로그 레벨 | 뜻                                 | 적용 예시                                                 |
| --------- | ---------------------------------- | --------------------------------------------------------- |
| DEBUG     | 개발 중 자세한 흐름 확인           | 분기 처리나 계산 단계 확인. 운영에서는 보통 출력량을 제한 |
| INFO      | 정상적인 처리 흐름                 | 요청 처리 시작·완료, 서버 시작                            |
| WARNING   | 주의할 상황이지만 전체 장애는 아님 | 없는 도서 ID 요청, 예상한 외부 연동 재시도                |
| ERROR     | 특정 작업을 처리하지 못함          | DB 저장 실패, 외부 API 시간 초과                          |
| CRITICAL  | 서비스 운영을 위협하는 심각한 장애 | 핵심 기반 시스템 장애로 서비스 지속이 어려운 상황         |

`INFO`를 출력 기준으로 설정하면 보통 `INFO` 이상이 기록되고 `DEBUG`는 제외된다. 개발·운영 환경에 맞게 기준을 바꾸고, FastAPI 앱 로그와 Uvicorn 로그도 함께 추적할 수 있도록 설정을 맞춘다. 비밀번호·토큰·민감한 요청 본문을 그대로 남기지는 않는다.

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/문법                      | 뜻                               | 기억할 점 / 주의점                                                    |
| ------------------------------ | -------------------------------- | --------------------------------------------------------------------- |
| `@app.get("/books/{book_id}")` | 메서드와 경로를 처리 함수에 연결 | 같은 경로도 메서드가 다르면 다른 작업                                 |
| `async def` / `await`          | 비동기 함수 / 비동기 작업 대기   | 동기 I/O나 긴 계산을 자동으로 빠르게 바꾸지 않음                      |
| Path / Query / Body            | 대상 / 조건 / 본문 데이터        | 이름만 보지 말고 실제 요청 위치와 맞는지 확인                         |
| `HTTPException`                | 실패 상태 코드와 설명을 전달     | 없는 대상은 `404` 등으로 구분. 오류 문장만 주고 `200`으로 숨기지 않기 |
| 멱등성                         | 반복해도 의도한 효과가 같은 성질 | 상태 코드나 응답 본문이 항상 같아야 한다는 뜻은 아님                  |
| `logging.getLogger(__name__)`  | 모듈 이름의 로거 가져오기        | 설정은 한곳에서 관리하고 필요한 문맥을 기록                           |

| -------------------------------------- | ---------------------------------- | ---------------------------------------------------------- |
| `Query(...)`, `Body(...)`, `Form(...)` | 입력 위치와 조건을 명시하는 선언   | 필수 여부·기본값·별칭이 필요할 때 확인                     |
| Pydantic 모델 / `Field`                | 데이터 구조와 검증 조건 정의       | 타입 외에 범위·길이 조건도 따로 확인                       |
| 로깅의 `level` / `format` / `datefmt`  | 출력 기준 / 기록 모양 / 시간 형식  | 로그 설정을 분리할 때 찾아보기                             |
| `/docs` / Postman / curl               | 요청을 보내고 응답을 확인하는 도구 | FastAPI 기본 설정의 `/docs`에서 명세와 요청 형식 확인 가능 |

## 3. 예제 및 실습

### 실습 내용 — 도서 한 권 조회 흐름 읽기 (미실행)

전체 CRUD를 만들기 전에 Path로 책 선택 → Query로 응답 옵션 선택 → 없으면 404 → 있으면 JSON 응답을 한 예제에서 확인한다. 아래는 별도 `main.py`를 가정한 코드이며, 실제 소스 파일을 만들거나 서버를 실행하지는 않았다.

```python
import logging
from fastapi import FastAPI, HTTPException

# 작은 예제에서는 시작 지점에서 한 번 설정. 여러 모듈로 커지면 설정 분리
logging.basicConfig(level=logging.INFO, format="%(levelname)s [%(name)s] %(message)s")
logger = logging.getLogger(__name__)  # 기록을 남기는 모듈 이름
app = FastAPI()

# 프로세스 메모리의 예제 데이터. DB에 영구 저장한 것이 아님
books = {1: {"id": 1, "title": "파이썬 기초", "author": "홍길동"}}

@app.get("/books/{book_id}")
def get_book(book_id: int, include_author: bool = True):
    # book_id는 Path, include_author는 Query. 선언한 타입으로 검증됨
    book = books.get(book_id)
    if book is None:
        logger.warning("도서 조회 실패: book_id=%s", book_id)
        raise HTTPException(status_code=404, detail="도서를 찾을 수 없습니다.")

    result = book.copy()  # 응답을 다듬다가 원본에서 저자를 지우지 않도록 복사
    if not include_author:
        result.pop("author")
    logger.info("도서 조회 완료: book_id=%s", book_id)
    return result  # 딕셔너리를 FastAPI가 JSON 응답으로 변환
```

이 예제는 별도 입출력 대기가 없는 짧은 조회다. `def` 엔드포인트의 스레드풀 처리를 배우는 예시이며, 비동기 I/O나 도메인 규칙 구현을 보여 주는 코드는 아니다. 기본 로깅 설정만으로 Uvicorn의 모든 로그 형식까지 같아지는 것도 아니므로, 앱이 커지면 공통 설정 적용 범위를 확인한다.

### 요청과 예상 응답 (미실행)

서버가 `127.0.0.1:8000`에서 실행 중이라고 가정한다. Windows PowerShell에서는 `curl.exe`를 사용해 curl 프로그램을 명확히 호출할 수 있다.

```powershell
# -i: 응답 상태 코드와 헤더까지 확인. Query로 저자 제외 옵션 전달
curl.exe -i "http://127.0.0.1:8000/books/1?include_author=false"
```

예상 응답의 주요 부분:

```http
HTTP/1.1 200 OK
content-type: application/json

{"id":1,"title":"파이썬 기초"}
```

| 요청             | 예상 결과                                      | 확인하려는 차이                                                 |
| ---------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| `GET /books/1`   | `200`, 저자까지 포함                           | Query를 생략하면 기본값 `True` 적용                             |
| `GET /books/99`  | `404`, `{"detail":"도서를 찾을 수 없습니다."}` | 번호는 올바르지만 해당 데이터가 없음                            |
| `GET /books/abc` | `422`, 입력 검증 오류 내용                     | 정수로 선언한 Path에 문자를 보냄. 함수 본문 실행 전에 검증 실패 |

curl은 터미널에서 HTTP 요청을 보내는 도구다. `-X`는 메서드, `-H`는 헤더, `-d`는 본문 데이터를 지정한다. JSON 생성 요청이라면 `Content-Type: application/json`과 JSON 본문을 함께 보내야 한다. 위 조회 예제에는 생성 기능이 없으므로 `POST /books` 요청과 혼동하지 않기.

### 실행 결과

- 정상적으로 된 부분: 미실행 — 직접 실행 후 작성
- 새롭게 확인한 부분: 직접 작성
- 추가 확인: `422`는 함수 본문에 들어오기 전 발생하므로 위 함수의 실패 로그만으로는 잡히지 않는다. 기본 접근 로그의 상태 코드와 검증 응답을 함께 확인하고, 필요한 검증 실패 기록은 별도로 설계한다.

### AI 코드와 실습을 확인할 때 사용할 기준 (아직 미실행)

- [ ] 요청의 메서드·경로·입력 위치·Content-Type이 API 선언과 맞는가?
- [ ] 성공은 `200`, 생성은 `201`, 본문 없는 성공은 `204` 등 요구한 규약대로 응답하는가? `204`에 본문을 넣지 않았는가?
- [ ] 없는 대상 `404`, 입력 검증 실패 `422`, 처리하지 못한 서버 오류 `500`을 구분하는가? 실패를 `200`과 오류 문장으로 숨기지 않는가?
- [ ] `async def` 안에 동기 I/O·`time.sleep()`·긴 계산이 숨어 있지 않은가?
- [ ] 영구 저장을 요구했다면 재시작 후에도 데이터가 남는가? 메모리 딕셔너리를 DB처럼 설명하지 않는가?
- [ ] 실패한 요청을 상태 코드·검증 내용·로그로 추적할 수 있는가? 비밀값은 기록하지 않는가?

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 요청은 메서드 + 경로 + 입력 위치·형식으로 읽고, 응답은 상태 코드 + 본문을 함께 확인한다. AI에게도 이 조건과 실패했을 때의 동작을 구체적으로 요구할 것.
- 💡 참고로 알아둘 내용: 비동기는 I/O 대기 시간을 활용하는 방식이다. 도메인 규칙, 입력 검증, 영구 저장은 각각 무엇을 책임지는지 구분해서 본다.
- ⚠️ 헷갈리기 쉬운 주의점: `async`만 붙인다고 빨라지지 않고, 멱등이라고 응답까지 같아야 하는 것도 아니다. Query는 GET 전용, Body는 POST 전용이 아니다.
- 한 문장 요약: AI가 만든 API를 판단하려면, 무엇을 어디로 보내고 어떤 처리와 응답이 나와야 하는지 내가 먼저 설명할 수 있어야 한다.
