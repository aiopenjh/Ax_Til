## 2. 개념과 용어 정리

### 1) 전날 복습 — 응답 양식과 검증 결과를 실제로 사용하기

응답 모델은 외부로 내보낼 필드를 정하고, 반환값을 검증·필터링하는 기준이다. 내부 메모가 들어 있는 딕셔너리도 공개용 모델을 거쳐 응답하면 선언한 필드만 보낼 수 있다. 다만 직접 `JSONResponse`를 반환하는 경우에는 일반적인 응답 모델 처리를 거치지 않으므로 별도로 확인해야 한다.

- `model_validator(mode='before')`는 모델 생성 전의 원시 입력을, `after`는 기본 검증을 통과한 모델을 다룬다. `after` 검증 뒤에는 `self`를 반환한다.
- `exclude_unset=True`는 명시적으로 설정한 필드만 추린다. 생략한 필드와 명시한 `null`은 다르며, 병합 후 다시 검증했다면 정리된 검증 결과를 실제 처리에 사용한다.
- `Query(alias='status')`는 외부에서 사용하는 `status`라는 쿼리 이름과 내부 변수명을 연결한다.
- `TypeVar`는 바꿔 넣을 타입을 나타내고, `Generic[T]`는 그 타입을 받아 재사용하는 틀이다. `APIResponse[BookResponse]`와 `APIResponse[list[BookResponse]]`는 같은 봉투에 단건·목록을 각각 담는 방식이다.
- 다중 상속의 메서드 탐색은 MRO라는 순서를 따른다. 단순히 무조건 왼쪽 클래스만 본다고 외우기보다 `클래스.__mro__`로 실제 순서를 확인한다.

`/openapi.json`은 API 명세, `/docs`는 요청을 직접 보내 볼 수 있는 문서, `/redoc`은 읽기 중심 문서다. 문서가 만들어진 것과 실제 동작을 확인한 것은 구분한다.

### 2) Path와 Query — 어떤 대상인지, 어떤 조건인지 구분

주소를 식료품 장부에 비유하면 Path는 ‘몇 번 품목을 펼칠지’, Query는 ‘어떤 조건으로 몇 개씩 볼지’에 해당한다.

| 구분               | 위치와 역할                         | 예시 / 주의점                                                              |
| ------------------ | ----------------------------------- | -------------------------------------------------------------------------- |
| Path 매개변수      | URL 경로에 포함된 대상 식별값       | `/groceries/1`의 `1`. 해당 경로로 요청할 때 필수                           |
| Query 매개변수     | `?` 뒤의 검색·필터·정렬·페이지 조건 | `/groceries?category=과일&limit=10`. 기본값 없이 선언하면 필수일 수도 있음 |
| `alias`            | 외부 입력 이름과 내부 변수 연결     | 내부 변수 `q`에 `Query(alias='query')`를 쓰면 요청은 `?query=사과`         |
| `limit` / `offset` | 가져올 개수 / 건너뛸 개수           | `limit=10&offset=20`은 앞의 20개를 건너뛰고 최대 10개 조회                 |

‘식별은 Path, 조건은 Query’는 API를 읽기 쉽게 만드는 설계 관례다. Query로 ID를 받는 것이 HTTP 규약 위반이라는 뜻은 아니다. 중요한 것은 API의 목적과 입력 위치를 일관되게 정하는 것이다.

`category: str`처럼 기본값 없이 선언한 쿼리는 필수다. `category: str | None = None`이면 `None`을 허용하면서 생략 시 기본값도 정한 것이다. 쿼리는 항상 선택이라는 뜻으로 외우지 않기.

### 3) Path·Query 검증과 Annotated

`int`나 `str` 같은 타입만으로 부족하면 범위·길이 조건을 추가한다. 한 번에 수십만 개를 조회하지 못하도록 `limit`에 상한을 두거나, 음수 ID를 저장소에 조회하기 전에 막는 식이다.

| 조건                        | 뜻                            | 예시                                                      |
| --------------------------- | ----------------------------- | --------------------------------------------------------- |
| `gt` / `ge`                 | 초과 / 이상                   | `Path(gt=0)`은 0보다 큰 ID, `Query(ge=0)`은 0 이상 offset |
| `lt` / `le`                 | 미만 / 이하                   | `Query(le=50)`이면 최대 50까지                            |
| `min_length` / `max_length` | 문자열 등의 최소 / 최대 길이  | 검색어는 입력했다면 1~30글자 허용                         |
| `pattern`                   | 문자열이 맞아야 할 정규표현식 | 정해진 형식의 코드 등을 검사할 때 사용                    |
| `description`               | 자동 문서에 표시할 설명       | 값의 의미와 단위를 안내. 설명 자체가 검증 조건은 아님     |

`Annotated[타입, 추가 정보]`는 타입에 FastAPI의 입력 위치·검증 조건 같은 메타데이터를 붙이는 문법이다. 예를 들어 `item_id: Annotated[int, Path(gt=0)]`은 ‘정수인 경로값이며 0보다 커야 한다’를 함께 표현한다. 파이썬 자체가 Annotated의 내용을 모두 강제하는 것이 아니라 FastAPI가 이 정보를 읽어 검증한다.

기본값은 바깥의 `= None`, `= 10` 등으로 정한다. `Annotated`를 사용해도 파이썬의 일반적인 기본값 인자 순서 규칙이 없어지는 것은 아니다. 기본값 없는 인자들을 앞에 두는 등 문법에 맞게 선언해야 한다.

검증된 `limit`, `offset`으로 `results[offset:offset + limit]`처럼 목록의 일부를 꺼낼 수 있다. 이는 메모리 목록의 학습 예시이며, DB를 쓸 때 모든 행을 먼저 읽는 방식까지 그대로 따라야 한다는 뜻은 아니다.

### 4) 422와 404, HTTPException과 예외 핸들러

‘번호 형식이 틀렸다’와 ‘올바른 번호지만 장부에 없다’는 다른 문제다. 먼저 입력 조건을 검사하고, 통과한 값으로 조회한 뒤 대상 유무를 확인한다.

| 상황                                                 | 처리 방식                          | 상태 코드 / 기억할 점                                        |
| ---------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------ |
| 정수 ID에 문자 입력, 범위 위반, 필수 쿼리·폼 값 누락 | FastAPI의 요청 검증                | 기본 `422`. 처리 함수 본문에 들어오기 전에 실패할 수 있음    |
| 형식이 올바른 ID지만 데이터가 없음                   | `raise HTTPException(...)`         | 예: `404`. 조회 결과를 보고 코드에서 명시적으로 결정         |
| 유통기한 검사에서 만료 품목 발견                     | 업무용 커스텀 예외 → 등록한 핸들러 | 교재에서는 `400`으로 변환. 입력 양식 검증과 별도의 업무 판단 |
| 서버 반환값이 응답 모델에 맞지 않음                  | 응답 검증 실패                     | 서버 코드의 문제. 사용자 입력 오류와 구분                    |

`HTTPException`은 `return`이 아니라 `raise`로 발생시킨다. 현재 처리 흐름을 중단하고 상태 코드와 오류 정보를 응답하도록 전달하는 방식이며, 서버 전체를 종료하는 명령은 아니다.

- `status_code`: 실패 종류를 표현하는 상태 코드.
- `detail`: 클라이언트에 알려 줄 오류 내용.
- `headers`: 필요하면 `X-Error-Code` 같은 응답 헤더도 추가할 수 있음. 본문·헤더에 내부 비밀값을 노출하지 않기.

예외 핸들러는 여러 곳에서 발생한 특정 예외를 같은 응답 모양으로 바꾸는 공통 안내 창구다. 예를 들어 `GroceryExpiredException`을 만들고 `@app.exception_handler(GroceryExpiredException)`으로 처리 함수를 등록하면, 요청 처리 중 해당 예외가 전파됐을 때 정해 둔 응답으로 변환할 수 있다.

일반 `ValueError` 처리기 하나로 모든 오류가 해결되지는 않는다. FastAPI 요청 검증의 `RequestValidationError`, 직접 만든 모델의 `ValidationError`, 업무 예외는 발생 위치와 처리 경로가 다르다. 예상한 업무 실패를 다루는 예외는 구체적으로 정하고, 서버 결함까지 무조건 `400`으로 바꾸지 않도록 확인한다.

### 5) SSR과 Jinja2 — 데이터와 HTML 틀을 서버에서 합치기

지금까지 API가 JSON 데이터를 돌려줬다면, Jinja2를 사용하면 서버가 그 데이터를 HTML 틀에 채워 화면을 만들어 보낼 수 있다. 메뉴가 바뀔 때마다 HTML 파일의 음식 이름을 직접 고치는 대신, 메뉴 목록을 템플릿에 전달하는 방식이다.

SSR 흐름: 브라우저 요청 → 데이터 조회·가공 → context에 담기 → Jinja 렌더링 → HTML 응답 → 브라우저 표시

| 구분 | 화면을 조립하는 주체                    | 이해할 점                                                                         |
| ---- | --------------------------------------- | --------------------------------------------------------------------------------- |
| SSR  | 서버가 데이터와 템플릿을 합쳐 HTML 생성 | 첫 HTML에 내용이 담기므로 초기 표시·검색 엔진의 내용 파악에 도움이 될 수 있음     |
| CSR  | 브라우저가 JavaScript 등으로 화면 구성  | 전달받은 데이터로 화면을 구성·갱신. 실제 서비스는 두 방식을 함께 사용할 수도 있음 |

SSR이 언제나 CSR보다 빠르다는 뜻은 아니다. 서버 처리 시간, 전송량, 브라우저 작업에 따라 달라진다. 우선 ‘어디에서 데이터와 화면을 합치는가’를 구분한다.

`context`는 템플릿으로 전달하는 데이터 묶음이다. `context={'dishes': 메뉴목록}`을 전달하면 템플릿 안에서는 `dishes`라는 이름으로 접근한다. `TemplateResponse(request=request, name='menu.html', context={...})`처럼 요청·템플릿 이름·데이터를 명시해서 연결한다. HTML 화면에 필요한 공개 데이터만 담고, JSON 응답 모델이 HTML 내용까지 자동으로 걸러 줄 것이라고 생각하지 않기.

### 6) Jinja 문법과 템플릿 재사용

| 문법                                                | 역할                              | 기억할 점 / 예시                                                      |
| --------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------- |
| `{{ dish.name }}`                                   | 값이나 표현식을 출력              | 파이썬에서 전달한 메뉴 이름 표시                                      |
| `{% if ... %}` / `{% endif %}`                      | 조건에 따라 표시                  | 추천 메뉴인 경우에만 배지 출력                                        |
| `{% for ... %}` / `{% endfor %}`                    | 목록 반복 출력                    | 메뉴 수만큼 행 생성. `for`의 `else`로 반복할 항목이 없을 때 안내 가능 |
| `{# ... #}`                                         | 템플릿 주석                       | 렌더링한 HTML 결과에는 포함되지 않음                                  |
| `{{ dishes \| length }}`                            | 필터로 값 가공                    | 목록 개수를 출력. 필터는 파이프 기호로 연결                           |
| `{% include 'header.html' %}`                       | 작은 조각을 끼워 넣기             | 여러 페이지에서 같은 헤더·푸터 재사용                                 |
| `{% extends 'base.html' %}`와 `{% block content %}` | 공통 틀을 상속하고 빈 영역 채우기 | 기본 레이아웃은 공통으로 두고 페이지 본문만 교체                      |

`include`는 부품을 끼우는 방식, `extends`와 `block`은 공통 도면의 빈칸을 채우는 방식으로 생각하면 된다. 페이지마다 같은 헤더를 복사하지 않아도 되므로 수정할 지점이 줄어든다.

필터의 조건도 확인할 것. `default('익명')`은 기본적으로 정의되지 않은 값에 적용되며, `None`을 무조건 ‘익명’으로 바꾸지는 않는다. `default('익명', true)`는 `None`·빈 문자열·0처럼 거짓으로 평가되는 값도 대체하므로, 0이 유효한 값일 때는 주의한다.

`safe`는 HTML이 안전한지 검사하는 필터가 아니라 자동 이스케이프를 생략하도록 표시하는 기능이다. 사용자 입력에 무조건 적용하면 입력한 태그 등이 HTML로 해석될 수 있다. HTML 출력의 자동 이스케이프 설정과 신뢰할 수 있는 데이터인지 함께 확인한다.

### 7) templates와 static, StaticFiles와 url_for

템플릿은 데이터를 넣어 HTML을 만드는 틀이고, 정적 파일은 CSS·이미지·JavaScript 같은 파일을 그대로 제공하는 자산이다. 정적이라는 말이 파일 내용을 영원히 수정할 수 없다는 뜻은 아니다.

| 설정 요소                    | 무엇을 뜻하는가?                   | 예시                                                                                |
| ---------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------- |
| 템플릿 폴더                  | 서버가 HTML 틀을 찾는 실제 폴더    | `templates/menu.html`. 폴더를 지정했다고 원본 템플릿 전체가 웹에 공개되는 것은 아님 |
| 마운트 URL 경로              | 브라우저가 정적 파일을 요청할 주소 | `/static`                                                                           |
| `StaticFiles(directory=...)` | 파일이 있는 실제 폴더              | `BASE_DIR / 'static'`                                                               |
| `name='static'`              | URL을 찾을 때 사용할 등록 이름     | 템플릿의 `url_for('static', ...)`와 연결                                            |

`url_for('static', path='/css/style.css')`는 등록한 이름과 파일 경로로 URL을 만든다. 경로를 HTML 곳곳에 직접 적는 것보다 마운트 설정과 연결하기 쉽다. 다만 파일이 실제로 존재하는지까지 보장하는 함수는 아니므로 CSS가 안 보이면 생성된 URL과 실제 파일을 함께 확인한다.

### 8) Form 입력 → Pydantic 검증 → 화면 응답

HTML의 `<input name='price'>`에서 `name`은 서버로 보내는 필드 이름이다. `id`나 화면에 보이는 안내문이 서버의 입력 이름을 대신하지는 않는다. `price: Annotated[int, Form()]`처럼 선언하면 그 이름의 폼 값을 읽어 정수로 검증한다. 다른 이름을 받아야 하면 `alias`로 연결한다.

일반 HTML 폼은 보통 `application/x-www-form-urlencoded`, 파일 첨부 폼은 `multipart/form-data`로 전송한다. JSON 본문과 인코딩이 다르므로 서버도 `Form`으로 받을지, JSON 입력 모델로 받을지 맞춰야 한다.

교재의 처리 흐름: Form 수신 → 입력 스키마 검증 → 도메인 객체 생성 → 임시 목록에 추가 → context 구성 → HTML 재렌더링

- 입력 스키마는 타입·길이·가격 범위를 확인하고, 도메인 객체는 메뉴 데이터와 업무 규칙을 다룬다. `min_length=1`만으로 공백뿐인 이름을 막을 수는 없으므로 `strip()` 후 유효성 검사도 필요하다.
- `price`에 숫자가 아닌 값이 오거나 필수값이 빠지면, FastAPI가 처리 함수에 들어오기 전에 `422`로 응답할 수 있다. 함수 안의 `except ValidationError`만으로 이 오류를 잡을 수는 없다.
- 함수 안에서 직접 만든 Pydantic 모델의 검증 실패는 해당 위치에서 처리할 수 있다. 실패 HTML을 반환한다면 상황에 맞는 `status_code`도 명시한다. 화면에 빨간 오류 문구를 띄웠다고 상태 코드까지 자동으로 바뀌지는 않는다.
- 임시 목록은 영구 저장소가 아니다. 재시작하면 추가한 데이터가 사라지고, 여러 프로세스에 자동 공유되지 않는다.

등록 성공 후 HTML을 바로 반환하면 새로고침할 때 POST를 다시 보낼 수 있다. 성공 뒤 `303`으로 GET 화면에 이동하는 방식도 참고할 수 있다. 이는 아래 조회 예제에 구현한 동작은 아니다.

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/문법                                    | 뜻                                      | 기억할 점 / 주의점                                       |
| -------------------------------------------- | --------------------------------------- | -------------------------------------------------------- |
| Path / Query                                 | 대상 식별 / 검색·페이지 조건            | Query도 필수일 수 있음. alias는 외부 입력 이름 연결      |
| `Annotated[타입, Path(...) 또는 Query(...)]` | 타입과 입력·검증 정보 결합              | 기본값과 파이썬 인자 순서 규칙은 별도로 확인             |
| `422` / `404`                                | 요청 검증 실패 / 대상 없음              | 조회 전에 실패했는지, 조회 뒤 없는지 구분                |
| `HTTPException` / 예외 핸들러                | 실패 발생 / 예외를 응답으로 변환        | `raise`로 흐름 중단. 모든 예외를 같은 오류로 뭉개지 않기 |
| context / `TemplateResponse`                 | 화면에 전달할 데이터 / HTML 렌더링 응답 | 전달한 키와 템플릿 변수명을 맞추기                       |
| `StaticFiles` / `url_for`                    | 실제 파일 제공 / 등록 이름으로 URL 생성 | URL 경로·실제 폴더·이름을 구분                           |
| `Form`                                       | 폼 본문에서 입력 수신                   | HTML의 `name`, 전송 인코딩, 검증 위치 확인               |

### 💡 참고 (검색용) - 이해만 하고 넘어가기

| 패턴/문법                | 뜻                             | 필요할 때 찾는 팁                                                           |
| ------------------------ | ------------------------------ | --------------------------------------------------------------------------- |
| `macro`                  | 인자를 받는 재사용 템플릿 조각 | 같은 카드·버튼을 여러 데이터로 반복할 때                                    |
| `set` / `with`           | 템플릿 변수 설정 / 지역 범위   | 화면 표현을 위한 간단한 값에 사용                                           |
| `{% do ... %}`           | 결과 출력 없이 표현식 실행     | `jinja2.ext.do` 확장이 필요. 주요 데이터 가공은 서버에서 처리하는 편이 명확 |
| `default` / `safe`       | 대체값 / 이스케이프 생략 표시  | None·거짓값 처리와 HTML 안전성 의미를 혼동하지 않기                         |
| `RequestValidationError` | FastAPI 요청 검증 오류         | 폼 오류도 HTML로 안내하려면 별도의 처리 경로 검토                           |

## 3. 예제 및 실습

### 예제 1 — 식료품 주소 입력과 422·404 구분 (미실행)

학습용 메모리 데이터로 조회만 하는 예시다. 아래 코드를 실제 소스 앱으로 만들거나 실행하지 않았다.

```python
from typing import Annotated
from fastapi import FastAPI, HTTPException, Path, Query

app = FastAPI()
groceries = {1: {"id": 1, "name": "사과"}}

@app.get("/groceries")
def list_groceries(
    q: Annotated[str | None, Query(alias="query", min_length=1, max_length=30)] = None,
    limit: Annotated[int, Query(ge=1, le=50)] = 10,
    offset: Annotated[int, Query(ge=0)] = 0,
):
    results = list(groceries.values())
    if q is not None:
        results = [item for item in results if q in item["name"]]
    return results[offset:offset + limit]  # 검증한 범위로 일부만 반환

@app.get("/groceries/{item_id}")
def get_grocery(item_id: Annotated[int, Path(gt=0)]):
    # 형식·범위 검증을 통과해야 이 함수 본문까지 들어옴
    item = groceries.get(item_id)
    if item is None:
        raise HTTPException(
            status_code=404,
            detail="식료품을 찾을 수 없습니다.",
            headers={"X-Error-Code": "ITEM_NOT_FOUND"},
        )
    return item
```

| 요청                                     | 예상 결과                                        | 확인하려는 차이                                       |
| ---------------------------------------- | ------------------------------------------------ | ----------------------------------------------------- |
| `GET /groceries?limit=1&offset=0`        | `200`, `[{"id":1,"name":"사과"}]`                | 기본 목록에서 최대 1개 조회                           |
| `GET /groceries?query=없는이름`          | `200`, `[]`                                      | 정상 검색의 빈 결과. 반드시 404인 것은 아님           |
| `GET /groceries?limit=0`                 | `422`                                            | Query 범위 검증 실패                                  |
| `GET /groceries/abc` 또는 `/groceries/0` | `422`                                            | Path 타입 또는 범위 검증 실패                         |
| `GET /groceries/99`                      | `404`, `{"detail":"식료품을 찾을 수 없습니다."}` | 번호 조건은 맞지만 데이터 없음. 오류 헤더도 함께 확인 |

외부 검색 이름은 `query`이며 내부 변수는 `q`다. 예제에서 `?q=...`를 보낸다고 같은 검색으로 자동 연결되는 것은 아니다. `/docs`에서 실제 매개변수 이름을 확인한다.

### 예제 2 — 메뉴 데이터를 템플릿에 전달하기 (미실행)

예제 1의 앱에 아래 설정을 붙인다고 가정한 읽기용 코드다. `main.py` 옆에 `templates/menu.html`과 `static/css/style.css`가 이미 있다고 가정하며, 실제 파일은 만들지 않았다.

```python
from pathlib import Path as FilePath  # fastapi.Path와 이름이 겹치지 않도록 별칭
from fastapi import Request
from fastapi.responses import HTMLResponse
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

BASE_DIR = FilePath(__file__).resolve().parent
templates = Jinja2Templates(directory=str(BASE_DIR / "templates"))
app.mount("/static", StaticFiles(directory=str(BASE_DIR / "static")), name="static")

@app.get("/menu", response_class=HTMLResponse)
def menu_page(request: Request):
    dishes = [{"name": "비빔밥", "price": 9000, "recommended": True}]
    return templates.TemplateResponse(
        request=request,
        name="menu.html",
        context={"dishes": dishes},  # 템플릿의 dishes와 이름을 맞춤
    )
```

`menu.html`에 들어갈 핵심 부분:

```html
<link rel="stylesheet" href="{{ url_for('static', path='/css/style.css') }}" />
<h1>오늘의 메뉴</h1>
<ul>
  {% for dish in dishes %} {# 메뉴 하나마다 이름·가격·추천 여부를 표시 #}
  <li>
    {{ dish.name }} / {{ dish.price }}원 {% if dish.recommended
    %}<span>추천</span>{% endif %}
  </li>
  {% else %}
  <li>등록된 메뉴가 없습니다.</li>
  {% endfor %}
</ul>
```

예상 흐름은 `GET /menu` → `dishes` 전달 → 서버에서 반복·조건문 처리 → `200`과 HTML 응답이다. 브라우저에는 `비빔밥 / 9000원`, `추천`이 보이고, CSS 파일은 HTML을 읽은 브라우저가 생성된 정적 파일 URL로 별도 요청한다. `dishes=[]`로 전달하면 빈 목록 안내가 표시된다.

위 예제는 조회 화면만 다루며 폼 등록 라우터는 구현하지 않았다. 실제 폼 연동은 앞의 Form 수신·검증·업무 처리·HTML 응답 흐름을 기준으로 확인한다.

### 실행 결과

- 정상적으로 된 부분: 미실행 — 직접 요청 후 작성
- 새롭게 확인한 부분: 직접 작성
- 추가 확인: JSON 응답과 HTML 응답의 `Content-Type`, 잘못된 입력의 `422`, 없는 대상의 `404`, CSS 요청 성공 여부를 직접 확인 후 작성

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: Path는 대상, Query는 조건으로 나누어 읽는다. 입력 조건 위반과 없는 대상을 구분하고, 처리한 데이터를 context로 넘겨 서버에서 HTML을 완성한다.
- 💡 참고로 알아둘 내용: 헤더·푸터는 include, 공통 레이아웃은 extends·block으로 재사용한다. 정적 자산은 StaticFiles로 연결하고 url_for로 URL을 만든다.
- ⚠️ 헷갈리기 쉬운 주의점: Query가 항상 선택은 아니고 Annotated가 파이썬 문법 규칙을 없애지도 않는다. 오류 문구 출력과 실패 상태 코드, 입력 검증과 업무 예외는 각각 구분해야 한다.
- 한 문장 요약: 주소·폼에서 받은 입력을 올바르게 검사하고, 성공과 실패를 구분한 뒤 데이터에 맞는 JSON 또는 HTML 응답으로 연결하는 흐름을 익힌다.
