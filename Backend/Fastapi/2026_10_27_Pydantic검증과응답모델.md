## 2. 개념과 용어 정리

### 1) 타입 힌트와 Pydantic — 설명 메모와 실제 검사 장치의 차이

- 타입 힌트(Type Hint): `price: int`처럼 어떤 타입을 기대하는지 적는 설명. 일반 파이썬 코드에서는 타입 힌트만 붙였다고 잘못된 값을 실행 중에 자동으로 막아 주지는 않는다.
- Pydantic: 선언한 타입과 조건을 읽고, 실제 입력값을 검증하거나 허용된 방식으로 변환하는 라이브러리. FastAPI에서 요청 데이터를 검사할 때 사용한다.
- `BaseModel` 상속: `class BookCreate(BaseModel)`처럼 선언하면 필드와 타입을 가진 데이터 양식을 만들고, Pydantic의 검증·변환·내보내기 기능을 사용할 수 있다.

타입 힌트가 상자에 붙인 ‘정수만 넣어 주세요’라는 안내문이라면, Pydantic 모델은 상자 입구에서 실제 내용물을 확인하는 검사 장치다. 다만 무조건 원래 타입만 통과시키는 것은 아니다. 기본 모드에서는 `"12000"` 같은 숫자 문자열을 정수 `12000`으로 변환할 수 있다. `"무료"`처럼 정수로 해석할 수 없는 값은 검증에 실패한다.

| 타입 표현                        | 뜻                                  | 예시 / 기억할 점                                                       |
| -------------------------------- | ----------------------------------- | ---------------------------------------------------------------------- |
| `list[str]`                      | 문자열 요소를 담는 리스트           | 도서 태그 `['파이썬', '백엔드']`. Pydantic 모델에서는 내부 요소도 검사 |
| `dict[str, int]`                 | 문자열 키와 정수 값을 갖는 딕셔너리 | `{'입문': 3, '심화': 2}` 같은 분류별 수량                              |
| `str \| None`                    | 문자열 또는 `None` 허용             | `Optional[str]`과 같은 뜻. 이것만으로 생략 시 기본값을 정한 것은 아님  |
| `Literal['AVAILABLE', 'RENTED']` | 정해진 값 중 하나만 허용            | 아무 문자열이나 받지 않고 대여 상태를 제한. `typing`에서 가져와 사용   |

`discount_price: int | None`은 ‘정수 또는 None’이라는 타입 조건이고, `discount_price: int | None = None`은 생략했을 때 사용할 기본값까지 정한 것이다. Pydantic v2에서는 앞의 선언처럼 기본값이 없으면 `None`을 허용하더라도 필드 자체는 필수다. JSON의 `null`은 파이썬에서 `None`에 대응한다.

전날 내용과 연결하면 요청 흐름은 다음처럼 구체화된다.

요청 JSON → 입력 모델 검증·변환 → 함수에서 처리 → 응답 모델 검증·필터링 → JSON 응답

같은 모델 정보는 OpenAPI 명세와 자동 문서에도 반영된다. 어제 배운 ASGI·WSGI는 서버와 앱을 연결하는 규약이고, 오늘 배우는 모델 검증은 요청·응답 데이터의 모양과 조건을 확인하는 일이다. 비동기 함수 안의 동기 I/O, `def` 엔드포인트의 스레드풀 처리, 실패 로그·상태 코드는 그대로 구분해서 본다. 멱등성도 응답이 항상 같은지가 아니라 반복 요청의 의도한 효과가 같은지를 보는 기준이다.

### 2) BaseModel과 Field — 데이터 양식에 구체적인 조건 붙이기

`BaseModel`이 신청서 전체의 틀이라면, `Field`는 각 칸에 붙이는 작성 조건이다. 가격에 `int`만 쓰면 정수라는 조건이고, `Field(gt=0)`까지 써야 0보다 큰 정수라는 조건이 된다.

| Field 옵션                  | 뜻                                | 예시 / 주의점                                                                      |
| --------------------------- | --------------------------------- | ---------------------------------------------------------------------------------- |
| `gt` / `ge`                 | 초과 / 이상                       | `gt=0`은 0 제외, `ge=0`은 0 포함                                                   |
| `lt` / `le`                 | 미만 / 이하                       | `le=5`는 5까지 허용. 평점은 `ge=1, le=5`처럼 범위를 조합                           |
| `min_length` / `max_length` | 문자열·목록 등의 최소 / 최대 길이 | 제목 `min_length=2, max_length=100`. 공백을 제거한 길이도 필요하면 따로 확인       |
| `default`                   | 생략했을 때 사용할 값             | `default=None`이면 기본값은 `None`. 기본값이 있다는 것과 `None` 허용은 별개        |
| `default_factory`           | 기본값을 필요할 때 함수로 생성    | `default_factory=list`는 새 리스트 생성. `list()`의 결과를 미리 넣는 것과 구분     |
| `description` / `alias`     | 설명 / 외부에서 사용하는 별칭     | 문서에 설명을 붙이거나 필드 이름을 연결. 출력에도 별칭을 쓸지는 내보내기 설정 확인 |

중첩 모델(Nested Model)은 양식 안에 다른 양식을 넣는 것이다. 예를 들어 `Review` 모델의 `rating`을 1~5로 제한하고 도서 모델에 `reviews: list[Review] = Field(default_factory=list)`를 선언하면, 도서 안의 리뷰 목록까지 각 리뷰의 조건으로 검사한다. 목록이라는 사실만 확인하고 끝나는 것이 아니다.

스키마와 도메인의 역할도 구분할 것. `schemas`의 모델은 외부에서 받을 값·보낼 값의 양식이고, 도메인은 도서·대출 같은 업무 데이터와 규칙을 다룬다. 요청에서 가격 관계를 검사할 수는 있지만, 다른 경로로도 데이터가 바뀐다면 업무 규칙이 항상 지켜지도록 도메인·처리 계층에서도 설계를 확인해야 한다.

### 3) field_validator와 model_validator — 한 칸 검사와 여러 칸 비교

`Field`로 표현하기 어려운 규칙은 검증 함수(Validator)를 붙인다. 예를 들어 ‘공백을 제외한 제목이 2글자 이상’은 제목 하나의 규칙이고, ‘할인가가 정가보다 낮아야 함’은 두 필드를 비교하는 규칙이다.

| 검증 장치         | 주로 확인하는 것            | 예시 / 기억할 점                                                                        |
| ----------------- | --------------------------- | --------------------------------------------------------------------------------------- |
| `field_validator` | 지정한 필드의 값            | 제목 앞뒤 공백 제거 후 길이 검사. 여러 필드에 같은 함수를 적용할 수도 있음              |
| `model_validator` | 모델 전체 또는 필드 간 관계 | `discount_price < price`인지 비교                                                       |
| `mode='before'`   | 기본 타입 검증·변환 전 입력 | 원시값을 먼저 다듬을 때 사용. 아직 원하는 타입이라는 보장이 없으므로 입력 형태부터 확인 |
| `mode='after'`    | 기본 검증이 통과한 뒤의 값  | 변환된 필드값이나 만들어진 모델을 이용해 규칙 검사                                      |

제목 검사에 `after`를 쓰면 먼저 문자열과 `Field`의 길이 조건을 통과한 뒤 검증 함수가 실행된다. 하지만 `"  "`도 공백 두 글자이므로 최초 길이 검사는 통과할 수 있다. 따라서 `strip()`으로 앞뒤 공백을 제거한 뒤 다시 길이를 확인해야 한다. 검사 후에는 정리한 값을 반환해야 이후 처리에도 반영된다.

- `field_validator`의 반환값: 검사·정리한 필드값. `return value`나 `return cleaned`를 빠뜨리지 않기.
- `model_validator(mode='after')`의 반환값: 검사를 마친 모델 객체인 `self`.
- `cls`: 클래스 자체를 가리키는 인자. 예제의 필드 검증 함수는 공식 예시 방식대로 `@classmethod`를 명시한다.
- `self`: 만들어진 개별 모델 객체. `self.price`처럼 여러 필드를 비교할 때 사용한다.

여기서 `model_validator`의 `mode`는 명시해서 선택한다. `before`·`after` 외에 검증 흐름을 감싸는 `wrap`도 있지만, 우선 위 두 시점과 반환값을 구분한다. `after`가 자동 기본이라고 외우지 않기.

### 4) model_dump와 부분 갱신 — 생략한 값과 지우겠다는 값 구분

검증한 모델을 다른 곳에 전달할 때는 필요한 형태로 내보낸다.

| 문법                             | 결과                                              | 기억할 점                                                                    |
| -------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------- |
| `model_dump()`                   | 파이썬 딕셔너리                                   | JSON 문자열 자체가 아님. 내부에는 파이썬 자료형이 남을 수 있음               |
| `model_dump_json()`              | JSON 문자열                                       | JSON 텍스트가 필요할 때 사용. FastAPI에서 모델·딕셔너리를 반환하는 것과 구분 |
| `model_dump(exclude_unset=True)` | 요청에서 명시적으로 설정한 필드만 내보낸 딕셔너리 | 값이 기본값과 같은지가 아니라 실제로 설정했는지가 기준                       |

부분 갱신은 `PATCH /books/1`로 생각하면 된다. 전체 교체를 뜻하는 PUT과 혼동하지 않기. `discount_price`를 받는 갱신 모델에서 기본값이 `None`일 때도 다음 두 요청은 의미가 다르다.

| 갱신 요청 JSON             | `exclude_unset=True`로 꺼낸 내용 | 의미                                |
| -------------------------- | -------------------------------- | ----------------------------------- |
| `{}`                       | `{}`                             | 할인가를 건드리지 않음              |
| `{"discount_price": null}` | `{'discount_price': None}`       | 명시적으로 할인가를 비우겠다는 요청 |

`exclude_unset`은 명시한 `null`을 제거하지 않는다. ‘생략’과 ‘삭제·초기화’를 구분해야 기존 값이 의도치 않게 사라지지 않는다. 필드마다 `null`로 비우는 것을 허용할지도 별도로 정한다.

안전하게 갱신하려면 새로 온 필드만 검사하고 끝내면 안 된다. 기존 정가가 20000원, 할인가가 15000원인데 정가만 10000원으로 바꾸면, 요청에는 정가 하나뿐이어도 병합 후에는 할인 규칙이 깨진다.

1. `changes = patch.model_dump(exclude_unset=True)`로 명시한 변경만 추린다.
2. 기존 값과 합쳐 전체 후보 데이터를 만든다.
3. `validated = BookCreate.model_validate(후보_데이터)`처럼 전체 상태의 조건을 다시 검사한다. 실제 서비스에서는 저장할 전체 상태에 맞는 모델을 사용한다.
4. 검사에 통과한 원본 후보를 그대로 쓰지 말고, `validated.model_dump()`처럼 변환·정규화까지 반영된 결과를 저장·처리에 사용한다.

검증 객체만 만들어 놓고 버리면 제목의 공백 제거 같은 결과도 함께 버릴 수 있다. ‘오류가 안 났다’뿐 아니라 ‘검증한 결과를 실제로 쓰는가’까지 확인할 것.

### 5) 입력 모델과 응답 모델 — 입구 검사와 출구 검사

입력 모델이 신청서를 검사하는 입구라면, 응답 모델은 외부에 공개할 항목만 골라 보내는 출구다. 내부 데이터에 값이 있다고 전부 사용자에게 보낼 필요는 없다.

| 구분                          | 역할                               | 예시                                                         |
| ----------------------------- | ---------------------------------- | ------------------------------------------------------------ |
| 입력 모델 `BookCreate`        | 요청에서 받을 값과 조건 정의       | 제목, 양수 정가, 정가보다 낮은 할인가                        |
| 응답 모델 `BookResponse`      | 반환할 데이터 검증·변환·필터링     | 외부에 보여 줄 제목·정가·할인가만 선언                       |
| `response_model=BookResponse` | 해당 응답 모델을 엔드포인트에 지정 | 반환한 딕셔너리에 내부 메모가 있어도 선언된 공개 필드만 응답 |

응답 모델은 OpenAPI 문서에도 반영되므로, 클라이언트가 어떤 값을 받을지 확인할 기준이 된다. 다만 모델에 민감한 필드를 선언해 버리면 그대로 공개될 수 있고, 인증·권한 검사까지 해결하는 기능도 아니다.

`JSONResponse` 같은 응답 객체를 직접 반환하면 일반적인 응답 모델의 자동 검증·필터링 흐름을 건너뛸 수 있다. 직접 응답을 만드는 이유와 내부 필드 노출 여부를 확인해야 한다. 응답 모델을 쓴다고 모든 상황에서 무조건 더 빨라진다고 단정하지도 않는다.

오류의 책임도 구분한다. 요청이 입력 모델에 맞지 않으면 FastAPI 기본 동작은 `422`다. 반대로 서버가 응답 모델에 맞지 않는 데이터를 반환하면 서버 코드 쪽 문제이며, 기본적으로 서버 오류로 처리된다. 처리 함수에서 검증 예외를 직접 잡아 `400`으로 바꾸는 것은 개발자가 추가로 정한 동작이다.

### 6) 공통 응답과 자동 문서화

공통 응답은 `{"success": true, "data": ..., "error": null}`처럼 결과를 같은 모양의 봉투에 담는 방식이다. 필수 규칙이라기보다 팀이 선택하는 약속이다. `APIResponse[T]` 같은 제네릭 모델을 만들어 두면 봉투의 모양은 유지하고 `data`에 들어갈 타입만 바꿔 쓸 수 있다.

| 타입 표현                         | `data`에 담는 내용 | 기억할 점                            |
| --------------------------------- | ------------------ | ------------------------------------ |
| `APIResponse[BookResponse]`       | 도서 한 권         | `T` 자리에 단건 도서 모델을 대입     |
| `APIResponse[list[BookResponse]]` | 도서 목록          | `T` 자리에 도서 모델의 리스트를 대입 |

이때 `APIResponse`는 직접 정의해야 하는 모델이며 FastAPI가 자동으로 만들어 주는 이름은 아니다. 성공 응답의 모양을 정했다고 `HTTPException`으로 발생한 오류까지 같은 봉투로 자동 통일되지는 않는다. 오류 응답도 통일하려면 예외 처리와 문서화 방식을 함께 정해야 한다.

| 기본 경로       | 무엇을 볼 수 있는가?                    | 확인할 점                             |
| --------------- | --------------------------------------- | ------------------------------------- |
| `/openapi.json` | 요청·응답 구조를 표현한 OpenAPI 명세    | 문서 도구가 읽는 기계용 JSON          |
| `/docs`         | 요청을 직접 보내 볼 수 있는 대화형 문서 | 입력 조건, 실제 상태 코드와 응답 확인 |
| `/redoc`        | API 구조를 읽기 좋게 보여 주는 문서     | 모델과 API 설명을 전체적으로 검토     |

앱의 제목·설명·버전이나 필드의 `description`도 문서 이해에 도움이 된다. 다만 문서가 생겼다고 정상·실패 요청을 테스트한 것은 아니다. 설명된 조건이 실제로 적용되는지 요청과 응답으로 확인해야 한다.

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/문법                       | 뜻                                  | 기억할 점 / 주의점                                       |
| ------------------------------- | ----------------------------------- | -------------------------------------------------------- |
| `BaseModel` / `Field`           | 데이터 모델 / 필드 조건             | 타입과 범위·길이·기본값은 구분해서 선언                  |
| `field_validator`               | 필드값 검사·정리                    | 정리한 값을 반환해야 반영됨                              |
| `model_validator(mode='after')` | 기본 검증 뒤 모델 전체 검사         | 필드 간 관계를 확인한 뒤 `self` 반환                     |
| `exclude_unset=True`            | 명시적으로 설정한 필드만 추출       | 명시한 `null`과 생략은 다름                              |
| `response_model`                | 응답의 검증·필터링·문서화 기준      | 내부 데이터 전체를 그대로 노출하지 않도록 공개 필드 확인 |
| 입력 검증 / 응답 검증 실패      | 요청 데이터 문제 / 서버 반환값 문제 | 둘을 모두 사용자 입력 오류로 취급하지 않기               |

### 💡 참고 (검색용) - 이해만 하고 넘어가기

| 패턴/문법                       | 뜻                                   | 필요할 때 찾는 팁                                    |
| ------------------------------- | ------------------------------------ | ---------------------------------------------------- |
| `strict` 모드                   | 자동 타입 변환을 더 엄격하게 제한    | 숫자 문자열까지 거절해야 할 때 타입별 허용 기준 확인 |
| `alias` / `by_alias`            | 외부 필드 별칭 / 별칭으로 내보내기   | 입력에서 받은 이름과 출력 이름이 다를 때 확인        |
| `mode='before'` / `mode='wrap'` | 기본 검증 전 처리 / 검증 흐름 감싸기 | 원시 입력 정리나 검증 흐름 제어가 필요할 때 찾아보기 |
| `APIResponse[T]`                | 내부 타입을 바꿔 쓰는 공통 응답 틀   | 단건·목록을 같은 외형으로 반환할 때 활용             |

## 3. 예제 및 실습

### 실습 내용 — 도서 입력값 미리보기 (미실행)

Pydantic v2 기준의 학습 예시다. 별도 소스 앱을 만들거나 실행하지 않았다. 저장 기능 없이 입력값을 검사하고 정리한 결과만 돌려주는 `POST /books/preview`를 가정한다. 따라서 등록 완료를 뜻하는 `201`이 아닌 `200`으로 응답한다.

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field, field_validator, model_validator

app = FastAPI()

class BookCreate(BaseModel):
    title: str = Field(min_length=2, max_length=100, description="도서 제목")
    price: int = Field(gt=0, description="0보다 큰 정가")
    discount_price: int | None = Field(default=None, ge=0)

    @field_validator("title", mode="after")
    @classmethod
    def clean_title(cls, value: str) -> str:
        cleaned = value.strip()  # 앞뒤 공백 제거 후 실제 글자 수 재확인
        if len(cleaned) < 2:
            raise ValueError("제목은 공백을 제외하고 2글자 이상이어야 합니다.")
        return cleaned  # 정리한 값이 모델의 title에 반영됨

    @model_validator(mode="after")
    def check_discount(self):
        if self.discount_price is not None and self.discount_price >= self.price:
            raise ValueError("할인가는 정가보다 낮아야 합니다.")
        return self  # 모델 전체 검사를 마친 객체 반환

class BookResponse(BaseModel):
    title: str
    price: int
    discount_price: int | None = None

@app.post("/books/preview", response_model=BookResponse)
def preview_book(payload: BookCreate):
    result = payload.model_dump()  # 검증·변환·공백 정리를 반영한 딕셔너리
    result["internal_note"] = "서버 내부 확인용"  # 응답 모델에 없는 필드
    return result  # BookResponse가 internal_note를 제외하고 응답
```

코드 읽는 순서: `BookCreate`가 본문을 검사하고 → 제목 공백을 정리하고 → 정가·할인가 관계를 확인하고 → 처리 함수가 딕셔너리를 반환하고 → `BookResponse`가 공개 필드를 골라 응답한다. `discount_price`가 `None`이면 할인 없음, 0이면 0원 할인가이며 서로 다른 값이다.

### 요청과 예상 응답 (미실행)

다음은 curl 명령 실행 결과가 아닌 HTTP 요청·응답의 주요 부분이다. 정상 응답에서 제목 공백이 제거됐는지, 숫자 문자열이 정수로 바뀌었는지, 내부 메모가 빠졌는지 함께 본다.

```http
POST /books/preview HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json

{"title":"  파이썬 기초  ","price":"20000","discount_price":15000}
```

```http
HTTP/1.1 200 OK
content-type: application/json

{"title":"파이썬 기초","price":20000,"discount_price":15000}
```

아래 실패 조건은 정상 요청의 해당 값만 바꿔 보낸다고 가정한다.

| 입력 조건                                        | 예상 결과            | 확인하려는 내용                             |
| ------------------------------------------------ | -------------------- | ------------------------------------------- |
| 정상 요청                                        | `200`, 공개 필드 3개 | 정리·변환된 값 반환, `internal_note` 미노출 |
| `price`를 `0`으로 변경                           | `422`                | `gt=0` 조건으로 0 거절                      |
| `title`을 `"  "`로 변경                          | `422`                | 공백 제거 뒤 2글자 미만인 제목 거절         |
| `discount_price`를 `20000` 또는 `25000`으로 변경 | `422`                | 정가와 같거나 더 큰 할인가 거절             |
| `discount_price`를 `-1`로 변경                   | `422`                | `ge=0` 조건으로 음수 거절                   |
| `discount_price` 생략                            | `200`, 할인가 `null` | 기본값 `None` 적용                          |

### 실행 결과

- 정상적으로 된 부분: 미실행 — 직접 요청 후 작성
- 새롭게 확인한 부분: 직접 작성
- 문서 확인: `/docs`의 입력 조건과 응답 모델이 코드와 맞는지, 실제 응답에서 내부 필드가 빠지는지 직접 확인 후 작성

### AI 코드와 실습을 확인할 때 사용할 기준 (아직 미실행)

- [ ] 타입만 선언했는가, 양수·길이·허용값 같은 실제 조건도 선언했는가?
- [ ] 제목을 공백 제거 후 다시 검사하고 그 결과를 반환하는가?
- [ ] 할인가의 음수를 막고, 할인가가 있을 때 정가보다 낮은지도 확인하는가?
- [ ] PATCH에서 생략과 `null`을 구분하고, 기존 값과 병합한 전체 상태를 다시 검증하는가?
- [ ] 검증 객체를 버리지 않고 변환·정리된 결과를 실제 처리에 사용하는가?
- [ ] `response_model`의 공개 필드가 적절하며, 직접 응답 반환 때문에 필터링을 건너뛰지 않는가?
- [ ] 정상·실패 상태 코드와 실제 응답을 확인했는가? 자동 문서가 생긴 것만으로 검증 완료라고 하지 않는가?

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 들어오는 데이터는 Pydantic으로 검사하고, 나가는 데이터는 응답 모델로 제한한다. `Field`로 각 칸의 조건을, Validator로 정리·비교 규칙을 표현한다.
- 💡 참고로 알아둘 내용: 공통 응답은 봉투를 재사용하는 방식이고, 자동 문서는 요청·응답 양식을 확인하는 도구다. 필요한 경우 팀의 규칙에 맞춰 적용한다.
- ⚠️ 헷갈리기 쉬운 주의점: 타입 힌트만으로 실행 중 검사가 강제되지는 않는다. `None` 허용과 필드 생략은 다르며, 검증한 결과를 버리면 정규화 결과도 사라질 수 있다.
- 한 문장 요약: 모델은 데이터 모양만 적는 문서가 아니라, 입력을 검사·정리하고 외부로 보낼 응답의 범위를 정하는 기준이다.
