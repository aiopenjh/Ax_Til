## 2. 개념과 용어 정리

### 1) 인증과 인가 — 누구인가, 무엇을 할 수 있는가

| 구분 | 확인하는 것 | 수업 코드의 예 |
| --- | --- | --- |
| 인증(Authentication) | 전달된 자격 정보로 사용자를 확인 | 이메일·비밀번호 검증, JWT 검증 후 사용자 조회 |
| 인가(Authorization) | 확인한 사용자의 행동을 허용할지 판단 | `role == "ADMIN"` 검사 |
| 인증 실패 | 사용할 수 있는 인증 정보가 없음 | 잘못된 비밀번호, 만료·위조·로그아웃 토큰 → 인증 예외 |
| 권한 부족 | 사용자는 확인됐지만 해당 권한이 없음 | 일반 사용자의 관리자 기능 요청 → 권한 예외 |

로그인에서 한 번 확인했다고 이후 요청을 모두 신뢰하는 것은 아니다. 보호된 요청에서도 토큰과 사용자 상태를 확인하고, 기능에 필요한 권한을 별도로 검사한다.

### 2) 세션과 JWT — 서버가 무엇을 기억하는가

| 구분 | 서버 세션 | JWT 기반 요청 |
| --- | --- | --- |
| 클라이언트가 보내는 것 | 보통 세션 ID | 서명된 토큰 |
| 기본적인 확인 방식 | 세션 저장소에서 상태 조회 | 서명·만료·필요한 클레임 확인 |
| 강제 무효화 | 서버의 세션 상태 변경 | 만료 외에 블랙리스트 같은 추가 장치 필요 |
| 이 수업의 구현 | 세션 ID 기반 구현 아님 | JWT 검증에 DB 블랙리스트·회원 조회를 추가 |

JWT를 쓴다고 DB 조회가 항상 0번인 것은 아니다. 이 수업 코드는 로그아웃된 토큰인지 DB로 확인하고 현재 회원도 조회한다. Stateless라는 설명을 '서버가 상태를 절대 저장하면 안 된다'는 뜻으로 받아들이지 않는다.

### 3) 비밀번호는 복호화하지 않고 검증하기

회원가입에서 해시를 저장하고, 로그인에서는 입력한 평문과 저장된 해시를 비밀번호 검증 함수에 함께 넘긴다. 저장된 해시를 원래 비밀번호로 되돌리는 과정은 없다.

```python
user = await self._user_repo.find_by_email(email)
if not user:
    return None
if not self._password_hasher.verify(plain_password, user.password_hash):
    return None  # 저장된 해시와 검증. 새로 해시한 문자열끼리 비교하지 않음
return user.id
```

비밀번호 해시는 salt 때문에 같은 평문이라도 생성 결과가 달라질 수 있다. `hash(입력값) == 저장값`처럼 직접 비교하지 않고 `verify`를 사용한다.

수업의 `UserCredentialVerifierImpl`은 회원 저장소와 해시 도구를 받아 검증한다. `AuthService`는 이메일 조회 SQL이나 Bcrypt 내부 연산을 직접 구현하지 않는다.

### 4) JWT의 구조와 클레임

JWT는 `header.payload.signature` 형태다. 서명은 변조 여부를 검증하는 장치이며 payload를 비밀로 숨기는 암호화와는 다르다. payload에 비밀번호나 비밀값을 넣지 않는다.

| 항목 | 뜻 | 수업 코드의 사용 |
| --- | --- | --- |
| `sub` | 토큰의 주체 | 사용자 UUID를 문자열로 저장 |
| `jti` | 토큰 하나의 식별자 | 로그아웃 시 이 값을 블랙리스트에 저장 |
| `exp` | 만료 시각 | 유효기간 검증·차단 기록 정리에 사용 |
| `iat` | 발급 시각 | 토큰 생성 시각 기록 |
| `HS512` | 수업 코드의 대칭키 서명 알고리즘 | 발급·검증 양쪽에서 같은 설정 사용 |

```python
payload = {
    "sub": str(user_id),
    "jti": str(uuid.uuid4()),     # 같은 사용자가 발급받아도 토큰마다 다름
    "exp": expired_at,
    "iat": now,
}
encoded = jwt.encode(payload, secret_key, algorithm="HS512")
```

수업 코드 기본 유효기간은 60분이며 응답의 `expires_in`은 초 단위다. 60분이면 3600초다. 비밀키는 발급·검증 서버 설정에서 관리하며 수업의 예시 기본 문자열을 실제 서비스의 공용 키로 사용하지 않는다.

### 5) decode — 읽기와 검증을 구분하기

```python
payload = jwt.decode(token, self.secret_key, algorithms=[self.algorithm])
return TokenPayload(
    user_id=uuid.UUID(payload["sub"]),  # 문자열 → UUID
    jti=payload["jti"],
    exp=datetime.fromtimestamp(payload["exp"], tz=timezone.utc),
)
```

단순히 payload 문자열을 읽는 것만으로 인증을 통과시키지 않는다. 수업 코드는 `jwt.decode`로 서명·만료를 검증하고, 필요한 값의 누락·UUID 변환 실패 등도 인증 예외로 처리한다.

| 확인 대상 | 코드 위치 | 실패했을 때 |
| --- | --- | --- |
| 서명·만료·토큰 형식 | `JwtTokenProvider.decode_token` | 유효하지 않거나 만료된 토큰으로 처리 |
| jti 차단 여부 | `AuthService.authenticate_token` | 로그아웃된 토큰으로 처리 |
| 사용자 존재·탈퇴 상태 | `wiring/user.py` | 사용자 없음 또는 탈퇴 상태 예외 |
| 관리자 역할 | `resolve_require_admin` | 관리자 권한 예외 |

### 6) 로그아웃 — 토큰을 지우는 것과 차단하는 것

클라이언트에서 토큰을 지워도 이미 복사된 문자열은 남을 수 있다. 따라서 수업 코드는 로그아웃한 토큰의 `jti`와 만료 시각을 DB에 저장한다.

```python
payload = self._token_provider.decode_token(token)
if not await self._blacklist_repo.is_blacklisted(payload.jti):
    await self._blacklist_repo.add(jti=payload.jti, expired_at=payload.exp)
await self._blacklist_repo.cleanup_expired(datetime.now(timezone.utc))
```

| 처리 | 목적 | 주의점 |
| --- | --- | --- |
| `is_blacklisted(jti)` | 차단 기록 존재 확인 | 해당 토큰 식별자 기준 |
| `add(jti, expired_at)` | 만료 전 토큰도 재사용 금지 | 사용자 전체 토큰을 일괄 차단하는 구현은 아님 |
| `cleanup_expired(now)` | 만료된 차단 기록 삭제 | 이 예제는 로그아웃 시 호출. 시간이 지나면 DB가 저절로 삭제하는 기능은 아님 |
| 인증 시 재검사 | 복사된 토큰 재사용 차단 | 검사를 거치지 않는 경로에는 효과를 단정할 수 없음 |

`TokenBlacklistModel`은 `jti`를 기본키로, `expired_at`을 시간대가 있는 `DateTime`으로 둔다. JWT 내용이나 서명을 바꾸는 대신 서버의 차단 판단을 추가하는 방식이다.

### 7) 교재와 당일 코드의 차이

| 항목 | 노션 교재 예제 | 11/4 `auth_ex` 수업 코드 |
| --- | --- | --- |
| 로그인 입력 | `OAuth2PasswordRequestForm` 폼 | `LoginRequest` JSON, 이메일·비밀번호 |
| 토큰 | 액세스 + 리프레시 | 액세스 토큰 |
| 서명·기간 | HS256, 액세스 30분 | HS512, 액세스 기본 60분 |
| 블랙리스트 | 메모리 set에 리프레시 토큰 문자열 | DB에 액세스 토큰 `jti`·만료 시각 |
| 재발급 | `/refresh` 예제 있음 | 확인한 라우터에는 재발급 API 없음 |

리프레시 토큰은 교재의 보충 개념으로 구분한다. 당일 코드에서 액세스·리프레시 토큰 쌍을 구현했다고 적지 않는다. JSON 로그인과 Bearer 인증을 사용한다고 해서 교재의 OAuth2 폼 흐름과 구현이 완전히 같은 것도 아니다.

### 8) wiring — 의존성의 빈자리를 구현체로 연결하기

`provide_auth_service` 같은 함수는 표현 계층이 필요한 의존성을 선언하는 자리다. 함수 본문에는 `NotImplementedError`가 있지만, 앱 시작 시 실제 생성 함수로 연결한다.

```python
app.dependency_overrides.update({
    provide_auth_service: create_auth_service,  # 함수 호출 결과가 아니라 함수 자체
})
```

| 구성 | 맡는 일 | 주의점 |
| --- | --- | --- |
| `presentation/dependencies.py` | 필요한 서비스·사용자 의존성 선언 | 바인딩 없이 호출하면 `NotImplementedError` |
| `wiring/auth.py` | 토큰 도구·자격 검증기·블랙리스트 저장소 조립 | 세션과 회원 저장소 전달 |
| `wiring/user.py` | 현재 사용자 확인·관리자 검사 연결 | 토큰 주체 UUID로 회원 조회 |
| `wiring/__init__.py` | 모듈별 연결 함수 실행 | 모듈 연결 호출 누락 확인 |
| `get_db` | 세션 제공·성공 시 커밋·실패 시 롤백 | 비동기 `commit`도 `await` 필요 |

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/명령어 | 뜻 | 기억할 점 / 주의점 |

| 인증 / 인가 | 사용자 확인 / 행동 허용 판단 | 사용자 조회 뒤 역할 검사 |

## 3. 예제 및 실습

### 수업 예제 — 로그인부터 로그아웃까지 (미실행)

```text
POST /v1/auth/login
  → 이메일·비밀번호 확인
  → 액세스 토큰, bearer, expires_in 반환

Authorization: Bearer <토큰>
  → 서명·만료 → jti 차단 여부 → 사용자 조회
  → 관리자 기능이면 역할도 확인

POST /v1/auth/logout
  → 토큰의 jti·만료 시각 저장
  → 이후 같은 토큰 인증 요청 차단
```

| 비교할 요청 | 코드에서 기대하는 동작 | 직접 확인할 항목 |
| --- | --- | --- |
| 올바른 계정으로 로그인 | 토큰 응답 | 응답 필드·유효기간 |
| 잘못된 비밀번호 | 인증 예외 | 실제 HTTP 상태·오류 본문 |
| 로그아웃 후 같은 토큰 | 블랙리스트로 인증 거절 | DB 적재와 다음 요청의 차단 |
| 일반 사용자로 관리자 기능 | 권한 예외 | 인증과 인가가 다른 단계인지 |

`/v1/users/me`는 당시 코드에서 사용자 로깅용 경로이며 명시적인 사용자 응답 반환이 없다. 사용자 정보 JSON을 반환하는 완성 API로 소개하지 않는다.

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 비밀번호 확인, JWT 검증, 블랙리스트 조회, 사용자 상태 확인, 권한 검사를 각각 구분한다.
- 💡 참고로 알아둘 내용: 수업 코드는 DB의 jti 블랙리스트를 사용한다. 교재의 리프레시 토큰 예제와 구현 범위가 다르다.
- ⚠️ 헷갈리기 쉬운 주의점: 토큰을 삭제하는 것과 서버가 재사용을 차단하는 것은 다르다. JWT는 payload를 숨기는 암호화가 아니다.
- 한 문장 요약: 토큰을 발급하는 데서 끝내지 않고, 요청마다 사용할 수 있는 토큰과 사용자인지 확인한다.
