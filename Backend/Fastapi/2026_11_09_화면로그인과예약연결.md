## 2. 개념과 용어 정리

### 1) 라우터 등록과 응답 모양 맞추기

운영자·예약 조회 라우터를 메인 앱에 등록하고, 예약 응답 변환 함수가 받는 인자를 최신 규격에 맞췄다. 함수 파일이 존재하는 것과 앱에 HTTP 경로가 등록되는 것은 다른 단계다.

```python
now = seoul_now()
items = [
    ReservationOut.from_domain(reservation, slot, owner.user_id, now)
    for reservation, slot in rows
]
# 누가 보는지와 현재 시각을 넘겨 응답의 취소 가능 여부를 계산한다.
```

| 전달 값 | 필요한 이유 | 주의점 |
| --- | --- | --- |
| `reservation` | 예약 상태·본인 정보 | 예약 데이터의 소유자와 현재 요청자를 구분 |
| `slot` | 방문 시작 시각 등 | 현재 시각과 비교할 시간대 일치 |
| `viewer_id` | 누가 보고 있는지 | 운영자는 운영자 ID, 손님은 손님 ID 전달 |
| `now` | 시간에 따른 가능 여부 | 목록 응답에서는 같은 now를 재사용 |

당시 취소 권한 규칙에서는 손님 본인의 시작 전 예약만 취소 가능했다. 이후 운영자·관리자 취소가 추가된 규칙을 이 날짜의 응답에 거꾸로 적용하지 않는다.

### 2) 실제 DB 확인 — 가짜 저장소가 지나가지 않는 부분

| 검사 방식 | 잘 확인하는 것 | 빠지는 부분 |
| --- | --- | --- |
| 서비스 + 가짜 저장소 | 403·404 조건, 반환값 | SQL·외래키·JOIN·DB 자료형 |
| 라우터 + 가짜 로그인 | HTTP 응답 모양, 역할 분기 | 실제 토큰 검증 |
| 실제 앱 + DB·로그인 | 인증 → SQL → 변환 → 응답 | 재현할 계정·날짜·데이터 준비 필요 |

이날 작업 기록에는 운영자·손님 계정을 나눠 가입·로그인하고, 식당·슬롯·예약 데이터를 준비해 API를 호출한 확인이 남아 있다. 임의로 반복 실행하는 대신 기대하는 계정·상태·응답을 먼저 정해 두는 방식이다.

시간 필터도 실제 DB에서 확인해야 한다. 서울 기준 날짜를 골랐는데 UTC의 다른 날짜로 조회되거나, 응답의 시간대가 사라지는 문제는 권한 테스트만으로 잡기 어렵다.

### 3) Jinja2 화면과 JSON API의 오류 응답

| 구분 | JSON API | Jinja2 화면 |
| --- | --- | --- |
| 정상 응답 | 정해진 응답 스키마 | 템플릿에 데이터 전달 |
| 없는 식당 | JSON 오류 봉투 | 읽을 수 있는 404 안내 화면 |
| 로그인 필요 | 인증 오류 | 로그인 화면으로 이동 후 원래 화면 복귀 |
| 권한 없음 | 403 오류 봉투 | 403 안내 화면 |

같은 서비스 예외를 사용하더라도 표현 방식은 요청 경계에 맞춘다. 화면에서 JSON 오류 본문이 그대로 열리면 사용자는 어떻게 돌아가야 할지 알기 어렵다.

```python
try:
    restaurant = await service.get_restaurant(restaurant_id)
except RestaurantNotFoundError:
    return templates.TemplateResponse(
        request=request, name="message.html",
        context={"title": "식당을 찾을 수 없어요"}, status_code=404,
    )
# 안내 화면 변환을 설명한 발췌. 업무의 존재 여부 판단은 서비스에서 한다.
```

### 4) HTML 폼의 빈 문자열과 None

검색 폼은 비워 둔 칸도 빈 문자열로 보낼 수 있다. 선택하지 않았다는 뜻의 None과 빈 글자를 검색하라는 뜻이 섞이지 않도록 화면 입력 단계에서 정리한다.

```python
Blank = BeforeValidator(lambda value: value or None)
# ""은 None으로 바꾼 뒤 날짜·필터 타입 검증을 진행한다.
```

| 입력 | 의미 | 처리 |
| --- | --- | --- |
| 날짜 생략·빈칸 | 아직 선택하지 않음 | 서울 기준 기본 날짜 적용 |
| 음식 종류 빈칸 | 종류 필터 없음 | None으로 정리 |
| 올바른 날짜 | 해당 날짜 조회 | 날짜 타입으로 전달 |
| 잘못된 날짜 문자열 | 형식 오류 | 기본 날짜로 몰래 바꾸지 않고 검증 |

### 5) JWT의 종류와 전달 위치는 다르다

기존 API는 `Authorization: Bearer` 헤더로 토큰을 받는다. 일반 브라우저 이동은 그 헤더를 자동으로 만들어 주지 않으므로, 화면에서는 같은 JWT를 쿠키에 담아 보냈다.

| 항목 | API | 화면 |
| --- | --- | --- |
| 경로 | `/api/v1/...` | `/ui/...` |
| 전달 위치 | Authorization 헤더 | `ui_access_token` 쿠키 |
| 인증 처리 | 기존 인증 서비스 | 기존 `login`·`authenticate` 재사용 |
| 성공 후 동작 | 토큰·JSON 응답 | 쿠키 저장·화면 이동 |

```python
response.set_cookie(
    COOKIE_NAME, issued.access_token,
    max_age=issued.expires_in,
    httponly=True, samesite="lax", path="/ui",
)
```

| 쿠키 설정 | 의미 | 한계·주의점 |
| --- | --- | --- |
| `HttpOnly` | 자바스크립트에서 직접 읽지 못함 | 모든 보안 문제를 해결하는 옵션은 아님 |
| `SameSite=Lax` | 다른 사이트에서 보낼 때의 동작 제한 | 쿠키 기반 요청의 보호 범위는 별도 검토 필요 |
| `Path=/ui` | 해당 화면 경로에 전송 | API의 Bearer 인증을 대신하지 않음 |
| `max_age` | 브라우저의 쿠키 보관 시간 | 서버의 토큰 만료 검증도 필요 |

이날 화면 로그아웃은 쿠키 삭제까지였다. 서버의 토큰 차단 서비스와 연결한 것은 다음 날 변경이므로, 이미 복사한 토큰까지 이날 무효화됐다고 쓰지 않는다.

### 6) 로그인 뒤 돌아갈 주소 검증

`next`로 받은 주소를 그대로 사용하면 외부 사이트로 보내는 이동 경로가 될 수 있다. 화면 복귀에 필요한 내부 주소인지 제한한다.

```python
if (next_url and next_url.startswith("/ui")
        and not next_url.startswith("//") and "\\" not in next_url):
    return next_url
return None
```

이는 당시 구현의 검사 조건이다. 문자열 접두어 검사만으로 모든 URL 우회 가능성을 증명한 것은 아니며, 허용할 화면 경로와 URL 해석 방식까지 함께 봐야 한다.

### 7) 역할 허용과 조회 데이터 범위

관리자에게 운영자 권한 검사만 통과시킨다고 전체 식당을 볼 수 있는 것은 아니다. 운영자 저장소가 `owner_id = 로그인한 사람`으로 조회하면 관리자 자신의 식당만 찾게 된다.

| 역할 | 접근할 화면 | 조회 범위 |
| --- | --- | --- |
| 손님 | 식당 둘러보기·예약 | 공개 식당과 본인 예약 |
| 운영자 | 운영 식당·예약 | 본인 식당의 예약 |
| 관리자 | 운영자 → 식당 → 예약 | 관리자 조회용 범위 |

관리자 조회는 읽기 전용 저장소·서비스로 분리했다. 예약·슬롯·회원 표에서 표시할 정보만 골라 조합하며, 예약 저장 규칙이나 인증 서비스 자체를 새로 구현한 것은 아니다.

`outerjoin`을 사용하면 식당이 0곳인 운영자도 목록에 남길 수 있다. 삭제 여부 조건을 어느 위치에 두느냐에 따라 결과가 달라지므로, 단순히 JOIN 이름만 바꾸는 것으로 끝내지 않는다.

### 8) 예약 화면은 기존 예약 서비스를 호출하기

화면은 날짜·인원·슬롯이 선택한 식당과 맞는지 확인하고, 예약 저장은 다른 담당의 예약 서비스에 위임했다. 슬롯 잠금·정원·중복 예약을 화면에서 따로 구현하지 않는다.

```text
식당 상세 → 날짜·인원·시간 선택
  → 미로그인이면 로그인 후 같은 선택으로 복귀
  → 식당·날짜와 슬롯의 대응 확인
  → 기존 예약 서비스 호출
  → 성공 안내 또는 오류 코드에 맞는 화면 문구
```

사용자가 빈자리 화면을 본 뒤 실제 예약하기까지 시간이 흐른다. 화면에 보인 잔여석을 최종 판정으로 쓰지 않고, 실제 저장 시점의 검사는 예약 서비스가 수행하도록 유지한다.

| 실제 DB 확인 | 인증·SQL·응답 연결 검증 | 가짜 저장소 테스트를 보완 |
| JWT 쿠키 | 화면에서 토큰 전달 | 토큰 종류와 전달 위치는 다른 개념 |
| 역할·조회 범위 | 접근 허용과 볼 데이터 구분 | 관리자에게 운영자 문만 열어서는 부족 |
| 서비스 재사용 | 화면에서 기존 업무 처리 호출 | 화면에서 예약 규칙을 복제하지 않기 |

## 4. 실수 및 트러블슈팅

### 발생한 문제 요약

- 상황: 화면은 있었지만 로그인한 사용자를 알 수 없어 운영자·관리자 데이터를 연결하기 어려웠음
- 원인: API의 Bearer 헤더를 일반 화면 이동에서는 자동으로 보내지 않음
- 해결: 같은 인증 서비스로 발급·검증한 JWT를 화면 경로의 HttpOnly 쿠키로 전달하고, 역할과 조회 범위를 구분
- 해결 결과: 당시 실제 로그인·DB로 역할별 화면과 접근 거절을 확인한 기록이 있음. 서버 로그아웃 차단은 다음 단계로 남아 있었음

### 연결 과정에서 확인한 점

| 문제 | 원인 | 처리 |
| --- | --- | --- |
| 빈 필터로 검색 결과가 없음 | 폼의 빈 문자열을 값으로 사용 | 입력을 None으로 정리 |
| 없는 식당에서 JSON이 열림 | API 오류 응답을 화면에도 그대로 사용 | 404 안내 템플릿으로 변환 |
| 관리자가 식당을 못 봄 | 운영자 본인 범위 조회를 재사용 | 관리자 전용 읽기 조회 분리 |
| 같은 코드가 다른 PR에 중복될 위험 | dev에 직접 올린 뒤 PR을 다시 구성 | 기존 변경을 되돌린 후 PR 경로로 반영한 이력 확인 |

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 화면과 API는 같은 업무·인증 서비스를 사용하되 입력과 응답 표현은 다르게 연결할 수 있다.
