## 2. 개념과 용어 정리

### 1) 전날 복습 — DB를 기다리는 것과 데이터를 안전하게 바꾸는 것

| 복습 항목 | 뜻 | 헷갈리기 쉬운 점 |
| --- | --- | --- |
| `asyncpg` | DB 응답을 기다리는 동안 다른 요청을 처리할 수 있게 하는 비동기 드라이버 | SQL 자체의 실행 시간이 자동으로 짧아지는 것은 아님 |
| 커넥션 풀 | DB 연결을 빌려 쓰고 반납하는 구조 | 세션을 닫지 않으면 연결을 계속 점유할 수 있음 |
| `pool_pre_ping` | 연결을 꺼내기 전에 살아 있는지 확인 | 끊어진 연결을 그대로 재사용하는 문제를 줄임 |
| `selectinload` | 부모를 조회한 뒤 자식들을 IN 조건으로 미리 조회 | 일반적인 부모·자식 조회는 쿼리 2번. 모든 상황에서 항상 2번이라는 뜻은 아님 |
| `joinedload` | JOIN으로 관계 객체를 함께 조회 | 단일 관계와 컬렉션의 중복 행 문제를 구분 |
| `with_for_update()` | 같은 행을 바꾸는 트랜잭션 사이의 순서를 조절 | 일반 SELECT 전체를 막는 잠금이라는 뜻은 아님 |

메모에는 `expire_on_commit=False`와 관계 미리 로딩이 함께 적혀 있다. 둘의 대상은 다르다. 전자는 커밋 뒤 속성 만료를 막고, 후자는 아직 읽지 않은 관계 데이터의 암묵적 조회를 피한다. 전자만 설정해도 모든 관계가 자동으로 채워지는 것은 아니다.

비관적 락은 SELECT → 상태 확인 → UPDATE → COMMIT을 한 트랜잭션으로 묶어야 한다. UPDATE 문을 보낸 것만으로 잠금이 바로 풀리는 것은 아니고, 트랜잭션이 커밋·롤백될 때 풀린다.

### 2) N:N 관계 — 글 여러 개와 태그 여러 개

게시글 하나에는 태그가 여러 개 붙고, 태그 하나는 여러 게시글에서 사용된다. 어느 한쪽에 외래키 하나만 두는 것으로는 이 관계를 표현하기 어렵기 때문에 두 기본키를 모은 연결 테이블을 둔다.

```python
post_tag_association = Table(
    "posts_tags", Base.metadata,
    Column("post_id", BigInteger, ForeignKey("posts.id"), primary_key=True),
    Column("tag_id", BigInteger, ForeignKey("tags.id"), primary_key=True),
)
# 같은 (post_id, tag_id) 조합의 중복을 복합 기본키로 막는다.
```

| 설정 | 하는 일 | 수업 코드에서 확인한 점 |
| --- | --- | --- |
| `secondary=post_tag_association` | N:N 관계의 연결 테이블 지정 | `Post.tags`, `Tag.posts` 양쪽에서 사용 |
| `back_populates` | 반대쪽 관계 속성과 연결 | `tags` ↔ `posts` 이름을 맞춤 |
| `lazy="selectin"` | 컬렉션을 미리 조회 | 비동기 환경의 암묵적 관계 조회를 피하는 데 사용 |
| `Column` | 독립적인 `Table`의 컬럼 정의 | 5630990에서 누락된 import 추가 |
| 외래키 자료형 | 참조 대상 기본키와 맞춤 | `tag_id`를 `String(60)`에서 `BigInteger`로 수정 |

이 예시는 `sqlalchemy` 브랜치다. 이후 `board` 브랜치의 도메인 분리 예제와 파일 경로·모델 이름이 같다고 가정하지 않는다.

### 3) 4계층 — 요청 처리, 진행 순서, 업무 규칙, 저장 기술

| 계층 | 폴더 | 맡는 일 | 게시판 수업 코드의 예 |
| --- | --- | --- | --- |
| 표현 | `presentation` | 요청 해석, 입력·출력 스키마, HTTP 응답 | 라우터, Pydantic 스키마 |
| 응용 | `application` | 조회 → 규칙 적용 → 저장의 순서 조율 | `PostService` |
| 도메인 | `domain` | 게시글·작성자·권한 등 업무 개념과 규칙 | `Post`, `Author`, `Authority` |
| 인프라 | `infrastructure` | SQLAlchemy, DB 조회·저장, 외부 기술 구현 | `PostModel`, `SqlAlchemyPostRepository` |

메모의 주문 접수·결제 예시에서, 업무 규칙은 도메인에 두고 여러 단계를 어떤 순서로 실행할지는 응용 서비스가 조율한다. DB에 어떤 SQL을 보낼지는 저장소 구현체가 담당한다.

요청이 흘러가는 순서와 코드의 import 방향은 다르다. 수업 게시판 코드는 도메인에 저장소 인터페이스를 두고 인프라가 이를 구현한다. 따라서 도메인이 SQLAlchemy 구현 파일을 직접 불러오도록 만들 필요가 없다.

### 4) 엔티티·값 객체·애그리거트

| 개념 | 구분 기준 | 메모·수업 코드의 예 |
| --- | --- | --- |
| 엔티티(Entity) | 속성이 바뀌어도 식별자로 같은 대상을 추적 | `Post`: 제목이 바뀌어도 같은 글 |
| 값 객체(VO) | 식별자보다 값과 그 값의 규칙이 중요 | `Author`, `GuestPassword`, `BoardInfo` |
| 애그리거트(Aggregate) | 함께 일관성을 지켜야 하는 도메인 객체 묶음 | 글과 글에 필요한 작성자·비밀번호·게시판 정보 |
| 애그리거트 루트 | 묶음의 규칙을 적용하는 진입점 | `Post`의 생성·수정 메서드 |
| 도메인 서비스 | 한 객체에 자연스럽게 넣기 어려운 도메인 연산 | 여러 업무 객체가 필요한 규칙의 협력 지점 |

애그리거트는 외래키로 연결된 모든 테이블을 한 묶음으로 부르는 말이 아니다. 함께 지켜야 하는 규칙의 경계를 잡는 개념이다. 모든 연관 객체를 무조건 로딩하라는 뜻도 아니다.

메모의 회원·주문 예시에서는 주문이 필요한 주문자 정보와 회원의 전체 정보가 구분된다. 업무마다 필요한 데이터와 책임의 범위를 먼저 생각한다.

### 5) 도메인 모델과 ORM 모델을 따로 두는 이유

| 비교 | 도메인 객체 | ORM 객체 |
| --- | --- | --- |
| 목적 | 업무 개념과 규칙 표현 | DB 컬럼·외래키·관계 표현 |
| 예 | `Post`, `Author` | `PostModel` |
| 내부 구조 | `post.author.author_name` | `model.author_name`, `model.author_id` |
| 저장 관련 상태 | SQLAlchemy 세션과 독립적으로 다룸 | 세션의 변경 추적·로딩 상태가 있음 |
| 변환 | `to_domain(model)`로 복원 | `to_model(domain)`으로 저장 형태 조립 |

Mapper는 이름이 같은 칸을 기계적으로 복사하는 것만은 아니다. DB의 여러 컬럼을 `Author` 같은 값 객체로 묶거나, Enum을 문자열로 바꾸는 일도 한다.

```python
author = Author(
    author_name=model.author_name,  # DB의 평평한 컬럼을
    author_id=model.author_id,      # 작성자 값 객체로 묶는다.
)
```

기존 비밀번호 해시를 DB에서 복원할 때는 `GuestPassword.from_hash(...)`를 사용한다. 이미 해시된 값을 새 평문 비밀번호처럼 다시 해시하면 검증 대상이 달라진다.

### 6) Repository — 무엇을 저장할지와 어떻게 저장할지

도메인의 `PostRepository`는 `find_by_id`, `find_by_board_id`, `count_by_board_id`, `save` 같은 계약을 정의한다. `SqlAlchemyPostRepository`는 그 계약을 SQLAlchemy로 구현한다.

```python
stmt = select(PostModel).where(
    PostModel.post_id == post_id,
    PostModel.deleted_at.is_(None),  # 소프트 삭제된 글은 제외
)
model = await self.session.scalar(stmt)
return PostMapper.to_domain(model) if model else None
```

| 조회 요소 | 목적 | 주의점 |
| --- | --- | --- |
| `scalar` | 첫 행의 첫 값을 가져오기 | 모델 한 개 또는 COUNT 값에 사용 |
| `scalars(...).all()` | 각 행의 첫 값을 모아 목록으로 가져오기 | ORM 모델 목록을 도메인 목록으로 변환 |
| `offset`·`limit` | 건너뛸 개수와 가져올 개수 | 정렬 기준과 함께 사용 |
| 목록 조건·COUNT 조건 | 페이지 목록과 전체 개수 계산 | 게시판·삭제 여부·검색 조건이 같아야 함 |
| `outerjoin(UserModel, ...)` | 작성자 이메일 등 회원 정보 검색 | 회원 연결이 없는 비회원 글을 보존할 필요가 있음 |

### 7) flush와 commit — SQL을 보내기와 확정하기

저장소 내부에서는 `commit` 대신 `flush`를 사용하고, 공통 세션 함수에서 커밋하도록 책임을 나눴다.

| 동작 | 의미 | 트랜잭션 종료 여부 |
| --- | --- | --- |
| `add` | 세션에 새 객체 등록 | 종료하지 않음 |
| `flush` | 현재 변경을 DB에 SQL로 반영 | 종료하지 않음. 이후 롤백 가능 |
| `refresh` | DB 값을 다시 읽어 객체 갱신 | 저장 확정과 다른 일 |
| `commit` | 트랜잭션 확정 | 종료 |
| `rollback` | 이번 트랜잭션 취소 | 종료 |

저장소마다 커밋하면 두 저장 작업 중 첫 번째만 확정된 뒤 두 번째가 실패할 수 있다. 함께 성공·실패해야 하는 작업은 같은 트랜잭션 경계 안에서 처리한다. 이 수업 코드는 요청의 세션 의존성에서 커밋하도록 변경한 예다.

비동기 세션의 `commit()`에는 `await`가 필요하다. 저장소에서 `flush`까지만 했다면 마지막 커밋이 실제로 실행되는지도 확인해야 한다.

## 3. 예제 및 실습

### 수업 예제 — 조회·변환·저장의 흐름 (미실행)

```python
# 수업 Repository의 저장 흐름을 줄인 예시
new_model = PostMapper.to_model(post)  # 업무 객체 → 저장 객체
self.session.add(new_model)
await self.session.flush()            # INSERT 수행, 아직 커밋 아님
await self.session.refresh(new_model) # DB가 생성한 값 다시 읽기
return PostMapper.to_domain(new_model)
```

| 따라갈 순서 | 코드에서 확인할 내용 |
| --- | --- |
| 도메인 | 글·작성자·비밀번호 규칙이 어느 객체에 있는지 |
| ORM | 기본키·외래키·삭제 시각 컬럼이 어떻게 저장되는지 |
| Mapper | 도메인과 ORM 양쪽 속성 이름·타입이 맞는지 |
| Repository | 조회 결과 변환, 목록·개수 조건, 저장 방식 |
| 세션 | 최종 커밋과 오류 시 롤백이 어디서 실행되는지 |

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 도메인은 업무 규칙, Repository 구현체는 DB 입출력, Mapper는 둘 사이의 변환을 맡는다.
