## 2. 개념과 용어 정리

### 1) 표현 계층 — HTTP와 업무 코드를 이어 주는 곳

게시판의 규칙이 서비스와 도메인에 있어도, HTTP 요청이 그 코드로 연결되지 않으면 API로 사용할 수 없다. 라우터는 요청을 읽고 필요한 값을 서비스에 넘긴 뒤 결과를 응답 스키마로 바꾼다.

| 단계 | 수업 코드의 구성 | 맡는 일 |
| --- | --- | --- |
| 요청 받기 | `APIRouter`, 경로·본문·쿼리 | 어떤 기능을 호출할지와 입력 위치 정의 |
| 입력 검증 | `CreatePostRequest`, `PostSearchQuery` | 형식·길이·페이지 값 등 경계 검증 |
| 요청자 확인 | `get_current_author`, `get_current_role` | 작성자와 역할을 서비스에 전달 |
| 업무 처리 | `PostService`, `CommentService` | 규칙 검사와 조회·저장 순서 조율 |
| 응답 조립 | `PostDetailResponse.from_domain(post)` | 외부에 내보낼 필드 선택 |

라우터를 단순히 '함수 실행만 하는 파일'로 보는 것도 정확하지 않다. 수업 라우터는 회원·비회원 입력을 구분하고 요청 데이터를 도메인 값 객체로 조립한다. 다만 DB 조회 SQL이나 핵심 수정 권한 규칙까지 이곳에 몰아넣지는 않는다.

### 2) 경로·본문·쿼리·의존성은 들어오는 위치가 다르다

```python
async def write_post(
    board_id: str,                                      # URL 경로
    req: CreatePostRequest,                            # JSON 본문
    current_author: Author | None = Depends(get_current_author),
    current_role: Role | None = Depends(get_current_role),
    post_service: PostService = Depends(provide_post_service),
):
    ...  # 인증 정보와 서비스는 Depends가 제공한다.
```

| 값 | 예 | 구분할 점 |
| --- | --- | --- |
| 경로 매개변수 | `/v1/boards/qna/posts`의 `qna` | 어떤 게시판의 글인지 |
| 본문 | 제목·내용·비회원 이름·비밀번호 | 새로 만들거나 바꿀 데이터 |
| 쿼리 | `?page=2&search_type=TITLE&keyword=...` | 조회 조건 |
| 인증 의존성 | 현재 작성자·역할 | 요청자가 임의의 회원 번호를 본문에 넣어 결정하는 값이 아님 |
| 서비스 의존성 | `provide_post_service` | 클라이언트 입력이 아니라 서버가 조립할 객체 |

### 3) 게시판 설정·게시글·댓글의 API 구분

라우터는 `prefix="/v1"`을 사용하고, `main.py`에 `include_router`로 연결한다. 아래 경로는 수업 코드 기준이다.

| 대상 | 요청 | 역할 |
| --- | --- | --- |
| 게시판 설정 | `POST /v1/boards` | 게시판·권한·페이지 크기 생성 |
| 게시판 설정 | `GET /v1/boards`, `GET /v1/boards/{board_id}` | 목록·설정 조회 |
| 게시판 설정 | `PUT`, `DELETE /v1/boards/{board_id}` | 관리자 의존성을 거쳐 설정 변경·삭제 |
| 게시글 | `POST`, `GET /v1/boards/{board_id}/posts` | 글 작성·목록 검색 |
| 게시글 | `GET`, `PUT`, `DELETE /v1/posts/{post_id}` | 상세·수정·삭제 |
| 댓글 | `POST`, `GET /v1/posts/{post_id}/comments` | 댓글 작성·목록 |
| 댓글 | `PUT`, `DELETE /v1/comments/{comment_id}` | 댓글 수정·삭제 |

| 상태 코드 선언 | 사용한 경우 | 의미 |
| --- | --- | --- |
| `201 Created` | 게시판·글·댓글 생성 | 새 리소스 생성 |
| `200 OK` | 조회·수정의 기본 응답 | 처리한 결과 반환 |
| `204 No Content` | 삭제 | 응답 본문을 보내지 않음 |

이는 라우터에서 선언한 동작이다. 실제 호출이 성공했다는 기록과는 구분한다.

### 4) 회원·비회원 글 작성 — 작성자를 어디서 가져오는가

| 요청자 | 작성자 구성 | 비밀번호 |
| --- | --- | --- |
| 회원 | 인증 정보의 `Author` 사용 | 글 전용 비회원 비밀번호를 사용하지 않음 |
| 비회원 | 요청의 이름으로 `Author.guest(...)` 구성 | 요청의 비회원 비밀번호를 도메인 생성에 전달 |
| 작성 권한 없음 | 게시판의 허용 역할 검사에서 거절 | 이름·비밀번호가 있어도 권한을 우회하지 못함 |

```python
if current_author is not None:
    author = current_author
    raw_password = None
else:
    if not req.guest_name or not req.guest_password:
        raise BadRequestException("비회원 작성자 이름과 비밀번호는 필수입니다.")
    # 작성자 팩토리 호출은 다음 날 인자 이름 수정이 있으므로 원문과 대조한다.
    raw_password = req.guest_password
```

서비스는 게시판이 존재하고 활성 상태인지 확인하고, 게시판의 작성 권한을 검사한 뒤 도메인 생성 함수를 호출한다. 이름과 비밀번호의 존재 확인만으로 모든 업무 검증이 끝난 것은 아니다.

수업 코드의 `Author.guest(name=...)` 호출은 실제 팩토리 인자인 `guest_name`과 맞지 않는다. 호출부도 `Author.guest(guest_name=...)`처럼 맞춰야 한다.

### 5) 응답 스키마 — 내부 객체를 그대로 내보내지 않기

```python
post = await post_service.get_post_detail(
    post_id=post_id,
    user_role=current_role,
)
return PostDetailResponse.from_domain(post)  # 외부 응답 모양으로 변환
```

| 변환 | 위치·예 | 목적 |
| --- | --- | --- |
| ORM → 도메인 | `PostMapper.to_domain` | 저장 구조를 업무 객체로 복원 |
| 요청 → 업무 입력 | 라우터의 `Authority`, `Author` 조립 | HTTP 입력을 서비스가 쓸 값으로 전달 |
| 도메인 → 응답 | `PostDetailResponse.from_domain` | JSON으로 공개할 필드와 형태 선택 |

Mapper와 응답 변환 함수는 모두 변환을 하지만 경계가 다르다. ORM 컬럼에 있는 비밀번호 해시를 응답에 그대로 포함할 이유는 없다.

`BoardMapper.to_model`에서는 `edit_role.value`로 Enum 값을 꺼낸다. Enum 객체를 DB 문자열로 바꿀 때도 실제 속성 이름을 맞춰야 한다.

### 6) 목록·검색·페이지 응답

| 항목 | 뜻 | 수업 흐름 |
| --- | --- | --- |
| `page` | 요청한 페이지 번호 | 스키마 → 서비스로 전달 |
| `page_size` | 한 번에 보여 줄 개수 | 요청 또는 서비스의 기본값 사용 |
| `search_type` | 제목·내용·작성자 등 검색 대상 | 저장소의 검색 조건으로 변환 |
| `keyword` | 검색 문자열 | 목록과 전체 개수 조회에 같은 조건 전달 |
| `total_count` | 조건에 맞는 전체 글 개수 | 현재 페이지 길이와 다름 |
| `total_pages` | 전체 페이지 수 | 전체 개수를 페이지 크기로 나누고 올림 |

```python
# 라우터의 페이지 응답 계산 부분
actual_page_size = search_params.page_size or 20
total_pages = math.ceil(total_count / actual_page_size) if total_count > 0 else 0
```

0건이면 코드에서 전체 페이지를 0으로 만든다. 마지막 페이지의 글 수가 작다고 `total_count`도 그 수로 바꾸는 것은 아니다.

또한 응답의 페이지 크기와 서비스가 실제 조회에 사용한 페이지 크기가 같아야 한다. 위 라우터의 기본값 20과 게시판 설정의 기본값이 달라질 수 있는지 따로 확인해야 하며, 코드가 있다는 것만으로 페이지 계산의 일관성까지 검증된 것은 아니다.

### 7) wiring — 서비스만 만들지 말고 앱까지 연결하기

```python
def create_post_repository(session: AsyncSession = Depends(get_db)):
    return SqlAlchemyPostRepository(session)

def create_post_service(
    post_repo=Depends(create_post_repository),
    board_repo=Depends(create_board_repository),
):
    return PostService(
        post_repo=post_repo,
        board_repo=board_repo,
        password_hasher=_password_hasher,
    )
```

| 연결 단계 | 확인할 코드 | 빠지면 생기는 문제 |
| --- | --- | --- |
| 저장소 생성 | 세션 → SQLAlchemy 저장소 | 서비스에 저장소를 줄 수 없음 |
| 서비스 생성 | 저장소·해시 도구 → 서비스 | 필요한 업무 협력 객체 누락 |
| 의존성 바인딩 | `provide_post_service: create_post_service` | placeholder의 `NotImplementedError` |
| 모듈 wiring 호출 | `wire_board_dependencies(app)` | 연결 함수를 정의해도 앱에 적용되지 않음 |
| 라우터 등록 | `app.include_router(board_router)` | 함수가 있어도 HTTP 경로로 등록되지 않음 |

`Depends`는 FastAPI가 의존성 그래프를 따라 호출할 때 해석한다. 위 생성 함수를 일반 파이썬 함수처럼 인자 없이 직접 호출하면 필요한 저장소가 자동으로 만들어진다고 가정하지 않는다.

### 8) 아직 빈 함수와 동작하는 기능 구분

`register_middleware_handlers(app)`는 본문이 `pass`인 상태다. 게시판 wiring은 저장소·서비스 생성 함수와 의존성 연결을 채우고, 앱에서 연결 함수를 호출해야 동작한다. 함수 이름만 있는 상태와 실제 구현된 상태를 구분한다.

또한 회원가입 서비스에 `except Exception`으로 예외를 받아 `ConflictException`으로 바꾸는 코드가 추가됐다. 이는 당시 코드의 처리 방식이며, 모든 예외가 실제 중복 충돌이라는 뜻은 아니다. DB 연결 실패나 구현 오류까지 같은 예외로 보일 수 있으므로 일반적인 권장 처리법으로 그대로 받아들이지 않는다.

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/명령어 | 뜻 | 기억할 점 / 주의점 |
| --- | --- | --- |
| 라우터 | HTTP 진입점 | 요청 위치·응답 스키마·상태 코드 연결 |
| `from_domain` | 업무 객체 → 응답 | DB Mapper와 구분 |
| `Depends` | 필요한 객체·요청자 정보 공급 | wiring과 앱 등록까지 확인 |
| 검색·페이지 | 조건에 맞는 글의 일부 조회 | 목록·COUNT 조건과 실제 페이지 크기 일치 |
| 회원·비회원 분기 | 작성자 정보를 얻는 경로 구분 | 인증 의존성이 비회원을 막는지도 확인 |

## 3. 예제 및 실습

### 수업 예제 — 게시글 작성 요청의 흐름 추적 (미실행)

```text
POST /v1/boards/{board_id}/posts
  → CreatePostRequest 검증
  → 현재 작성자·역할 의존성
  → 회원/비회원 입력 구분
  → PostService.write_post
  → 활성 게시판·작성 권한 검사
  → Post.create → Repository.save
  → PostDetailResponse.from_domain
```

| 확인할 사례 | 확인하려는 경계 | 직접 확인할 항목 |
| --- | --- | --- |
| 관리자 게시판 생성 | 관리자 의존성 → 서비스 | 실제 관리자 토큰으로 생성 성공 여부 |
| 회원 글 작성 | 로그인 작성자 → 도메인 | DB 적재·응답 변환 성공 여부 |
| 비회원 글 작성 | 비회원 입력 → 생성 함수 | 팩토리 인자 이름과 선택적 인증 연결 |
| 검색·페이지 조회 | 스키마 → 저장소 → 응답 | 실제 검색 결과·COUNT·페이지 수 일치 |
| 삭제 | 권한 검사 → 삭제 처리 → 204 | 재조회 시 삭제된 글이 제외되는지 |

### 실행 결과

- 정상적으로 된 부분: 직접 실행 후 작성
- 새롭게 확인한 부분: 직접 작성

| 항목 | 확인한 상태 | 다음 확인 |
| --- | --- | --- |
| 라우터 등록 | `app.include_router(board_router)` | 등록 전에는 API 코드 파일만으로 호출할 수 없음 |

| 페이지 크기 | 라우터 기본값 20 사용 | 서비스·게시판 설정과 일치하는지 |
| 미들웨어 | 등록 함수 본문은 `pass` | CORS·캐시·로깅이 구현됐다고 적지 않기 |

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 라우터는 입력·의존성을 받아 서비스로 넘기고, 처리 결과를 응답 스키마로 변환한다.
- 💡 참고로 알아둘 내용: 저장소·서비스 생성, 의존성 바인딩, 모듈 wiring 호출, 라우터 등록은 서로 다른 연결 단계다.
- ⚠️ 헷갈리기 쉬운 주의점: 비회원 None 분기가 있어도 앞단이 필수 인증이면 거기까지 도달하지 못한다. `pass`인 등록 함수는 기능 완성이 아니다.
- 한 문장 요약: 개별 계층을 만드는 것과 HTTP 요청이 끝까지 흐르도록 연결하는 것은 구분해서 확인한다.

- 아직 어려운 부분: 직접 작성
- 다음에 복습할 내용: 직접 선택·작성 — 라우터 등록, Depends 그래프, 회원·비회원 분기, 페이지 응답 계산
- 오늘의 느낀 점: 직접 작성
