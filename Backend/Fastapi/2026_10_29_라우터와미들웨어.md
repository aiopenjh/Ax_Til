### 2) APIRouter — 기능별로 나눈 작은 라우팅 묶음

회원·상품·주문 API를 모두 `main.py`에 쓰면 파일이 계속 길어지고, 여러 사람이 같은 파일을 고치다 충돌하기 쉽다. `APIRouter`는 기능별 파일에 경로를 따로 정의해 두고, `main.py`에서는 `app.include_router()`로 모아 붙이기만 하는 방식이다. 이렇게 한 파일이 한 가지 역할만 맡게 나누는 것을 관심사 분리라고 한다.

| 설정                      | 뜻                                  | 예시 / 기억할 점                                                                       |
| ------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------- |
| `prefix`                  | 라우터 안 모든 경로 앞에 붙는 주소  | `prefix="/v1/order"` + `@router.get("/{id}")` → `GET /v1/order/{id}`                   |
| `tags`                    | `/docs`·`/redoc`에서 묶어 볼 이름표 | `tags=["주문"]`. 문서 정리용이며 동작·권한에는 영향 없음                               |
| `dependencies`            | 이 라우터의 모든 경로 앞에서 실행   | `dependencies=[Depends(verify_secret_token)]`. 토큰 검사 같은 공통 규칙을 한 번에 적용 |
| `app.include_router(...)` | 분리한 라우터를 앱에 등록           | 등록하지 않으면 파일이 있어도 해당 경로는 404                                          |

수업 코드 구조(chapter04-1): `src/order/presentation/router.py`, `src/board/presentation/router.py`에 라우터를 두고 `main.py`에서 `order_router`, `board_router`로 가져와 등록했다. `include_router(router, prefix="/api")`처럼 등록할 때 접두사를 더 붙이면 `/api/v1/order`처럼 앞에 이어 붙는다.

### 3) Depends와 Header — 경로 함수 전에 공통 검사 끼워 넣기

`Depends(함수)`는 '이 경로를 실행하기 전에 이 함수를 먼저 실행하라'는 표시다. FastAPI가 그 함수에 필요한 값(헤더·쿼리 등)을 요청에서 꺼내 넣어 주고, 반환값을 경로 함수에 전달한다. 개발자가 직접 호출하지 않고 프레임워크가 넣어 준다는 점에서 의존성 주입이라고 부른다.

DRY(Don't Repeat Yourself, 같은 코드를 반복하지 말 것): 토큰 검사를 경로 함수마다 복사해 넣으면, 규칙이 바뀔 때 모든 곳을 고쳐야 하고 한 곳을 빠뜨리기 쉽다. 검사 함수를 한 번만 만들고 `Depends`로 필요한 곳(또는 라우터 전체)에 연결하면 수정할 곳이 한 군데로 줄어든다.

| 위치                                    | 반환값                       | 쓰는 경우                                                     |
| --------------------------------------- | ---------------------------- | ------------------------------------------------------------- |
| 경로 함수 인자 `x: str = Depends(f)`    | `x`에 들어옴                 | 검사 결과나 현재 사용자 정보처럼 함수 안에서 값을 써야 할 때  |
| `APIRouter(dependencies=[Depends(f)])` | 버려짐 (실행만 됨)           | 값은 필요 없고 '통과/차단'만 정하면 될 때. 예: 토큰 검사       |
| `@router.get(..., dependencies=[...])`  | 버려짐                       | 특정 경로 하나에만 검사를 걸 때                               |

의존성 함수 안에서 `raise HTTPException(status_code=403, ...)`을 하면 경로 함수 본문은 실행되지 않고 바로 오류 응답이 나간다.

`Header`는 요청 헤더에서 값을 읽는다. 파이썬 변수명 `x_token`의 밑줄(`_`)은 자동으로 하이픈(`-`)으로 바뀌어 `X-Token` 헤더를 찾는다. 헤더 이름은 대소문자를 구분하지 않는다. `Header(None)`이면 헤더가 없을 때 `None`이 들어오고, `Header(...)`이면 필수가 되어 없을 때 `422`가 난다. 수업 코드는 `Header(None)` + `if x_token != "secret"`이라서 헤더가 없을 때도 `403`이다.

`401`은 '누구인지 확인되지 않음(인증 필요)', `403`은 '누구인지와 상관없이 이 요청은 허용 안 함'에 가깝다. 수업 예제는 단순한 비밀값 비교라서 `403`을 썼다. 실제 인증은 6장(OAuth2·JWT)에서 다룬다.

### 4) 미들웨어 — 모든 요청과 응답이 지나가는 길목

미들웨어는 요청이 경로 함수에 닿기 전(전처리)과, 응답이 클라이언트로 나가기 직전(후처리)에 끼어드는 층이다. `@app.middleware("http")`로 함수를 만들고, 안에서 `await call_next(request)`를 호출하면 그 지점에서 다음 층(다른 미들웨어 또는 실제 경로)으로 넘어간다. `call_next` 앞은 전처리, 뒤는 후처리다.

```python
@app.middleware("http")
async def middleware1(request: Request, call_next):
    logger.info("요청 처리 전")          # 전처리
    response = await call_next(request)  # 다음 층으로 넘김
    logger.info("응답 처리 전")          # 후처리
    return response                      # 반드시 응답을 돌려줘야 함
```

| 내장 미들웨어           | 역할                                                     | 기억할 점                                                                           |
| ----------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `TrustedHostMiddleware` | `Host` 헤더가 허용 목록에 있는 요청만 통과               | 목록 밖이면 `400 Invalid host header`. 배포 도메인·사내 IP로 접속할 때도 목록에 추가 |
| `CORSMiddleware`        | 다른 출처의 브라우저 요청을 허용할지 결정                | 아래 5) 참고. 브라우저 규칙이라 curl·Postman 요청에는 해당 없음                     |

### 5) CORS — 다른 출처에서 온 브라우저 요청

CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)는 브라우저가 지키는 보안 정책이다. 출처(Origin)는 프로토콜(http/https) + 도메인 + 포트 세 가지를 합친 것이고, 셋이 모두 같아야 같은 출처다.

| 화면 주소 → API 주소                                   | 같은 출처? | 이유               |
| ------------------------------------------------------ | ---------- | ------------------ |
| `http://localhost:8000` → `http://localhost:8000/api`  | 같음       | 세 가지가 모두 같음 |
| `http://localhost:3000` → `http://localhost:8000`      | 다름       | 포트가 다름        |
| `http://example.com` → `https://example.com`           | 다름       | 프로토콜이 다름    |

브라우저의 기본 정책은 '다른 출처의 응답은 공유하지 않음'이다. 그래서 Next.js 화면(3000번)에서 FastAPI(8000번)를 부르면, 서버가 "이 출처는 허용한다"는 응답 헤더를 보내 줘야 브라우저가 응답을 화면 코드에 넘겨준다.

preflight(사전 요청) 흐름

1. 브라우저가 실제 요청 전에 `OPTIONS` 메서드로 먼저 묻는다: "이 출처에서, 이 메서드·헤더로 보내도 되나요?"
2. 서버가 허용하는 출처·메서드·헤더를 응답 헤더(`Access-Control-Allow-Origin`, `Access-Control-Allow-Methods` 등)로 알려 준다.
3. 허용되면 브라우저가 실제 `GET`/`POST` 요청을 보낸다. 허용되지 않으면 브라우저가 막고 콘솔에 CORS 오류를 띄운다.

JSON 본문(`Content-Type: application/json`)이나 `X-Token` 같은 직접 만든 헤더를 보내면 보통 preflight가 먼저 일어난다. 기본 헤더만 쓰는 단순한 `GET` 등은 preflight 없이 바로 보내기도 한다.

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],  # 허용할 화면 출처
    allow_methods=["*"],                      # 허용할 메서드
    allow_headers=["*"],                      # 허용할 요청 헤더 (X-Token 등)
    allow_credentials=True,                   # 쿠키·인증 정보 포함 허용
)
```

헷갈리기 쉬운 점

- CORS 오류는 '서버가 요청을 거부했다'와 다를 수 있다. 서버는 요청을 처리했어도 허용 헤더가 없으면 브라우저가 응답을 화면 코드에 주지 않는다.
- curl·Postman은 브라우저가 아니라서 CORS 규칙을 적용하지 않는다. Postman에서 되는데 브라우저에서 안 되면 CORS부터 의심한다.
- `allow_credentials=True`와 `allow_origins=["*"]`를 함께 쓰면 쿠키를 보내는 요청이 동작하지 않는다. 출처를 구체적으로 적는다.

### 6) 미들웨어 실행 순서 — 나중에 등록한 것이 바깥 껍질

미들웨어는 경로 함수를 양파 껍질처럼 감싼다. 나중에 등록한 미들웨어가 가장 바깥이 되므로, 요청 때는 나중에 등록한 것부터, 응답 때는 먼저 등록한 것부터 실행된다. `@app.middleware`와 `app.add_middleware()`가 같은 규칙을 따른다.

수업 코드 등록 순서: `middleware1` → `middleware2` → `TrustedHostMiddleware`

요청 흐름: TrustedHost → middleware2 → middleware1 → 의존성(토큰 검사) → 경로 함수
응답 흐름: 경로 함수 → middleware1 → middleware2 → TrustedHost

그래서 TrustedHost를 마지막에 등록해 두면, 이상한 호스트의 요청은 가장 바깥에서 먼저 막히고 안쪽 미들웨어·경로까지 들어오지 않는다. 반대로 토큰 검사(라우터 의존성)는 미들웨어 안쪽에서 실행되므로, 토큰이 틀려 `403`이 나는 요청도 미들웨어 로그는 남는다.

### 7) 미들웨어와 라우터 의존성 — 어디에 걸지 고르기

| 비교          | 전역 미들웨어                                       | 라우터 의존성 (`dependencies=[Depends(...)]`)      |
| ------------- | --------------------------------------------------- | -------------------------------------------------- |
| 적용 범위     | 모든 요청 (`/docs`, 없는 경로 요청까지)             | 해당 라우터(또는 경로)에 속한 요청만               |
| 어울리는 일   | 처리 시간 측정, 요청 로그, 공통 응답 헤더, 호스트 검사 | 기능별 토큰·권한 검사, 공통 입력값 준비            |
| 오류 처리     | 안에서 `HTTPException`을 던지면 예외 핸들러가 못 잡아 `500`이 될 수 있음. 막으려면 `JSONResponse` 등을 직접 반환 | `HTTPException`을 던지면 평소처럼 오류 응답으로 바뀜 |
| 요청 값 읽기  | `request.headers` 등을 직접 꺼냄                    | `Header`, `Query` 등으로 선언하면 검증까지 해 줌   |

'모든 요청에 같은 일'이면 미들웨어, '이 기능 묶음에만 필요한 조건'이면 의존성으로 생각한다.

### 8) 로깅 모듈화 — 설정은 한 번, 로거는 파일마다

파일이 여러 개로 나뉘어도 로그 모양은 하나로 맞춰야 읽기 쉽다. 출력 형식·레벨은 시작 파일(`main.py`)에서 `logging.basicConfig(...)`로 한 번만 정하고, 각 파일에서는 `logging.getLogger("이름")`으로 로거만 받아 쓴다.

- 로거 이름을 `delivery_system.users`, `delivery_system.deliveries`처럼 점으로 이으면 계층이 생겨, 상위 이름 기준으로 레벨을 한꺼번에 조절할 수 있다.
- 형식에 `%(name)s`를 넣으면 어느 파일(로거)에서 찍힌 로그인지 바로 보인다. 수업 로그의 `INFO:MIDDLEWARE:...`, `WARNING:TEST:...`에서 `MIDDLEWARE`, `TEST`가 로거 이름이다.
- `basicConfig`는 이미 핸들러가 설정돼 있으면 다시 호출해도 적용되지 않는다. 하위 파일마다 `basicConfig`를 복사해 두면 어느 설정이 먹었는지 헷갈리기만 한다.

### ⭐️ 필수 (실무 핵심 90%) - 반드시 기억

| 용어/문법                                  | 뜻                                      | 기억할 점 / 주의점                                          |
| ------------------------------------------ | --------------------------------------- | ----------------------------------------------------------- |
| `APIRouter(prefix, tags)`                  | 기능별 경로 묶음                        | `include_router`로 등록해야 동작. 최종 주소는 접두사 + 경로 |
| `Depends(f)`                               | 경로 전에 `f`를 실행하고 결과를 주입    | `dependencies=[...]`에 넣으면 실행만 되고 반환값은 버려짐   |
| `Header()`                                 | 요청 헤더 읽기                          | `x_token` → `X-Token`. `None` 기본값이면 생략 가능          |
| `@app.middleware("http")` / `call_next`    | 모든 요청의 전처리·후처리               | `call_next` 결과 응답을 반드시 `return`                     |
| 미들웨어 순서                              | 나중에 등록 = 바깥 껍질 = 요청 때 먼저 | 보안 검사(TrustedHost)는 마지막에 등록해 가장 먼저 걸리게   |
| `TrustedHostMiddleware`                    | 허용한 Host만 통과                      | 목록 밖이면 `400`. 접속 주소가 바뀌면 목록도 바꾸기         |
| CORS / preflight(`OPTIONS`)                | 다른 출처 브라우저 요청 허용 여부       | 출처 = 프로토콜 + 도메인 + 포트. `CORSMiddleware`로 허용    |
| DRY                                        | 같은 코드를 반복하지 않기               | 공통 검사는 함수 하나 + `Depends`                           |
| `basicConfig` 한 번 + `getLogger(이름)`    | 로그 설정 통일                          | 하위 파일에서는 로거만 받기                                 |

## 3. 예제 및 실습

### 예제 1 — 라우터 + 토큰 의존성 + 미들웨어 순서 (수업 코드 chapter04-1 기준)

수업 코드에서 핵심만 남긴 읽기용 코드다. 아래 '예상 결과'는 수업 코드(chapter04-1)를 띄워 같은 요청을 보내 확인한 값이다. 이 축약 코드 자체를 따로 실행하지는 않았다.

```python
# src/order/presentation/router.py
from fastapi import APIRouter, Depends, Header, HTTPException

def verify_secret_token(x_token: str | None = Header(None)):  # X-Token 헤더를 읽음
    if x_token != "secret":
        raise HTTPException(status_code=403, detail="토큰이 잘못되었습니다.")

# 이 라우터의 모든 경로는 실행 전에 토큰 검사를 거침
router = APIRouter(prefix="/v1/order", tags=["주문"], dependencies=[Depends(verify_secret_token)])

@router.get("")
async def get_orders():
    return None  # 수업 코드는 pass → 응답 본문은 null
```

```python
# src/main.py
import logging
from fastapi import FastAPI, Request
from fastapi.middleware.trustedhost import TrustedHostMiddleware
from order.presentation.router import router as order_router

logging.basicConfig(level=logging.INFO)  # 로그 설정은 시작 파일에서 한 번
logger = logging.getLogger("MIDDLEWARE")

app = FastAPI()

@app.middleware("http")
async def middleware1(request: Request, call_next):
    logger.info("middleware1 요청 처리 전")
    response = await call_next(request)
    logger.info("middleware1 응답 처리 전")
    return response

@app.middleware("http")
async def middleware2(request: Request, call_next):  # 나중에 등록 → middleware1보다 바깥
    logger.info("middleware2 요청 처리 전")
    response = await call_next(request)
    logger.info("middleware2 응답 처리 전")
    return response

# 마지막에 등록 → 가장 바깥에서 Host부터 검사
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["localhost", "127.0.0.1"])

app.include_router(order_router)
```

| 요청                                                    | 예상 결과                                   | 확인하려는 차이                              |
| ------------------------------------------------------- | ------------------------------------------- | -------------------------------------------- |
| `GET /v1/order` + `X-Token: secret`                     | `200`, `null`                               | 의존성 통과 후 경로 함수 실행                |
| `GET /v1/order` (헤더 없음)                             | `403`, `{"detail":"토큰이 잘못되었습니다."}` | `Header(None)`이라 422가 아니라 403          |
| `GET /v1/order` + `X-Token: wrong`                      | `403`                                       | 경로 함수 본문은 실행되지 않음               |
| `GET /v1/order` + `Host: evil.com` + `X-Token: secret` | `400`, `Invalid host header`                | 토큰이 맞아도 가장 바깥 TrustedHost에서 차단 |

토큰이 맞는 요청의 서버 로그 순서:

```txt
INFO:MIDDLEWARE:middleware2()의 요청 처리전
INFO:MIDDLEWARE:middleware1()의 요청 처리전
WARNING:TEST:test_fun() 호출
WARNING:TEST:Test: test_fun
INFO:MIDDLEWARE:middleware1()의 응답 처리 전
INFO:MIDDLEWARE:middleware2()의 응답 처리 전
```

요청은 2 → 1, 응답은 1 → 2 순서다. 가운데 `test_fun`은 수업 코드에서 `get_orders(test: str = Depends(test_fun))`로 주입한 의존성이며, 반환값 `"test_fun"`이 `test` 변수로 들어온 것을 로그로 확인할 수 있다.

```bash
# -i: 상태 코드와 헤더까지 보기. -H: 요청 헤더 추가
curl -i http://127.0.0.1:8000/v1/order -H "X-Token: secret"
curl -i http://127.0.0.1:8000/v1/order -H "Host: evil.com" -H "X-Token: secret"
```

### 실행 결과

- 정상적으로 된 부분: 직접 요청 후 작성
- 새롭게 확인한 부분: 직접 작성
- 추가 확인: `/docs`에서 `주문` 태그로 묶여 보이는지, 토큰 실패(403) 요청에도 미들웨어 로그가 찍히는지, `prefix`를 바꾸면 주소가 어떻게 바뀌는지 직접 확인 후 작성

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 기능별로 APIRouter를 나누고 main에서 모아 등록한다. 모든 요청에 같은 일은 미들웨어, 특정 기능 묶음의 조건은 의존성으로 건다.
- 💡 참고로 알아둘 내용: 로그 형식은 시작 파일에서 한 번 정하고, 각 파일은 이름 있는 로거를 쓴다. TrustedHost는 허용하지 않은 Host를 가장 바깥에서 막는다. 다른 출처의 브라우저 요청은 preflight(OPTIONS)로 먼저 허용 여부를 묻고, 서버는 CORSMiddleware로 허용한다.
- ⚠️ 헷갈리기 쉬운 주의점: 미들웨어는 나중에 등록한 것이 요청 때 먼저 실행된다. `dependencies=[...]`의 반환값은 경로 함수로 전달되지 않는다. 미들웨어 안의 `HTTPException`은 평소처럼 처리되지 않을 수 있다.
- 한 문장 요약: 요청은 바깥 미들웨어부터 안쪽으로, 라우터 의존성을 거쳐 경로 함수에 닿고, 응답은 그 반대 순서로 나간다.
