## 2. 개념과 용어 정리

### 1) 화면 로그아웃 — 쿠키를 지우는 것과 토큰을 막는 것

전날 화면 로그아웃은 브라우저 쿠키만 삭제했다. 토큰을 미리 복사했다면 서버가 그 토큰을 계속 받아 줄 수 있으므로, 기존 인증 담당의 `logout`을 화면에서도 호출하도록 연결했다.

```python
token = request.cookies.get(COOKIE_NAME)
if token:
    try:
        await auth.logout(token=token)  # 기존 인증 서비스의 차단 처리
    except AppError:
        pass
response.delete_cookie(COOKIE_NAME, path=COOKIE_PATH)
```

| 처리 | 목적 | 구분할 점 |
| --- | --- | --- |
| 인증 서비스 `logout` | 서버가 토큰 재사용을 거절하도록 처리 | 블랙리스트·트랜잭션은 인증 담당 구현 재사용 |
| `delete_cookie` | 브라우저가 다음 화면 요청에 쿠키를 보내지 않게 함 | 설정 때와 같은 경로 사용 |
| 예외 처리 | 이미 사용할 수 없는 토큰도 화면 로그아웃 진행 | 모든 장애를 무조건 정상 처리해도 된다는 일반 규칙은 아님 |
| HTTPS의 `Secure` | HTTPS 접속에서 쿠키를 안전한 전송으로 제한 | 프록시 환경에서는 실제 scheme 인식도 확인 필요 |

```python
secure=request.url.scheme == "https"
# 로컬 HTTP와 HTTPS에서의 쿠키 설정을 구분한다.
```

내 변경은 화면과 기존 로그아웃 서비스를 연결한 것이다. 인증 서비스의 해싱·시도 제한·만료 기록 정리 등 다른 담당의 구현을 내가 새로 만들었다고 쓰지 않는다.

### 2) 파이썬 int와 DB 번호 범위는 다르다

파이썬에서 큰 정수로 읽을 수 있어도 DB의 BIGINT 범위를 넘으면 조회 중 오류가 날 수 있다. 존재하지 않는 번호와 자료형 범위를 벗어난 입력을 구분해 요청 단계에서 제한했다.

```python
restaurant_id: Annotated[int, Path(ge=1, le=BIGINT_MAX)]
# 양수이면서 DB 번호 범위 안인 값만 서비스로 넘긴다.
```

| 입력·상황 | 처리 | 의미 |
| --- | --- | --- |
| 정수로 바꿀 수 없는 번호 | 422 | 입력 형식 오류 |
| 0·음수·BIGINT 상한 초과 | 422 | 허용 범위 밖 입력 |
| 범위 안이지만 없는 식당 | 404 | 올바른 형식의 리소스 조회 실패 |
| 다른 사람의 식당 | 권한 규칙에 따른 거절 | 자료형 검증과 다른 단계 |
| 매우 큰 페이지 번호 | 페이지 상한 검증 | 계산한 offset이 DB 범위를 넘지 않게 제한 |

화면 예약 도중 식당이 삭제된 경우에도 JSON 오류를 그대로 보여 주지 않고 404 안내 화면으로 바꿨다. 입력 검증과 업무상 존재 확인, 화면 표시를 각각 나눠 처리한다.

### 3) 무작위 정렬과 페이지 이동의 충돌

식당 목록을 열 때마다 섞으면 새로운 식당을 보여 줄 수 있지만, 다음 페이지에서도 새로 섞으면 1쪽의 식당이 2쪽에 다시 나오거나 일부가 빠질 수 있다.

```python
seed = seed or secrets.token_hex(4)  # 처음 열 때만 새 순서 선택
page_base = request.url.include_query_params(seed=seed)
```

```jinja2
{% set base = page_base or request.url %}
<a href="{{ base.include_query_params(page=result.page + 1,
                                    page_size=result.page_size) }}">다음</a>
```

| 동작 | seed | 기대하는 순서 |
| --- | --- | --- |
| 처음 목록 열기 | 새로 생성 | 새로 섞인 목록 |
| 다음·이전 페이지 이동 | 링크에서 전달받은 값 유지 | 같은 목록의 다른 구간 |
| 새 검색 | 새 검색 흐름에서 다시 선택 | 검색 결과의 순서를 새로 결정 |

seed는 인증 비밀값이 아니라 정렬 재현용 값이다. 또 동일한 seed를 썼다고 동시 데이터 추가·삭제까지 고정되는 스냅샷 조회가 되는 것은 아니다.

### 4) 업무 상태 변경은 기존 예약 서비스에 위임하기

입장 확인·노쇼·취소 이유 같은 예약 규칙은 예약 담당이 구현했다. 내 작업은 화면 버튼·입력·상태 표시를 그 규칙에 맞춰 연결하는 부분이다.

| 화면 기능 | 내가 연결한 부분 | 기존 규칙을 사용하는 부분 |
| --- | --- | --- |
| 손님 취소 | 내 예약 화면의 취소 요청 | 예약 취소 가능 여부·저장 |
| 운영자 입장·노쇼 | 버튼·요청·결과 표시 | `can_check_in`, `can_mark_no_show`, 처리 서비스 |
| 운영자 취소 | 사유 선택·메모 입력 | 요청자·사유에 따른 취소 규칙 |
| 관리자 취소 | 사유·필수 메모 입력 | 관리자 권한·허용 사유 검증 |
| 예약 상태 표시 | 공통 Jinja2 조각 | 예약 데이터의 상태·입장·취소 기록 |

템플릿에서 버튼을 숨기는 것은 사용성 처리다. URL을 직접 호출할 수 있으므로 서버에서도 같은 권한·상태 조건을 검사해야 한다.

```python
can_check_in = reservation.can_check_in(
    user, now, slot.starts_at, slot.ends_at, owner_id
)
# 화면에 버튼을 보여 줄지 도메인에 묻는다. 여기서 규칙을 다시 만들지 않는다.
```

노쇼 처리와 잔여석 정책도 기존 예약 담당 규칙을 따른다. 노쇼가 단순한 일반 취소와 같은 좌석 반환 결과를 낸다고 임의로 가정하지 않는다.

### 5) 잔여석은 선택 화면과 완료 안내에서 같은 값을 보여 주기

시간 버튼에 '가능·불가'만 보이면 예약 뒤 몇 석이 줄었는지 알기 어렵다. 선택 시간대와 완료 안내 모두 실제 슬롯의 `remaining`을 표시하도록 바꿨다.

```jinja2
{% if done_slot.remaining == 0 %}매진 · {% endif %}
남은 {{ done_slot.remaining }}석
```

| 값 | 보여 줄 의미 | 주의점 |
| --- | --- | --- |
| 잔여석 > 신청 인원 | 현재 조회상 신청 가능 | 저장 직전에는 서버가 다시 확인 |
| 잔여석 < 신청 인원 | 자리 부족 | 전체 정원이 0이라는 뜻은 아님 |
| 잔여석 = 0 | 매진 · 남은 0석 | 오류의 원인도 같은지 확인 |
| 시작 시각 경과 | 지난 시간 | 자리 수와 별개 조건 |

매진을 보여 주려는데 이미 그 시간에 예약한 계정으로 요청하면 중복 예약 오류가 먼저 날 수 있다. 시연할 실패 원인 외의 조건을 제거해야 원하는 분기를 검증할 수 있다.

시연 앱에서 매진 시간 버튼을 누를 수 있게 한 것은 실패 응답을 보여 주기 위한 설정이다. 실제 예약 서비스의 매진 검사를 해제한 것이 아니다.

### 6) 관리자 조회 — 방문 시각과 예약 접수 시각 구분

관리자가 손님이 방금 예약한 식당을 바로 찾도록 식당 검색과 최근 예약 접수순 표를 추가했다. 정렬 기준은 슬롯의 방문 시각이 아니라 예약이 생성된 시각이다.

```python
latest = (
    select(ReservationSlotModel.restaurant_id,
           func.max(ReservationModel.created_at).label("received"))
    .select_from(ReservationModel)
    .join(ReservationSlotModel, ReservationSlotModel.id == ReservationModel.slot_id)
    .group_by(ReservationSlotModel.restaurant_id)
    .subquery()
)
# 식당별 가장 최근 접수 시각을 만든 뒤 식당 목록에 연결한다.
```

| 요소 | 역할 | 구분할 점 |
| --- | --- | --- |
| `max(created_at)` | 식당별 가장 최근 예약 접수 | 마지막 방문 시간과 다름 |
| `outerjoin` | 예약 없는 식당도 포함 | 접수 시각이 없는 행 처리 필요 |
| `nulls_last()` | 접수 기록 없는 식당을 뒤에 배치 | 정렬 동점은 이름·ID로 보완 |
| 부분 이름 검색 | 상호로 식당 찾기 | 필요 없는 개인 정보는 노출하지 않기 |
| 시연 표 주기 갱신 | 새 예약의 위치를 보여 주기 | 시연 앱의 동작과 일반 운영 기능을 구분 |

### 7) 시연 로그·데이터·문서의 역할

| 도구·자료 | 목적 | 증명하지 못하는 것 |
| --- | --- | --- |
| 시연 로그 창 | 화면 요청과 서버 오류를 함께 보기 | 로그 색이 정상이라고 데이터 저장까지 확정되는 것은 아님 |
| 가짜 데이터·시드 | 역할·식당·시간대를 재현 가능하게 준비 | 실제 고객·운영 데이터가 아님 |
| 상태 코드별 시나리오 | 정상·거절 분기를 같은 순서로 설명 | 모든 조합을 검사하는 자동 테스트의 대체는 아님 |
| 실제 DB 확인 | 예약 수·좌석 수의 변경 확인 | 다른 환경의 성능·동시성 결과까지 일반화 불가 |
| 최신 API 문서 | 구현된 경로·권한·범위 설명 | 문서 수정만으로 앱이 바뀌지는 않음 |

대표 사진과 지역 데이터도 시연을 구분하기 쉽게 정리했다. 시연용 데이터는 실제 식당 운영 정보로 소개하지 않는다. 로그 창에는 내부 정보가 나올 수 있으므로 배포용 기능과 분리한다.

## 4. 실수 및 트러블슈팅

### 발생한 문제 요약

- 상황: 쿠키 로그아웃 뒤 토큰이 남고, 큰 번호 입력은 500을 만들며, 목록의 페이지 이동에서 중복·누락이 생길 수 있었음
- 원인: 화면 상태와 서버 인증 상태를 따로 처리했고, 입력 상한과 정렬 상태를 다음 요청에 충분히 전달하지 않았음
- 해결: 기존 로그아웃 서비스 연결, 경로·페이지 상한 검증, 페이지 링크의 seed 유지, 화면 전용 오류 안내 적용
- 해결 결과: 당시 PR·작업 기록에 자동 테스트와 실제 DB·화면 확인이 남아 있음. 이번 작성에서는 재실행하지 않음

### 시연하면서 구분할 부분

| 문제 | 원인 | 처리 |

| 새 예약을 관리자가 찾기 어려움 | 운영자·식당 목록을 차례로 탐색 | 상호 검색과 최근 접수순 표 |

## 5. 오늘의 핵심

- ⭐️ 반드시 기억할 내용: 화면 입력·인증·정렬 상태를 다음 요청까지 일관되게 이어야 한다.
- 💡 참고로 알아둘 내용: 관리자에게 필요한 최근 접수순 조회와 손님의 방문 시간 조회는 기준이 다르다.
- ⚠️ 헷갈리기 쉬운 주의점: 시연용 버튼·데이터는 서버의 업무 규칙을 우회하는 기능이 아니다. 테스트 통과·실제 DB 확인·문서 검토도 구분한다.
- 한 문장 요약: 사용자에게 보이는 성공·실패가 서버의 실제 판단과 상태를 정확히 설명하도록 연결한다.
