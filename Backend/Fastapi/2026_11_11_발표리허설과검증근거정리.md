## 2. 개념과 용어 정리

### 1) 기능 목록보다 서비스 흐름으로 설명하기

리허설에서는 약 13분의 설명을 10분으로 줄이는 방향을 논의했다. 모든 기능과 모든 팀원의 오류 사례를 나열하기보다 손님의 예약부터 역할별 처리까지 한 흐름으로 연결하는 방식이다.

| 흐름 | 보여 줄 내용 | 설명에서 분리할 책임 |
| --- | --- | --- |
| 손님 | 가입·로그인 → 검색 → 예약 → 내 예약·취소 | 화면 연결과 인증·예약 규칙 |
| 운영자 | 내 식당 예약 → 입장·노쇼·사유 있는 취소 | 버튼·상태 표시와 도메인 상태 변경 |
| 관리자 | 전체 식당·예약 확인과 관리 | 관리자 조회 범위와 개별 식당 소유권 |
| 핵심 트러블슈팅 | 동시 요청에서 정원 초과를 막는 흐름 | 예약 담당 구현과 내가 검토한 개념 |

내 역할은 시연 영상·권한별 화면 설명 관련 협업으로 정리되어 있다. 영상 재편집과 전체 발표 자료 수정은 다른 담당의 작업이므로 내 구현 실적으로 옮기지 않는다.

### 2) 4계층은 폴더 수가 아니라 책임으로 설명하기

| 계층 | 설명할 핵심 | 예약 화면에서의 예 |
| --- | --- | --- |
| 표현 | 입력을 받고 결과를 표현 | 폼·라우터·템플릿·HTTP 상태 |
| 응용 | 업무 처리 순서와 트랜잭션 조율 | 조회 → 규칙 적용 → 저장 |
| 도메인 | 업무 상태·불변 규칙 | 정원·취소·입장·노쇼 가능 여부 |
| 인프라 | DB·외부 기술의 실제 처리 | SQLAlchemy 조회·행 잠금·저장 |

화면에 '예약하기' 버튼을 붙인 것과 정원·중복·잠금 규칙을 구현한 것은 다르다. 내 화면 코드는 기존 서비스를 호출해 결과를 표시했고, 해당 규칙 구현은 다른 담당의 기여로 설명한다.

의존 방향도 요청이 내려가는 실행 순서와 똑같은 화살표라고 단순화하지 않는다. 업무 규칙이 DB·웹 프레임워크에 묶이지 않도록 인터페이스와 구현을 구분한 이유를 설명하는 것이 중요하다.

### 3) 화면의 빈자리와 예약 순간의 판정

빈자리 화면을 본 시각과 예약 버튼을 누른 시각은 다르다. 그 사이 다른 손님이 예약하면 화면에서 본 값은 오래된 정보가 된다.

```text
빈자리 조회: 현재 참고할 값 표시
예약 요청: 인증·입력 검사
         → 트랜잭션에서 슬롯 잠금
         → 최신 잔여석·중복·시간 규칙 재확인
         → 예약과 좌석 변경 저장
         → 커밋
```

위 흐름은 팀에서 공유한 예약 처리 설명이다. 내가 그날 예약 잠금 코드를 새로 구현하거나 동시성 실험을 수행했다는 뜻은 아니다.

| 검사 위치 | 맡는 일 | 맡기면 안 되는 최종 판단 |
| --- | --- | --- |
| HTML 버튼 | 선택할 수 있는 시간 안내 | 화면에서 읽은 잔여석만으로 예약 확정 |
| 입력 스키마 | 형식·범위 확인 | 현재 DB의 정원·중복 상태 확정 |
| 예약 트랜잭션 | 최신 상태와 업무 규칙 재판정 | 커밋 이전 결과를 최종 저장처럼 설명 |
| 완료 화면 | 처리된 예약과 잔여석 표시 | 다른 요청까지 영구히 같은 상태라고 보장 |

### 4) 동시성 테스트는 실제로 동시에 부딪혀야 한다

팀에서 공유한 사례는 락을 제거해도 테스트가 통과했던 문제다. DB 연결 준비 시간이 달라 요청들의 시작이 어긋나면 실제 경쟁이 일어나지 않을 수 있다.

| 확인 조건 | 필요한 이유 |
| --- | --- |
| 같은 슬롯에 요청 | 서로 다른 데이터를 바꾸면 경합이 없음 |
| 시작 시점 맞추기 | 연결 준비 때문에 순서대로 실행되는 현상 줄이기 |
| 정원에 비해 충분한 요청 | 초과 예약 위험을 드러내기 |
| 최종 DB 상태 확인 | 응답 성공 개수만으로 정합성을 단정하지 않기 |
| 락 제거 비교 | 보호 장치가 없어도 통과하는 무의미한 검사가 아닌지 확인 |

동시 요청 수만 크게 적었다고 동시성 검증이 되는 것은 아니다. 어떤 경합을 만들었고, 어떤 데이터 불변식을 확인했는지 함께 설명해야 한다.

```python
# 발표 설명용 의사코드. 이날 내가 실행한 테스트나 구현 코드가 아님
await ready.wait()                  # 요청들의 출발 조건 맞추기
result = await request_same_slot()  # 같은 슬롯을 대상으로 요청
# 모든 요청이 끝난 뒤 정원·예약 수를 DB에서 확인한다.
```

### 5) 성능 숫자는 대상·조건·방법과 함께 말하기

리허설에서 공유된 성능 결과에는 단일 기능의 처리 시간, 여러 요청이 몰릴 때 다른 API가 기다린 시간 등이 섞여 있었다. 측정 대상이 다르면 하나의 개선율로 합칠 수 없다.

| 함께 밝혀야 할 것 | 예시 질문 |
| --- | --- |
| 측정 대상 | 로그인 자체인가, 다른 API의 지연인가? |
| 실행 조건 | 요청 수·데이터·DB 연결 조건이 같은가? |
| 측정 방법 | 실제 DB 요청인가, 가짜 의존성 테스트인가? |
| 비교 코드 | 어떤 변경 전후인가? |
| 결과 범위 | 평균인가, 한 번의 실행인가? 실패·대기 요청도 포함했는가? |

다른 담당이 공유한 해싱·DB 연결 점유 개선을 내 최적화로 소개하지 않는다. 이 글에서는 측정 조건을 직접 재확인하지 않은 수치를 새로운 개인 측정 결과로 적지 않는다.

### 6) UI 로그·API 로그·DB 결과가 각각 보여 주는 것

| 근거 | 알 수 있는 것 | 더 확인할 것 |
| --- | --- | --- |
| 화면 | 사용자가 보는 결과·복귀 경로 | 실제 요청과 저장 상태 |
| 요청·오류 로그 | 어떤 경로에서 어떤 응답이 났는지 | 최종 DB 데이터와 원인 |
| DB 재조회 | 예약·좌석 상태의 실제 반영 | 권한·실패 응답의 외부 표현 |
| 자동 테스트 | 정해진 조건의 기대 동작 | 실제 사용 환경과 다른 의존성 |
| 문서·PR | 구현·검토 범위와 이력 | 그 시점의 코드·실행 근거 |

시연 영상은 처음에 로그가 의미하는 흐름을 안내하고, 재생 중 설명을 줄이는 방향을 논의했다. 기능 흐름을 보여 주는 영상과 동시성·성능을 입증하는 실험은 별도 근거가 필요하다.

### 7) 발표에서 구현과 검토를 구분하기

| 말할 내용 | 정확한 표현 |
| --- | --- |
| 내가 작성한 화면 | 로그인 쿠키·오류 안내·역할별 조회·예약 결과 표시를 연결 |
| 재사용한 기능 | 인증·슬롯·예약 서비스와 도메인 규칙 사용 |
| 팀에서 공유한 검사 | 다른 담당의 동시성·성능 사례를 검토 |
| 아직 확인되지 않은 일 | 재편집·제출·배포 완료를 임의로 선언하지 않음 |

발표를 짧게 만들 때 근거를 없애는 것이 아니라, 핵심 결과만 본문에 남기고 조건·실패 사례·코드 차이는 질의응답에서 설명할 수 있도록 구분한다.
